## 1. What was built

### Plan, as written before building

**The question identifier is `QuestionOut.turn`.**
It already exists, it is unique within a session, and a question's text never changes once the client has it: a pending question is fixed until it's answered, and a failed first question is never sent to the client.
M3's D12 proposed `session_id` + turn for `/tts`, so no `question_id` was added.
`/tts` takes `{session_id, turn}` and `/answers` takes an optional `turn`.

**E13 against Claude Code's M3 proposal.**
The M3 proposal was "`AnswerRequest` carries the turn it answers and the server refuses a mismatch, plus a `GET` for the current question".
E13 is the same turn check plus a replay of the last response; the `GET` isn't in E13 and wasn't built.
That's not a material difference, so this didn't stop the run.

**Not changed:** v1's MiMo client, voice map, voice-design strings and browser-voice selection (E12), and every prompt template.

### Slice 1: backend (`f44c1f4`)

- `POST /tts` (`backend/defense_routes.py:241`) takes `{session_id, turn}`, never text; extra fields are refused with 422.
  It looks up the question the backend generated (`Defense.asked`, written when a question becomes pending) and the asking panelist's archetype, calls v1's `synthesize_speech` unchanged, and returns `audio/wav`.
  No audio is kept after the response.
- Errors per E3: unknown session 404, question not in the session 404, the third call for a question 429 `tts_limit` (failed calls count), MiMo error or invalid audio 502 `tts_failed`, no key 503 `tts_unavailable`.
- E4: `backend/tts.py` wraps v1's client and raises on empty bytes and on bytes that don't start with `RIFF`.
- E5: `/tts` is a plain `def` route, so FastAPI runs it in its threadpool, and it never takes the turn lock.
- E6: `/status` and `/health` return `tts_available`, true when `MIMO_API_KEY` is set and not blank.
- E2: `GET /status` is the browser's route; `GET /health` stays on the same handler, marked deprecated in the schema (`backend/app.py:206`).
- E13: `/answers` takes an optional `turn` (`backend/defense_routes.py:209`).
  The turn just answered gets its stored `AnswerResponse` back with no Gemini call, checked before the "defense is finished" check so a lost response to the final answer also replays.
  The open turn is processed.
  Anything else is 409 `stale_question`.
  Leaving `turn` out keeps M2's behaviour.
- `MIMO_API_KEY` is a `SecretStr` in `backend/settings.py`, read without the `ADS_` prefix, like `GEMINI_API_KEY`.

   It's a polish-milestone question (section 5).
2. **v1's 12 s MiMo timeout isn't a total-time limit.**
   Three of four calls took over 20 s through v1's client, which sets `timeout=12.0`; httpx applies that per network operation, so a response that keeps streaming isn't cut off.
   Not a bug in itself, but "fails within 12 s" isn't a guarantee v1's docstring gives.
3. **In dev mode, Panel voices spend two MiMo calls per question.**
   StrictMode runs the effect twice; the first request is aborted in the browser, but the backend may already be synthesizing it.
   That uses the whole 2-call budget, so a Replay that needs a refetch would get `tts_limit` and fall back.
   Production makes one call.
   Worth knowing before I test voices locally with `npm run dev`.

## 3. Concepts map

**`fetch` with binary responses and `Blob`.**
`fetch` gives a `Response` whose body can be read as text, JSON, or raw bytes; `response.blob()` reads it as a `Blob`, an immutable chunk of binary data with a MIME type, which is what audio is.
`src/api/client.ts:174` reads `/tts` that way instead of as text, which would corrupt the bytes.

**Object URLs and why they're revoked.**
`URL.createObjectURL(blob)` gives a short `blob:` URL that an `<audio>` element can play, pointing at the Blob in the page's memory.
The browser keeps that Blob alive as long as the URL exists, so each clip is revoked when its turn ends (`src/voice/useQuestionVoice.ts:81` creates it, `:92` revokes it), or every question's audio would pile up in memory.

**`HTMLAudioElement`.**
The `<audio>` element's JavaScript object: set `src`, call `play()` (which returns a promise), and listen for `playing`, `ended` and `error`.
The app keeps one, created with `new Audio()` (`src/voice/player.ts:26`), so a new clip always replaces the old one.

**The browser autoplay policy.**
Browsers block sound a page starts on its own until the person has interacted with it; a blocked `play()` rejects with `NotAllowedError`.
The gate and Start clicks play a silent WAV inside the click to unlock audio (`src/voice/player.ts:49`), and a play that's still refused shows the play button (`:90`).

**The `speechSynthesis` API.**
The browser's built-in text-to-speech: build a `SpeechSynthesisUtterance` with the text, voice, pitch and rate, and pass it to `speechSynthesis.speak()`.
Its voice list loads asynchronously and differs by browser and OS, which is why v1 waits for `voiceschanged` and walks a preference list (`src/voice/browserVoice.ts:49`, `:73`, `:91`).

**`AbortController`.**
An object whose `signal` is passed to `fetch`; calling `abort()` cancels the request and makes `fetch` reject.
The voice hook makes one per question (`src/voice/useQuestionVoice.ts:48`) and aborts it when the turn changes (`:89`), so a late clip for an old question never plays.

**Idempotency, and why replaying the last response fixes lost responses.**
An operation is idempotent when doing it twice has the same effect as doing it once.
With the turn number attached, resending an answer the server already scored returns the stored result instead of scoring it again or treating it as the next answer (`backend/defense_routes.py:209-212`, stored at `:227`), so "Try again" after a lost response is always safe.

**Why sync code in an async endpoint stalls a one-worker server.**
An `async def` route runs on the event loop, the single thread that handles every request in turn, so a blocking 20 s MiMo call inside it freezes every other request for 20 s.
A plain `def` route runs in a threadpool instead (`backend/defense_routes.py:241`); the negative control in section 1 shows the stall when it's made `async`.

**How ad-block filter lists match URLs.**
A list is lines of patterns: `||example.com/path` matches that domain and any subdomain followed by that path, and `@@` lines are exceptions; the extension checks every request a page makes against them.
`||onrender.com/health` (EasyPrivacy line 12418) matches `/health` on every Render app, which is why the browser now calls `/status` (`backend/app.py:204-207`).
