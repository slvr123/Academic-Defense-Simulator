## 4. D2 - the `App.frontDoor` flake

### Cause, reproduced

`renderApp()` installs fake timers with `shouldAdvanceTime: true`, so real elapsed time leaks into the fake clock.
The polling test asserts no poll has happened after `advance(1999)`.
If more than 1 ms of real time passes between the 202 and that assertion, the 2 s poll has already fired, which is what a loaded machine does.

Forced with a real 30 ms block (`Atomics.wait`, which fake timers can't touch) right after the upload is accepted, on the test as it is on `main`:

```
AssertionError: expected 1 to be +0 // Object.is equality
      Tests  1 failed | 23 skipped (24)
```

The product schedules a plain 2 s `setTimeout` after the 202, and nothing in it races.
**Stop point A doesn't apply.**

### Fix, test code only

- `renderApp({ clock: 'strict' })` (`src/test/renderApp.tsx`) installs fake timers that move only when the test advances them.
- On that clock Testing Library's `asyncWrapper` hangs: it drains each user-event call with a `setTimeout(0)` that it only advances when it detects Jest's fake timers.
  The strict clock stubs a `jest` global with `advanceTimersByTime`, and `setup.ts`'s `vi.unstubAllGlobals()` removes it after each test.
- The four upload-polling tests (queue, embedding and ready every 2 s; scanned PDF; other failure; network pause and resume) use the strict clock and `getBy*` after each `advance`.
  The main one now counts every poll exactly: 0, 1, 2, 3, then still 3 after 10 s.

The same 30 ms block on the new test:

```
      Tests  1 passed | 23 skipped (24)
```
