### E2. Ad-blocker fix — diagnose first, then a pre-committed rule
**What happened:** on 2026-10-26, in my normal Chrome with an ad-blocker extension on, every call to the backend failed with `net::ERR_BLOCKED_BY_CLIENT`. In Incognito (extensions off), the live site worked. So a common blocker breaks the app for real visitors.
**Claude's hypothesis, unverified:** the hostnames start with `ads-` (`ads-backend-…`, `ads-frontend-…`), and ad-block filter lists block hostnames and paths that look like ad servers. "ADS" the acronym collides with "ads" the word. It could also be a path rule (e.g. `/health`).
**Diagnosis:** Code tests every URL the frontend requests (each endpoint path, on the real backend host, as an `xmlhttprequest` from the real frontend origin) against EasyList, EasyPrivacy and uBlock Origin's default lists, using a filter-matching library (e.g. Brave's `adblock` Python package or `@ghostery/adblocker`) in a gitignored scratch folder. This tool is never added to the app's dependencies. Show each URL, blocked or not, and the matching filter text.
**Decision rule:**
- **Hostname match** (a filter matches on `ads-`): rename to `defense-sim-api` (backend) and `defense-sim-web` (frontend), after confirming both names, plus a likely random suffix, pass the same test. Code updates `render.yaml`, `VITE_API_BASE_URL` and the docs. Creating the new services is mine (stop point); Code writes my exact Render checklist into the debrief. Only rename the frontend if its host matches too.
- **Path match only:** rename the matching paths (e.g. `/health` → `/status`), keep the old path as an alias so nothing deployed breaks, update the frontend and `gen:api`.
- **Both:** do both.
- **No match in any list:** stop renaming. Record the result, and ask me for my extension's name in the debrief. Don't guess a fix.
*Downside I accept:* a hostname rename means new Render services and new URLs; the old URLs die.

### E3. `POST /tts` contract
The endpoint takes `session_id` and the question's identifier (the existing one on `QuestionOut`, or an additive `question_id: str` if none exists), **never text**. The backend looks up the question text it generated and the panelist's voice, calls MiMo (`mimo-v2.5-tts-voicedesign`), and returns `audio/wav` bytes. If the endpoint accepted text, anyone could use my backend as a free TTS service on my key.
- At most 2 synth calls per question (one retry). The third → 429 with `code: "tts_limit"`.
- Unknown session → 404. Question not in this session → 404.
- MiMo error, timeout, or invalid audio (E4) → 502 with `code: "tts_failed"`.
- `MIMO_API_KEY` missing → 503 with `code: "tts_unavailable"`.
- The server holds no audio after the response is sent.
*Downside I accept:* more backend logic than a text-in endpoint.

### E4. Invalid audio raises (the dead-player fix)
v1 showed an empty `0:00 / 0:00` player on 2026-10-21. Suspected cause: MiMo returned empty audio, `""` decoded to `b""` without raising, and an `is not None` check let it through. The v2 TTS path raises when the decoded bytes are empty or don't start with a `RIFF` header, with tests that force each case. v1 code is not changed (no v1 fixes from here on); v2 wraps or validates around v1's MiMo client.

### E5. `/tts` must not block the server
The backend runs one uvicorn worker. A MiMo call takes about 6 s (v1.2.1 measured a 6.160 s median). If that call runs synchronously inside an `async` endpoint, the whole server stalls, `/health` and other users' turns included. `/tts` runs the MiMo call off the event loop (a plain `def` endpoint or `run_in_threadpool`). `/tts` does not take the per-session turn lock, so a Submit during playback never gets a 409. A test proves `/health` answers while a mocked 6 s `/tts` is in flight.

### E6. `/health` reports voice availability
Add `tts_available: bool` to `/health` (additive), true when `MIMO_API_KEY` is set. When it's false, the disclosure gate (E9) doesn't offer the MiMo option.

### E7. Client playback
- As soon as a question arrives, the client requests its audio. The text shows at once with the typewriter; the audio plays when it arrives, with a small "voice loading" indicator on the panelist until then.
- If I've already submitted that turn when the audio arrives, it's discarded.
- In-flight `/tts` requests are cancelled with `AbortController` when the turn changes or the screen unmounts, and playing audio stops.
- Each clip is cached as an object URL for replay within the turn. URLs are revoked in effect cleanup so they don't leak memory.
- A replay button on the current question. No auto-replay.
*Downside I accept:* the voice starts about 6 s after the text. No waiting screen is added for it.

### E8. Fallback
Any `/tts` failure (`tts_failed`, `tts_limit`, `tts_unavailable`, network) → browser `speechSynthesis` for that turn, silently. Text is always on screen, and voice is never required to proceed. There's no timeout-based switch to the browser voice, because a slow MiMo clip arriving after the browser voice started would talk over it.

### E9. Disclosure gate (ported from v1)
Before the first voiced question, I choose: **Panel voices** (the question text, which is derived from my document, is sent to Xiaomi's MiMo service) / **Browser voice** (stays on my device) / **No voice**. Port v1's disclosure wording; adjust only what's Streamlit-specific. The choice lasts for the session, lives in the reducer state, and isn't persisted. A client-side gate is enough: the person whose document is sent is the person clicking.

### E10. Autoplay
Browsers block audio that wasn't started by a click. The first clip plays off the gate choice or the "Start the defense" click. If a later autoplay is blocked, show a play button instead of failing silently.

### E11. Speaking indicator
The current panelist's avatar shows a speaking state while audio plays (MiMo or browser). CSS only, no new dependencies.

### E12. v1 voice behaviour is ported unchanged
The voice map, the per-archetype voice-design descriptions, and v1's browser-voice selection are ported as they are. Changing any of them is a v1 behaviour change and a stop point. The voice map's zero-margin constraint (a 10th male archetype, an avatar gender change, or a panel seating a 4th male breaks the test) stays as it is.

### E13. Lost-response fix: idempotent answers
**The bug (from M3 results):** if the server records a turn but the response is lost on the way back, "Try again" either hangs or submits the same answer to the *next* question, putting a wrong answer into the defense.
**Fix:** `POST /sessions/{id}/answers` takes the identifier of the question being answered (optional field, so old callers keep working).
- It matches the open question → process normally.
- It matches the question that was *just* answered → return that turn's stored response unchanged (200), with no re-scoring and no Gemini call. The server keeps only the last turn's response.
- Anything else → 409 with `code: "stale_question"`.
- A retry that gets 409 because the original request is still running → the client waits 3 s and retries, up to 10 times, then shows "Try again".

This supersedes M3's D16 409 row ("swallowed"). If Code's proposal in `v2.0-m3-results.md` differs materially from this, stop and show both.
*Downside I accept:* a change to M2's answer contract, plus a little memory per session for the stored response.
