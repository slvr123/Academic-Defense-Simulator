# v0.4b — Session Persistence: Decisions + Brief

**Scope:** Save-per-turn session persistence to local disk, resumable across
app restarts, scoped to local/self-hosted runs only. This is the v1.0

## Decision 1 — Persistence is local-only, behind a config flag (LOCKED)

`ADS_PERSISTENCE_ENABLED` env var (read in `load_settings()`, same pattern as
the Gemini key sourcing), **default off**. Deployed Streamlit Cloud stays
`st.session_state`-only exactly as today.

This one flag resolves both landmines identified in design:

1. **Ephemeral-disk honesty** — Streamlit Community Cloud recycles the
   container filesystem on restarts/redeploys, so disk persistence there is
   a promise the platform structurally breaks. The deployed app therefore
   doesn't make it.
2. **Cross-user privacy** — a shared sessions directory on a public deployment
   would let stranger A reload stranger B's session, uploaded thesis content
   included. Off by default, never enabled on the public instance, the
   directory simply doesn't exist there.

When the flag is off: no `sessions/` directory is created, no save calls fire,
no resume UI renders. Off-mode is behavioral parity with today, not a stubbed
version of persistence.

**In plain terms:** saving sessions to disk only happens on your own machine,
where the disk is really yours and really persistent. The public demo site
keeps working exactly like it does now — nothing saved, nothing to leak,
nothing to falsely promise.

## Decision 2 — One JSON file per session, extending the v0.2.5 export shape (LOCKED)

`sessions/{session_id}.json` (directory gitignored), where `session_id` is a
UUID4 minted at session start. Top-level `PersistedSession` Pydantic model,
serialized via `model_dump_json()` — no hand-rolled dict building. Contents:

- `schema_version: int = 1` (see Decision 7)
- `session_id`, created/updated timestamps, `stage` (in-progress / completed /
  aborted)
- The `DefenseProfile` (customizations included)
- The **post-generation panelist roster** — personas persisted verbatim, never
  regenerated on resume; regeneration would seat a different panel mid-defense
- Full transcript: every turn with question, answer, `AnswerScore`, panelist
  attribution — superset of the v0.2.5 export shape, not a rival schema
- Live state: current difficulty level, current speaker / turn index, the
  v0.3f follow-up retention counters
- **Document chunks as extracted text** — but *not* the PDF and *not* the
  embedding vectors

That last line is a real decision: on resume, chunks are **re-embedded
locally**. `all-MiniLM-L6-v2` is local, free, fast at this scale (a few dozen
vectors), and deterministic — same text in, same vectors out. Persisting numpy
arrays would bloat the file and add a serialization format for zero
correctness gain; persisting the PDF would duplicate a file the user already
has. Text chunks are the minimal sufficient state.

**In plain terms:** each session becomes one readable JSON file containing
everything needed to pick the defense back up — who the panelists are, every
exchange so far, how hard things currently are, and the relevant pieces of
your document. The one thing recomputed on resume is the document's search
index, because rebuilding it locally takes moments and always comes out
identical.

## Decision 3 — Save-per-turn, atomic writes, failures never kill the session (LOCKED)

Save fires after each *completed* turn (answer scored, next state computed),
at session completion, and on abort. A crash loses at most the in-flight turn.

Writes are atomic: write to `{session_id}.json.tmp`, then `os.replace()` onto
the real path — a crash mid-write can never leave a half-written file where a
good one used to be.

**Save failure is non-fatal:** disk error → log a warning, show a
non-blocking caption ("Couldn't save progress — session continues, resume may
be unavailable"), session proceeds. The live defense never dies because the
disk hiccuped. **Load failure is non-fatal to the app:** a corrupt or
unreadable file is skipped in the resume list with a visible note, never a
crash.

**In plain terms:** progress is saved after every question-and-answer, using a
write pattern that can't corrupt the file even if the power dies mid-save. And
if saving ever fails, you lose the safety net, not the session you're in the
middle of.

## Decision 4 — Resume entry point: intake screen, in-progress sessions only (LOCKED)

When the flag is on and in-progress session files exist, the intake screen
gains a "Resume a saved session" section above the fresh-upload flow: one row
per in-progress session showing document name, last-updated timestamp, and
progress ("turn 3 · 2 panelists heard"), with a Resume button and a Delete
button (confirm-on-click, deletes the file).

Completed and aborted sessions do **not** appear in the resume list — they're
retained on disk as the v1.0 analytics raw data (that retention is the point
of this slice per the roadmap), but they're not resumable and the UI doesn't
pretend they are. No auto-cleanup; deletion is always explicit and per-file.

**In plain terms:** when you open the app, unfinished defenses are listed
right there to pick up or discard. Finished ones quietly stay on disk as data
for the future analytics version — they just don't clutter the resume list,
because there's nothing left to resume.

---

## Decision 5 — Resume restores full transcript + exact live state; stateless rendering makes this correct by construction (LOCKED)

Resume rebuilds the complete UI transcript (the existing rendering already
collapses older turns — reused as-is) and restores exact live state:
difficulty, speaker/turn position, retention counters. The session continues
as if the restart never happened.

The architectural note worth recording: this is cheap **because of the Day 3
stateless-prompt-rendering decision.** Prompts are re-rendered every call from
structured state — persona re-injected, no growing chat history. There is no
hidden conversational context living only in memory that a restart destroys.
The persisted state *is* the entire input to the next prompt render. Resume
isn't a reconstruction effort; it's loading the same state the next turn would
have read anyway. Pattern 2 paying out, noted for the case study.

**In plain terms:** the app never relied on the AI "remembering" the
conversation — every question is generated fresh from saved facts about the
session. So after a restart, loading those saved facts back is literally all
it takes; the panel picks up mid-defense with nothing lost and nothing
re-improvised.

---

## Decision 6 — Persistence is orthogonal to key mode (LOCKED)

The flag governs persistence; key mode (own-key vs. demo) governs quota. If
both persistence and demo mode are active locally, demo sessions persist and
resume like any other — but a resumed demo session re-enters under the same
demo turn cap, and `demo_session_used` semantics from v0.4a are unchanged.
No special-casing; the two systems don't know about each other beyond both
reading `load_settings()`.

**In plain terms:** saving sessions and choosing whose API key pays for them
are separate dials. Turning one doesn't secretly move the other.

---

## Decision 7 — Schema versioning: stamp now, migrate never (yet) (LOCKED)

`schema_version: 1` in every file. The loader accepts version 1 and rejects
anything else with a plain message in the resume list ("Saved with an
incompatible version"), never a crash. No migration machinery — writing
migration code for a schema with zero historical versions is premature
abstraction by definition. The stamp exists so that *if* the schema ever
changes, old files fail loud and identifiable instead of half-loading.

**In plain terms:** every file records which format it was written in. Today
there's only one format, so this does nothing — it's insurance that costs one
line now versus a debugging nightmare later.

---

## Call budget (standing constraint)

Zero LLM-call change. Saves and loads are pure disk I/O; re-embedding on
resume is local compute, not API traffic.

---

## Explicitly out of scope

- SQLite — JSON-on-disk first per the roadmap's own "only if earned" clause;
  nothing at a-few-files scale earns it
- Any persistence on the deployed instance (Decision 1 is the decision)
- Cloud/remote storage of any kind
- Analytics over the retained files (v1.0 — this slice produces the raw data,
  nothing more)
- Multi-device or shared resume
- Any prompt-template change
- Encrypting session files at rest (local single-user files; revisit only if
  the threat model ever changes)

   restore live state → re-embed chunks locally → next turn proceeds.
   Delete button with confirm.
6. Demo-mode interaction per Decision 6 — resumed demo session still under
