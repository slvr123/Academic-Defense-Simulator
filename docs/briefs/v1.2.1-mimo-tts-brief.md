*Claude proposed; I locked.*

No integration work happens until all three are measured and recorded. Each
produces a real artifact in `evidence/`, not a prose summary.

**0a — Browser baseline listening pass.** v1.2's DoD 5 was left open on purpose:
the by-ear pass was never performed, recorded as *not performed, assumed

and my own evidence standard forbids the comparison otherwise. Judge the two
named pairs:

- `ethics` + `technical` — Microsoft David, pitch 0.70 vs 1.15
- `results` + `industry` — Microsoft Mark, pitch 0.80 vs 1.20

This closes v1.2's DoD 5 as a side effect, which is the only reason it belongs
in this slice.

**0b — Voice-design distinctness probe.** Mimo's documented built-in voice set is
small (`mimo_default`, `default_zh`, `default_en`); the value of this slice rests
entirely on the v2.5 series' voice-design-by-text-description producing **nine
distinguishable archetype voices**. If it does not, Mimo offers three voices
against the browser's nine and this is a regression, not an upgrade.

**Correction appended 2026-07-31 (issued mid-session from chat, during Phase
1 execution):** the "three built-in voices" claim above was wrong. The preset
catalog is roughly seven-plus voices, mixed-language. This does not change

branch rule below stands unchanged.

**0c — Latency measurement.** Synthesis end-to-end for a realistic question
(~40–60 words), ten runs, min/median/max. This lands on top of the existing ~15s
generation time.

### Pre-committed decision rule — all branches enumerated

Written before any measurement, per the lesson codified after the sleep-fix rule
failure. A rule with an unreachable or swallowed branch is a malformed rule.

- **Branch A — 0b ≥ 7 distinguishable voices AND 0c median ≤ 3s:** proceed to
  Part 2 in full.
- **Branch B — 0b ≥ 7 distinguishable voices AND 0c median > 3s:** proceed, but
  audio is opt-in per session behind a UI toggle defaulting off, and the latency
  number goes in this doc. Slow narration a user chose is acceptable; slow

- **Branch C — 0b < 7 distinguishable voices:** **halt.** Record the finding, add

- **Branch D — Mimo TTS is no longer free, the v2.5 TTS model ids have moved, or
  the promo has lapsed:** **halt** under the standing Day 4 no-paid-API decision.

- **Branch E — none of the above / results ambiguous or unreadable:** **halt and

## Decision 5 — Archetype voice descriptions (LOCKED)

*Claude proposed; Sean locked.*

Nine natural-language voice descriptions, one per archetype, stored beside
`VOICE_PROFILES` in `academic_defense_simulator/panel.py` as a separate
`MIMO_VOICE_DESCRIPTIONS` mapping. **Separate, not merged into `VOICE_PROFILES`.**
The two providers have unrelated inventories and unrelated constraints; merging
them couples the browser map's zero-margin test to a provider that does not share
its scarcity.

Descriptions are authored to the existing archetype character, not invented
fresh. Gender assignments follow the current avatar set so the two paths stay
consistent for a user switching between them.

**This is the payoff, if it works.** Nine described voices dissolves the
three-male-voice scarcity that forced the two accepted collisions
(`ethics`+`technical`, `results`+`industry`) and made gender matching a
constraint fighting separation rather than a free property.

## Decision 6 — Fail-open to browser, per turn (LOCKED)

*Claude proposed; Sean locked.*

One branch at the render call site. When provider is `mimo`: attempt synthesis;
on **any** failure — network, auth, quota, malformed response, timeout — fall
back to the existing browser `speak()` call for that turn and continue. A single
turn's failure never disables the provider for the session, and never surfaces a
traceback into the defense flow.

Timeout is explicit and short. A failed synthesis must not extend the pause
beyond what the browser path would have taken.

Fail-open matches the relevance-gate and answer-suggestions precedent. The
defense is the product; audio is garnish and must never block it.

---

## Decision 7 — Synthesis caching (LOCKED)

*Claude proposed; Sean locked.*

Synthesized audio is cached on `(text_hash, archetype)` via `st.cache_data`.

Non-negotiable, not an optimisation. Streamlit re-runs the entire script on every
widget interaction; without a cache, one question is re-synthesized on every
rerun of the page it appears on — burning quota and re-triggering audio. This is
the single most likely way this slice produces a bad bug.

## Decision 9 — Model pinning and deprecation tripwire (LOCKED)

*Claude proposed; Sean locked.*

The v2.5 TTS model id is read from Xiaomi's live docs at implementation time and
pinned in one constant with a comment recording the date it was read. **This doc
deliberately does not name the model id** — the V2 series was retired 2026-06-30
with model names invalidated, roughly four months after launch, and a stale id
copied out of a design doc is a guaranteed future breakage.

Integration facts worth recording now, all subject to confirmation against live
docs during 0b:

- Endpoint is OpenAI-chat-completions-shaped, `api-key` header.
- Target text goes in an **assistant**-role message, not user. Non-obvious; cost
  someone a debugging session.
- Audio returns base64 in the message's audio payload.
- `<style>...</style>` tags at the start of the text control expression.

When the pinned id breaks, the fix is Branch D of Decision 0: halt and record.
Not a scramble to the next model.

**Correction appended 2026-07-31 (issued mid-session from chat, during Phase
1 execution):** I announced a brief amendment mid-session meant to supersede
this decision, but the patch content did not reach Code — the message cut
off after "[then the patch]." Code flagged the gap and asked for the missing
text; none arrived, and I told it to continue. Code proceeded on this
decision's own standing instruction to confirm these facts against Xiaomi's
live docs rather than trust the brief, and found one inaccuracy: style
control is **not** `<style>...</style>` XML tags. It is a bracket prefix on
the synthesized content itself — `(Style)Content`, full-width
`（Style）Content`, or `[Style]Content` — confirmed against
`https://mimo.mi.com/docs/en-US/quick-start/usage-guide/audio/speech-synthesis-v2.5`
on 2026-07-31. The other three integration facts above (OpenAI-chat-
completions-shaped endpoint, `api-key` header, target text in the
assistant-role message, base64 audio in the message's audio payload) were
confirmed correct as written against the same live docs. Model id pinned as
`mimo-v2.5-tts-voicedesign`, read 2026-07-31 — see
`scripts/probe_mimo_voices.py::MODEL_ID`. The request body's `audio` object
carries no `voice` key (`{"format": "wav"}` only) — voicedesign omits it,
presets require it, so this is checkable evidence that the pinned model,
not a preset, produced the nine files in `evidence/v1.2.1-voices/`.

The `api-key` header was also confirmed empirically, not just from the
docs: `scripts/probe_mimo_voices.py` sends only that header (no `Authorization:
Bearer` fallback), and all 19 calls in Phase 1 (9 distinctness + 10 latency)
returned 200 with decodable audio.

TTS rate limits (resolve-before-integration item, previously unmeasured):
confirmed 2026-07-31 against
`https://mimo.mi.com/docs/en-US/api/guidance/rate-limit` — `mimo-v2.5-tts`,
`mimo-v2.5-tts-voiceclone`, and `mimo-v2.5-tts-voicedesign` all share 100
RPM / 10M TPM, scoped to the sum of all API keys on the account calling the
same model. No free-tier-vs-paid distinction is documented.
