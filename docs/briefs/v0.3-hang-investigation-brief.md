## What is known (constraints on the diagnosis)

- **Symptom:** browser (Streamlit) sessions freeze deterministically at ~the
  6th sequential Gemini call. CLI sessions run clean through the same engine
  path every time — most recently re-confirmed by 0.3c's live 6-turn run.
- **Localization:** the engine has run clean headless across v0.3a, v0.3b, and
  v0.3c. The fault is in `streamlit_app.py` (thin driver) or in the interaction
  between Streamlit's execution model and blocking calls made during a script
  run. 0.3b's engine/UI extraction (Decision 6) is what makes this bisection
  valid.
- **Prior partial fix:** a `threading.Lock` closed part of the symptom;
  something further remains. The lock itself is therefore also a suspect.
- **Diagnostic weight of determinism:** races are flaky; failures at a fixed
  call count usually indicate a fixed resource being exhausted or a fixed
  interaction pattern (e.g., the Nth rerun), not a timing-dependent race.

## Ranked hypotheses and their log signatures

| # | Hypothesis | Signature in Phase 1 logs |
|---|---|---|
| H1 | **Lock deadlock/starvation across cooperative script stops.** Streamlit stops superseded runs cooperatively (at the next `st.*` call); a thread blocked inside a Gemini call or `time.sleep(13)` holds the lock long past its run's supersession, or is stopped mid-critical-section without release. New reruns block on `acquire()` → app presents frozen. | Two or more script-run counters alive concurrently; at freeze time, lock held by a thread whose script-run counter is stale; the newest run's last log line is an acquire attempt. |
| H2 | **Client/connection exhaustion.** Provider or underlying `google-genai` client constructed per rerun in the script body (not cached); superseded runs leak clients/connections; after N, the next request blocks on a pool slot inside the API call. Fits fixed-count determinism and CLI-clean (one process, one client) best. | `id(provider)` differs across reruns; at freeze time, the newest run's last log line is *call started* (never *call returned*), with lock held normally by that same thread. |
| H3 | **Residual `st.session_state` race** despite the lock — the original diagnosis, incompletely fixed. Ranked last: the lock already partially addressed it, and pure state races rarely produce fixed-count determinism. | Interleaved state reads/writes from two run counters *without* either H1's stale-lock-holder or H2's changing client id; freeze coincides with a state mutation from a superseded run. |

## Phase 1 — Instrumentation (Streamlit layer only; zero engine changes)

Add temporary diagnostic logging to `streamlit_app.py` (and, if the lock lives
elsewhere in the driver layer, there). **The engine, provider internals, prompt
templates, and all business-logic modules are untouched.** Logging goes to a
file (`hang_diag.log`) via the `logging` module — stdout interleaving through
Streamlit's runner is not reliable evidence.

Log, with timestamp on every line:

1. **Script-run counter** — increments in `st.session_state` at the top of
   every script execution; every log line carries it.
2. **Thread id** — `threading.get_ident()` on every line.
3. **Lock events** — acquire-attempt, acquire-success, release, each with the
   holding thread id. Wrap via context manager only; if any bare
   `lock.acquire()` exists, that finding gets logged in the session notes (it
   is itself evidence for H1).
4. **Provider identity** — `id(provider)` (and `id()` of the underlying client
   object if reachable from the driver without modifying the provider module)
   logged immediately before each engine call.
5. **Call lifecycle** — one line immediately before each engine turn call
   (*call started*, with global call counter), one immediately after (*call
   returned*).

Then reproduce the hang once with full logging. The log file at freeze time is
the primary evidence artifact of the session — attach it raw.

**Verify:** `hang_diag.log` from the frozen run pasted (or attached whole),
freeze point annotated.

## Phase 2 — Decision tree (fix only what the logs prove)

- **H2 signature** → cache the provider (and the embedding model, if it is
  also constructed per rerun) via `st.cache_resource` in the driver; audit
  that exactly one client exists for the app process lifetime. This is also
  the fix ROADMAP already anticipates for v1.0 cold-start hardening — note
  the overlap in the session notes.
- **H1 signature** → **single-flight turn execution**: one blocking sequence
  per script run; input widgets disabled (`st.form` submit or disabled state)
  while a turn is processing so a rerun cannot race a live API call; all lock
  usage through context managers; lock scope reviewed to exclude blocking API
  calls where possible. Do not attempt to make concurrent runs "safe" — make
  them not happen.
- **H3 signature** → report the exact interleaving found before fixing; the
  fix must name the specific state key and the specific racing writers, not
  "add more locking."
- **No signature matches** → STOP. Commit nothing beyond instrumentation on a
  branch, report the log evidence back in chat. No improvised fixes.

If H1 and H2 signatures *both* appear, fix H2 first (cheaper, less invasive),
re-run the repro, and only proceed to the H1 fix if the hang persists — one
variable at a time.

**Verify:** the matched signature quoted from the log + the diff of the fix.
