# ADS v2.0 - Milestone 1: backend skeleton + ingest go/no-go

Brief written 2026-10-19.
Claude proposed the plan details during our session on 2026-10-19; I approved them with the adjustments in the last section the same day.

## Goal

Build the FastAPI backend skeleton for ADS v2.0: PDF upload, a single-worker embedding queue, in-memory sessions, and a memory measurement path, so I can make a go/no-go call on Render's free tier (512 MB) with the largest PDF.

## Context

- ADS is a RAG-based thesis defense panel simulator.
  v1 (`main`) is Streamlit + PyMuPDF + sentence-transformers + google-genai + numpy + pydantic.
  Retrieval is numpy cosine similarity (locked since v0.1, no vector DB).
- The engine/UI loop was previously extracted into a standalone module.
  Reuse it; don't fork it.
- Hosting spike: branch `spike/render-onnx`, results in `docs/v2.0-hosting-spike-results.md`.
  It runs all-MiniLM via `onnxruntime` directly, with the `tokenizers` library, mean pooling and normalisation.
  Verdict: GO on Render free, batch size 1, peak 370 MB.

## Locked decisions (do not revisit)

- FastAPI, run by uvicorn with exactly ONE worker.
  Each worker would load its own model copy and its own session memory.
- Embeddings: port the spike's ONNX MiniLM path, batch size 1.
  Production dependencies must NOT include torch, sentence-transformers, or chromadb.
  sentence-transformers is allowed only as a dev/test dependency.
- Retrieval: one numpy matrix per session (rows = chunks, 384 float32 columns) plus parallel chunk metadata (text, page number, chunk id).
  Search = matrix @ normalised query vector, then top-k.
  No vector database.
- Ingest: one `asyncio.Queue` consumed by ONE background worker task started in the app's lifespan.
  The worker runs CPU-bound embedding in a thread (e.g. `asyncio.to_thread`) so the event loop stays responsive.
  At most 3 jobs may wait.
  A 4th upload gets `503` with a friendly message.
- Sessions: in-memory store keyed by uuid4.
  Idle TTL 30 minutes.
  Hard cap on live sessions.
  Losing sessions on restart is accepted.
  An unknown or evicted id returns `404`.
- Load the ONNX model once at startup (lifespan), not on first request.
  `/health` must not do heavy work.
- `POST /sessions` takes multipart: the PDF file plus a `panel` JSON field (Pydantic model).
  In M1 the panel is validated and stored but nothing uses it yet.
  Provide sensible defaults so it can be omitted.
- Upload limits are checked BEFORE enqueueing: max MB and max pages.
  Start with 20 MB / 150 pages as provisional values; they will be finalised from the measurement.
- All limits come from env vars with defaults, in one settings module (pydantic-settings is fine): queue size, max live sessions (default 5), TTL, max MB, max pages, top-k.
- Do NOT touch the v1 Streamlit app or its requirements.
  v1 must still run and deploy exactly as before.

## Scope (M1 only)

1. Backend package layout: a `backend/` directory with its own requirements, importing the existing engine/chunking modules rather than copying them.
   If importing creates a dependency problem, stop and ask before restructuring anything.
2. `embedder` module ported from the spike, with an explicit `max_seq_length` that matches sentence-transformers' setting for all-MiniLM-L6-v2.
3. Parity test: embed about 20 real chunks from a sample PDF with both the ONNX embedder and sentence-transformers, and assert cosine similarity >= 0.999 for every pair.
   It runs only when sentence-transformers is installed.
4. Endpoints:
   - `GET /health` -> `{status, model_loaded}`
   - `POST /sessions` -> `202` `{session_id, status: "queued", queue_position}`; `413` or `422` on limit or validation failure; `503` when the queue is full or the live-session cap is reached.
   - `GET /sessions/{id}` -> `{status: queued|embedding|ready|failed, queue_position?, progress (0-1)?, chunk_count?, error?}`
   - `DELETE /sessions/{id}` -> frees the session.
5. Ingest pipeline: parse PDF -> chunk (reusing v1 chunking, including the Miss 3 fix) -> embed one chunk at a time, updating `progress` -> store matrix + metadata on the session -> `ready`.
   Any exception -> `failed` with a readable error.
   The worker keeps running after a failed job.
6. A `search(session, query, k)` function with a unit test, not exposed as an endpoint yet.
7. TTL eviction: a periodic sweep or lazy eviction, with the choice explained.
8. Memory instrumentation: log peak RSS (psutil) at startup, after model load, and at the end of each ingest job, with page and chunk counts.
   `scripts/measure_ingest.py` uploads a given PDF to a given base URL, polls until ready or failed, and prints timing.
9. Render deploy config for the backend only.
   Single worker, binds to `$PORT`.
10. `docs/v2.0-m1-memory-results.md` template with blanks for me to fill after running on Render.

Not in M1: answer/turn endpoints, wiring the engine's question/scoring loop, Gemini calls, Neon/Postgres or the daily quota guard, per-IP limits, CORS, the React frontend, streaming, or report generation.

## Acceptance criteria

- `pytest` passes.
  Tests cover: upload validation (too big, too many pages, not a PDF), the queue cap returning `503` on the 4th waiting job, correct queue positions, the live-session cap, `404` for unknown ids, TTL eviction, the worker surviving a failed job, top-k search correctness, and ONNX/sentence-transformers parity (when available).
- Production requirements contain no torch, sentence-transformers or chromadb.
- `uvicorn` starts locally with one worker, `/health` responds, and a real PDF goes queued -> embedding -> ready, with progress increasing.
- Startup, after-model-load and per-ingest peak RSS appear in the logs.
- The v1 Streamlit app still runs unchanged.

## Approved plan adjustments (2026-10-19)

1. Page ranges: `chunk_pdf_with_pages()` in `rag/chunking.py` returns text plus `page_start`/`page_end`, and `chunk_pdf()` becomes a wrapper returning the texts.
   Page indices come from PyMuPDF page indices, never parsed from text, stored 0-based; display decisions come later.
2. Uploads are spooled to temp files on disk, not held in memory while queued.
   Temp files are deleted in a `finally` block (covers failed and cancelled jobs), and the temp dir is cleared at startup.
3. The measurement runs with limits raised through env vars; the final limits come from the results.
4. The `render.yaml` build filter must still trigger on changes to any v1 module the backend imports (`rag/`, engine, panel) and ignore v1 UI files only.
5. ROADMAP gets a pointer to M1 and a line recording the known failing v1 test (missing session file) so it isn't mistaken for a regression.
6. The results template also closes out the spike's pending items: peak RSS/VmHWM across 3 fresh restarts, and cold-start time (first request after spin-down -> `/health` 200).
7. google-genai is in prod requirements and imported at startup like spike 2, with a comment that it is there for a realistic memory baseline and is used from M2.
8. Status codes: over-size -> 413, not a PDF -> 422, too many pages -> 413, capacity -> 503, invalid panel -> 422.
   A cheap capacity pre-check runs before reading the body; the authoritative check stays in the no-await section.
9. Zero extractable text (scanned PDF) -> status `failed` with a clear "looks scanned" error, not `ready` with 0 chunks, with a test.
   The scanned-PDF Parking Lot entry comes over from the spike branch.
10. Failed sessions are subject to TTL eviction.
    Queued and embedding sessions never expire; failed sessions do not count toward the live-session cap.
