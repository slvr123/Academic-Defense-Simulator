## Headline

A defense that never gets its first question no longer costs a slot.
The slot comes back when the session is ended or expires, or at once if setup fails.

## 1. What changed, per item

### P1 - refunds

**The double-charge finding: confirmed.**
Before any fix, a test patched `setup_defense` to raise once and then retried `/start` on the same session:

```
PROBE after the failed start: used=1; retry status=200; after the retry: used=2
```

The failed setup left its slot taken, and the retry took a second one: two slots for one defense.
Persona generation and domain extraction both fall back instead of raising, so this needed an unexpected error inside setup; but any such error charged twice.

**The rule as built.**
`/start` now records its reservation on the session as a charge (`backend/refund.py`).
A charge is settled exactly once, under its own lock: either released, or final.

- **Released:** setup failed (released at once, and the error returns as before), or the session is deleted or expires before a first question is delivered. The session store calls the refund on every drop.
- **Final:** the first question is delivered. After that nothing is refunded.

A busy first question keeps the charge while the session lives, so the retry stays free, as before.
A release gives back both counters: the daily store (`release(day)`, which never goes below 0, on the day the reservation was made) and the per-IP limiter.
If the Pacific day has changed, the daily release is skipped and logged.
Every release logs one line with its reason.

**An additive error code.**
A 503 from Gemini's overload now carries `code: "panel_busy"`.
Without it, the start screen couldn't tell Gemini's 503 from the quota store's own 503, and would have blamed Gemini for both.
The busy classification, the message and `Retry-After` are unchanged.

**The CORS fix.**
`allow_methods` was `["GET", "POST"]`, so a browser's `DELETE` from End session (M10 N2) failed its preflight, and production sessions were never deleted.
It's now `["GET", "POST", "DELETE"]`, and the CORS test checks DELETE is allowed and PUT still isn't.

## 3. Concepts map

**Reserve-then-release vs charge-on-success.**
Charging only after success would let a slow first question run while other people take the last slots, overshooting the day's cap.
Reserving first holds the slot while Gemini works, and a release gives it back if nothing was delivered (`backend/defense_routes.py:159`, `backend/refund.py:67`).

**Making a release happen at most once.**
A charge has one state, held, released or final, and moving out of held happens under a lock, so only the first caller wins.
A second DELETE, an expiry racing a DELETE, or a delivered question racing a DELETE all find the charge already settled and do nothing (`backend/refund.py:48`).

**An atomic decrement in Postgres.**
`UPDATE ... SET sessions = sessions - 1 WHERE day = %s AND sessions > 0` reads and writes in one statement under a row lock, so two releases can't both read the same number.
The `sessions > 0` condition is what stops it going negative; a release on an empty row just changes nothing (`backend/quota.py:231`).

**Why the per-IP limiter is in memory, and what a restart does.**
The per-IP count only has to last one Pacific day and is cheap to lose, so it lives in the process instead of costing a database write per start.
A restart (a Render deploy or spin-down) forgets it, which gives every IP a fresh allowance, while the daily cap stays safe in Postgres (`backend/client_ip.py:59`).

**Fault injection with monkeypatch.**
`monkeypatch.setattr(module, "name", replacement)` swaps a function for the length of one test and puts it back afterwards.
The refund test swaps `setup_defense` for one that raises once, which is how the double charge was shown without a broken Gemini (`backend/tests/test_refund.py:59`).
