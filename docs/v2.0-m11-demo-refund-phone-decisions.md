## Part 1 — Locked decisions

Claude proposed these after the M10 reveal merge (main at 622abeb), and I confirm them by sending this brief. The current behaviour described below was read from `main` at 622abeb.

### P1. Refund a slot when a defense never got its first question

**Today:**
- `/start` reserves the per-IP slot and the daily slot before any Gemini call.
- If the first question comes back busy, retrying `/start` on the same session is already free: the "resumes here, without a new reservation" path.
- The leak is a defense that **never delivers a first question** and is then abandoned (the user leaves, reloads, or ends the session). Its slot is gone, and the M10 recording lost two slots this way.
- Code to verify from the code, not assume: `setup_defense` (persona generation) runs before the `try`. If it raises, `session.defense` stays `None`, so a retry looks like it reserves a **second** slot. If confirmed, that's a double charge, and this item fixes it too.

**Rule:**
- A session holds at most one charge. The charge is **released**, at most once, when:
  - (a) `setup_defense` raises, released immediately and the error returned as today; or
  - (b) the session is deleted (End session or `DELETE /sessions/{id}`) or expires **before any first question was delivered**.
- Once a first question has been delivered, the charge is final: no refund for failures mid-defense, and none for a finished defense.
- A busy first question with the session kept alive keeps its charge (the retry is free, as today). It's released only through (b).

**Release mechanics:**
- Release both counters: the daily store (`release(day)`, an atomic decrement that never goes below 0, on the day the reservation was made) and the in-memory per-IP `StartLimiter` (`give_back`).
- If the Pacific day has changed since the reservation, skip the daily release and log it.
- Every release is logged on one line, with the reason.

**Out of scope, accepted:**
- A process restart (a Render deploy or spin-down) loses in-memory sessions without a refund.
- The memory store and Postgres store must both implement `release`.

**Frontend:**
- When `/start` comes back busy, the screen keeps the session.
- It shows "Gemini, the AI behind the panel, is overloaded right now. This hasn't used one of today's defenses yet. Try again in a moment.", plus a "Try again" button that resends `/start` on the same session, with the `Retry-After` countdown already supported in `client.ts`.
- "Start over" ends the session (`DELETE`), which triggers refund (b).
- The wording must be true under P1. If Code finds a path where it isn't, the wording changes, not the rule.

**Unchanged:** the busy classification (`is_panel_busy`), the 503 body and `Retry-After`, idempotent answers, the `/start` replay, and the error codes. Only additive fields or codes, if any are needed.
