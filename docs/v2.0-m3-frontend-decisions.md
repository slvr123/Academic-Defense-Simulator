## Part 1 — Locked decisions

These resolve the ten open items in `v2.0-m3-kickstart-handoff.md`, plus gaps found when Claude cross-checked that handoff against its first draft of this doc on 2026-10-21. Unless noted, Claude proposed each and I confirmed it. M2's decisions all still stand.

### D1. Repo layout and build tool (handoff item 1)
`frontend/` in this repo, scaffolded with Vite's `react-ts` template. No Next.js/Remix: the target is a Render static site with no server rendering. The backend service in `render.yaml` gets a build filter that ignores `frontend/**`; the static site is added to `render.yaml` as its own service with a filter on `frontend/**` only, so neither redeploys the other.
*Downside I accept:* the static site lives in the Blueprint, so merging the `render.yaml` change is what creates it on Render — that merge is a stop point.

### D2. CORS (handoff item 2)
There is no `CORSMiddleware` in `backend/app.py`. Add it with an explicit allowlist read from `ADS_CORS_ORIGINS` (comma-separated: the static site URL and `http://localhost:5173`). Never `*`. Only the methods and headers the frontend uses.
*Downside I accept:* a backend change inside a frontend milestone, and an env var to update if the static site URL changes.

### D3. TypeScript strict, no `any`
`"strict": true`. No `any`, no `@ts-ignore`. Genuinely unknown data (error bodies) is typed `unknown` and narrowed.

### D4. Generated API types (handoff item 3)
`openapi-typescript` (dev dependency) generates `frontend/src/api/schema.gen.ts` from the backend's `/openapi.json`, committed, with `npm run gen:api`. Short aliases for the types the UI uses live in `src/api/types.ts`, so components never import from the generated file directly.
*Downside I accept:* the generated file is hard to read while I'm learning TypeScript, and I must re-run `gen:api` after any `schemas.py` change.

### D5. One typed API client; upload uses XHR (handoff item 4)
`src/api/client.ts` is the only module that talks to the network. Every call returns either the typed success body or a typed `ApiError` discriminated union. Components never see status codes. No React Query, SWR, or axios.
**Exception, Claude proposed and I confirmed:** `POST /sessions` uses `XMLHttpRequest` instead of `fetch`, because `fetch` can't report upload progress and a 26 MB PDF on a Philippine mobile connection needs a real progress bar. It stays inside `client.ts` behind the same return type.
*Downside I accept:* I write polling and retry by hand, and the client has two request mechanisms.

### D6. Flow is a `useReducer` state machine (handoff item 4)
One `phase` discriminated union drives which screen shows: `waking → configuring → uploading → queued → embedding → ready → preparing → question → submitting → question … → finishing → report`, plus error variants carrying what recovery needs. The reducer is a pure function in `src/state/` with no React imports. No router, no Redux/Zustand.
*Downside I accept:* browser Back leaves the app; reload loses the session.

### D7. Styling: Tailwind; Framer Motion deferred (handoff item 5)
Tailwind. Provenance: Claude bundled Tailwind into the stack-swap proposal on 2026-07-07 without arguing for it separately, and Claude's first draft of this doc proposed CSS Modules instead. On 2026-10-21 I asked for a fresh comparison and Claude recommended Tailwind on its own merits; I confirmed it. Reasons: Code writes most of the UI and I review it, and Tailwind keeps a component's styling in the same file as its markup; its classes map almost one-to-one onto CSS properties, so I still learn flexbox and grid through it; its spacing and colour scale keeps the UI consistent without design training; and it's common in React job posts. Install it the way Tailwind's current docs say for Vite (verify, don't assume a version). Design tokens (archetype accent colours, type scale) live in Tailwind's theme config, not scattered as arbitrary values. Motion in M3 is CSS transitions only.
*Downside I accept:* I learn a class vocabulary on top of CSS, and the first deploy looks plainer than the vision.

### D8. Phone width
Every screen works at 375 px with no horizontal scroll.

### D9. No streaming; client-side typewriter reveal (handoff item 6)
Questions arrive whole. The question text reveals with a client-side typewriter effect. A click or keypress skips to full text. Under `prefers-reduced-motion`, text appears instantly. The README and case study must never call this streaming.

### D10. Keep-alive during a defense (handoff item 7)
Render free spins down after 15 idle minutes and sessions live in memory, so a user thinking for 15 minutes can lose the whole defense. While `phase` is `question` or `submitting`, the client calls `GET /health` every 10 minutes. No pings in any other phase. The interval lives in a `useEffect` with cleanup.
*Downside I accept:* uses free-tier instance hours while defense tabs are open, and it hides the problem rather than fixing it — persistence is the real fix, later.

### D11. Avatars from the static site (handoff item 8)
Copy `academic_defense_simulator/assets/icons/*.png` into `frontend/public/icons/`. A test asserts that every `icon` value the backend can send (read from the backend's source of truth for icon names) has a file. Panelists display as "Dr. " + `PanelistOut.name`.
*Downside I accept:* two copies of the icons to keep in sync — the test catches drift.

### D12. Voice is M3b, not M3 (handoff item 9)
M3 ships with no voice. M3b (its own decisions doc and run) adds `POST /tts`, the `speechSynthesis` fallback, the disclosure gate, the empty-audio fix, and the by-ear pass. **This supersedes my earlier handoff note that voice would be built in M3.** Claude recommended the split because the dead-player bug needs one live MiMo call to confirm its cause before any TTS code is designed around it. Claude's `/tts` design (takes `session_id` + turn, never text, so my key can't be used as a free TTS service; at most 2 synth calls per turn) is recorded here as a proposal for M3b to lock, not built now.
*Downside I accept:* M3's first deploy has no voice, and voice is what makes the app feel real.

### D13. M3 scope (handoff item 10)
Panel config + upload, quota display, every wait and error state, the full answer loop with source reveal after each answer, and a basic report with the transcript. Not in M3: debrief-style report rebuild, Framer Motion, voice.
*Downside I accept:* the first M3 deploy is functional, not impressive. Not the one I post about.

### D14. Panel config screen
The upload screen includes the `PanelConfig` form, with fields, enums and limits taken from the generated types for `backend/schemas.py` (not re-invented). Defense type choices and their labels match v1's.

### D15. Quota display
On page load (after `/health`), call `GET /quota` and show "N of 11 defenses left today". When `remaining` is 0, disable Start and show "More at <time>, Manila time" from `resets_at`. If `/quota` returns 503 (Neon unreachable), hide the quota line and let the user proceed; the server still enforces.

### D16. Wait and error states — exact behaviour

| Trigger | UI behaviour |
|---|---|
| Page load | `GET /health` at once. If the user submits before it returns, show "Waking the server — up to a minute on first visit" (measured: up to 42.7 s). |
| Upload in progress | Progress bar from XHR upload events (D5). |
| 202 → `queued` | "In line — position N" from `queue_position`, polling `GET /sessions/{id}` at the interval M2's doc specifies. If none is specified, 2 s; record that. |
| `embedding` | Progress bar from `progress`. Copy says large documents take about a minute (measured 63.6 s for 224 pages). |
| `failed` | Show the failure reason the API returns. If it identifies a scanned / no-text PDF, show "This PDF needs selectable text — scanned pages can't be read." |
| `/start` in flight | "The panel is preparing" — seated panelists shown as soon as known, staged copy changing every ~8 s (measured 30.6 s). Never a bare spinner. |
| 404 | "This session expired — upload your document again." One button back to `configuring`, file cleared. |
| 409 | Submit disabled from click until the response arrives. A 409 that still arrives is swallowed; the in-flight state continues. |
| 502 (turn failed, nothing recorded) | Keep the answer text in the box: "That turn didn't go through — nothing was recorded. Send it again." Resend sends the same text. |
| 413 / >30 MB | Blocked client-side by `file.size` before upload. Server 413 maps to the same message as a backstop. |
| 422 | Show the server's specific message verbatim (e.g. "document too short for this panel"). |
| 429 | Never auto-retry. Time = now + `Retry-After`, formatted with `Intl.DateTimeFormat`, `timeZone: "Asia/Manila"`. If the body distinguishes the per-IP limit (3 starts/day) from the daily cap (11), show "You've used your 3 defenses for today" vs "Today's defenses are all used" — each followed by "More at <time>, Manila time." If it doesn't distinguish, one neutral message. |
| 503 | "The panel is busy — retrying in N s" countdown, one automatic retry after `Retry-After`, then a "Try again" button. |
| Network failure | "Can't reach the server" + "Try again". |

### D17. Scores
Raw 1–5 from the API, rescaled to 100 for display with **v1.2.1's exact formula**, ported as a pure function `src/lib/scoreDisplay.ts` with a test using v1.2.1's own example values. No new scale. `AnswerScore` and the rubric are untouched.

### D18. Source reveal
Every question already carries `sources[]`. The client holds them hidden while the question is open and reveals them (pages `page_start`–`page_end` as given, `origin`, `score`, chunk text) only after that answer is evaluated. Never alongside the open question — that would hand over the answer.

### D19. Configuration
Backend URL from `VITE_API_BASE_URL`. `VITE_*` values are baked into the public JavaScript at build time: no secrets in `frontend/`, ever.

### D20. Testing
Vitest + React Testing Library + jsdom (dev dependencies). Unit tests: reducer (every transition and error variant), `client.ts` status → `ApiError` mapping, Manila-time formatter, `scoreDisplay`, the 30 MB pre-check, keep-alive only running in the right phases. Component tests render every D16 row with a mocked network and assert the visible text. Backend: pytest for the CORS allowlist (allowed origin gets the header, unlisted origin doesn't). No Playwright/Cypress — the visual pass is mine.
