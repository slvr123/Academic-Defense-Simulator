## Decision 1 — Mobile: scope the sidebar offset to wide screens, and measure the defense screen (LOCKED)

**Evidence.** At a 390px viewport the main container renders at
`left = 300px, width = 390px`, so most of the page is off-screen (measured in
headless Chromium against `0ea14bc`; also seen on the deployed app at 375px).
The cause is one rule in `_inject_theme_css`:

```css
.stMainBlockContainer { margin-left: max(300px, calc(50vw - 450px)) !important; }
```

That clamp fixed a real desktop bug (content under the open sidebar). It was
never scoped, so it also applies on phones.

**Fix (locked shape).** Wrap the `margin-left` clamp in
`@media (min-width: 1024px)`. Below 1024px the container uses Streamlit's normal
centred layout with its default gutters. `max-width: 900px` stays unconditional.

**Second issue: the sidebar on the defense screen.** `initial_sidebar_state`
expands the sidebar at `running`/`aborted`/`done`, and the overlay CSS gives it
`min-width: 330px`. On a 390px phone that probably covers the whole defense.
The sidebar holds captions only (case file, roster, progress). The main column
already shows the roster and turn progress (v1.0.1 Decision 8), so nothing is
lost if the sidebar is narrowed or hidden on small screens. Pre-committed
branches, decided by measurement at 390px and 768px on the `running` stage:

- **A — not covering** (Streamlit collapses it itself): no change.
- **B — covers, and a visible close control closes it in one tap**: under
  `@media (max-width: 1023px)`, cap the sidebar at `min(330px, 85vw)`.
- **C — covers, and no visible or reachable close control**: under
  `@media (max-width: 1023px)`, hide the sidebar with `display: none`. This is
  justified only because the main column duplicates its content.
- **D — none of the above** (some other breakage): halt. Record screenshots
  and measurements; no fix in this session.

This is CSS media queries, not the server-side viewport detection that
v1.0.1 Decision 8 rejected. That rejection stands.

**Standing check (Claude proposed, I confirmed).** Add
`scripts/screenshot_sweep.py`. It uses Playwright as a dev-only tool, not added
to `requirements.txt`, so deploy is unaffected. It screenshots intake,
panel-selection and the recorded example at 390, 768, 1024 and 1440 widths.
For each, it records `document.documentElement.scrollWidth` vs `innerWidth`
and the main container's left/width. Any future UI slice runs it as DoD
evidence. Downside: a dev dependency outside requirements, documented in the
script's docstring.

## Decision 3 — The duplicate-turn bug is fixed before anything is re-recorded (LOCKED)

**Evidence (from the committed fixture).** `turns[0]` and `turns[1]` in
`sample/example_session.json` have identical `question`, `answer` and `score`.
A genuinely generated second question with an identical score is not credible;
this is one turn recorded twice. It produced Dr. Nguyen's repeated gap bullet,
the identical Turn 1/2 suggestions, a phantom `1 → 1` step in the trajectory,
and an extra turn counted toward retention and session length. It happened in a
live session, so it is a production bug.

**Leading hypothesis (H1).** Inside `_render_answer_fragment`, the lock's
re-check reads `st.session_state.pending_turn`. The v0.3 hang investigation
found that overlapping reruns of one session can run concurrently, and that a
session-state flag was *not* a reliable guard between them. A second rerun can
therefore still see the old `pending_turn`. It then re-scores and appends the
**same `turn` object** again, which is why every field matches.

**Fix (locked shape).**
- Add a pure function in `engine.py` (no Streamlit import):
  `record_scored_turn(session, turn) -> bool`. It appends only if this exact
  object is not already in `session.turns` (identity check: `any(t is turn ...)`)
  and returns whether it appended.
- In the submit path, inside the lock and **before** the scoring call, skip
  everything if the turn is already recorded. A duplicate rerun then spends no
  scoring call either.
- The guard reads the `session` object, a plain Python list shared by
  reference, not `st.session_state`.

**Pre-committed branches:**
- **R1 — reproduced** (e.g. a rapid double-submit or two overlapping submits in
  a headless browser, at most 5 attempts): fix, then show the same repro no
  longer duplicates.
- **R2 — not reproduced in 5 attempts:** ship the guard anyway (the fixture
  proves a duplicate happened, and the guard is correct defensively), with unit
  tests, and record "root cause unconfirmed" in the verification notes.
- **R3 — reproduction shows a different mechanism** (resume, persistence reload,
  anything not H1): halt and report the evidence. No fix until it's reviewed in
  chat.

**Tests:** guard appends once; second call with the same object returns
`False` and leaves the length unchanged; a different turn object still appends.
After Decision 4, add a fixture tripwire: no two turns in the committed example
share an identical `(question, answer)`.

## Verification notes

### Phase A — Decision 3 (2026-10-18)

**Branch taken: R1, reproduced on attempt 3 of 5.**
The mechanism is the H1 family (overlapping reruns), not resume or persistence, so R3 did not apply.

Repro setup: a scratchpad wrapper replaced every LLM call with a stub that sleeps for realistic latency (question 3s, scoring 2s, report 4s) and logs each call and the object ids in `session.turns`, then ran the real `streamlit_app.py`.
Headless Chrome drove it through Playwright.
No Gemini calls were made.

| Attempt | What the driver did | Result |
|---|---|---|
| 1 | Second Submit click at +2.8s | One scoring call, no duplicate. The click landed in the post-score `MODEL_CALL_DELAY` sleep and was queued behind the running fragment. |
| 2 | Second click at +8.5s, during the next question's generation | Click timed out: the stale Submit button is gone from the DOM during generation. No duplicate. |
| 3 | Full rerun at +0.33s (sidebar "Developer view" toggle), then Submit again at +1.02s | **Duplicated.** Two overlapping scoring calls on one object (starts logged at `…097.638` and `…098.627`, each running 2s), then `generate_start turn_ids: [(6, [3220277405776, 3220277405776])]` and a "Turn 3" heading after one answer. |

**Fixture fingerprint.**
`difficulty_start` is 1 and the recorded deltas sum to +2, so the recorded turns account for a final difficulty of 3.
The committed `difficulty_current` is 4.
That missing +1 is the first scoring's delta: it was applied, and then the same turn object was re-scored and its `score` overwritten, which is why both list entries show the second score.

**Mechanism, as found in Streamlit 1.58's source.**
1. With `runner.fastReruns` on (the default), a full-rerun request while a run is blocked starts a second ScriptRunner thread at once (`app_session.py`), and the blocked run carries on.
2. The module-level `_turn_lock` never serialized anything: Streamlit execs the script into a fresh module on every rerun (`script_runner.py`: `self._new_module("__main__")`), so the `not in globals()` guard created a new Lock each time.
3. A superseded run raises `StopException` at its next `st.session_state` access (`SafeSessionState` calls `_maybe_handle_execution_control_request` on every access).
   So the stopped run's plain-object changes (append, difficulty) landed, and its `pending_turn = None` write never did.
   The live run then saw `pending_turn` still set, scored again, and appended again.

**Deviation 1 — per-session lock.**
Code proposed this after the attempt-3 repro; I approved it on 2026-10-18.
The lock lives in `st.session_state.turn_lock`, is created once before any stage renders, and is kept across `_reset()`.
The module-level `_turn_lock` and its `globals()` guard are deleted.
The question-generation block, the submit path and the reconcile step all use it.
A Lock in session state is incompatible with `runner.enforceSerializableSessionState`; that is noted at the definition.

**Deviation 2 — reconcile step.**
I proposed this in chat after Code found the stop-on-access behaviour; I approved it on 2026-10-18.
Code's first implementation of the locked shape ("skip everything if the turn is already recorded") turned the duplicate into a stuck session: the re-run of attempt 3 left `pending_turn` on the recorded turn, the next "Turn 2" showed turn 1's question again, and a normal submit made zero scoring calls.
The design I approved instead:
- `record_scored_turn` appends and applies the clamped delta, both plain mutations with no session-state access.
- The submit path only scores (unless already recorded), records, and clears `pending_turn`.
- `engine.reconcile_actions(session, pending_turn, saved_turn_count)` is pure and returns (a) clear pending, (b) persist IN_PROGRESS, (c) finish the session; `_reconcile_running_session` executes them at the top of every `running` pass, under the lock, before question generation.
- The `MODEL_CALL_DELAY` pacing moved to just before question generation, whenever the session already has a turn.

Small implementation choices inside that design:
- The submit path clears `pending_turn` only if it is still the turn it just handled, so a stale fragment for an older turn cannot drop a newer pending question.
- *(Superseded by the rule split below.)* In `finish_session` the stage is set to `done` before the report is stored. If the run is stopped at that write, the report stays unset and the next pass rebuilds it. Storing the report first would strand a reported session in `running`, because (c) requires `report is None`.
- After a resume, the first question now waits one pacing interval, because the resumed session already has turns.

**Post-fix verification** (same stubs, `ADS_TTS_PROVIDER=browser`):
- Attempt 3 plus a normal follow-up submit: `score calls: [(2589918147072, 'Stub question #1'), (2591230102976, 'Stub question #2')]`, `DUPLICATE TURN OBJECT IN session.turns: False`, and the heading advanced to "Turn 3" with a new question (`Stub question #3`).
- Final-turn variant (completion forced after one turn, full rerun at +4.0s during the report build): `session complete banner: Session complete · 1 turns.`, `answer boxes still on screen: 0`, one scoring call, no duplicate.
  As first committed, the report was built **twice** (`report builds: 2`): the stopped run's report was discarded at the stage write and the next pass rebuilt it.
  In production that costs one extra narrative call and one extra `gemini-2.5-flash` suggestions call, and only when a full rerun lands during the report build.

**Known residual.**
If a run is stopped at the `COMPLETED` save itself, the stage is already `done` and reconcile no longer runs, so the file on disk stays at the IN_PROGRESS save from step (b), with every turn present but no report.
Resuming it runs reconcile, which builds the report and finishes the session.

**Refinement to deviation 2 — rule (c) split.**
Code proposed fixing the double report build; I specified the rule split in chat and approved it on 2026-10-18.
Rule (c) is now two independent, idempotent rules:
- (c1) `session_is_complete` and `report is None` -> build the report and store it on the session object as the call returns, before any session-state access;
- (c2) `session_is_complete` and stage is not `done` -> set stage `done` and persist COMPLETED.

`reconcile_actions` gains a `stage` argument, and `ReconcileActions` has `build_report` and `finish_session` in place of the single flag.
A run stopped between the two rules leaves only (c2) for the next pass, so a stored report is never rebuilt.
New tests: a complete session with a stored report but stage still `running` fires only (c2); a complete session with no report fires (c1) and (c2), and the executor runs them in that order.
