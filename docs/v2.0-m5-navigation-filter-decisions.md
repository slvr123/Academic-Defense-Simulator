## Part 1 — Locked decisions

Unless noted, Claude proposed each of these in our design conversation on 2026-10-27, and I confirm them by sending this brief.

### G1. The defect
M4 Check C found that on `sample3.pdf`, the table of contents is the best match for 4 of 8 archetypes, and every recommended panel on that document asks at least one question sourced from the contents or the abstract. On DAZSMA, the List of Tables showed up in 2 of 18 session turns. A contents page lists every topic in the paper, so it looks like a good match for any panelist's focus. To a visitor, a panelist asking about the table of contents looks broken.

### G2. Filter pages, not chunks
M4 measured two chunk-level variants, and both have a flaw. Dropping chunks that lie *entirely* on navigation pages leaves the abstract-plus-contents chunk in (3 of 8 front-matter picks remain). Dropping chunks that *touch* a navigation page also throws away real content: the chunk running from the end of the contents into Chapter 1, and the chunk that starts on the abstract.

So M5 removes navigation **pages** before chunking. Chunks are then packed from the remaining pages only: no chunk contains contents text, and the abstract and Chapter 1 stay whole.
*Downside I accept:* on a document that has navigation pages, every later chunk boundary shifts, so all of its rankings change, not just front matter's. M4's harness re-measures all of them, so this is checked rather than assumed.

### G3. Which pages are removed: front matter only
A page is removed only if **both** of these are true:
- M4's detector flags it (`is_navigation_page`: at least 5 lines, and most lines end in a page number or carry dotted leaders), **and**
- it sits before the front-matter boundary (`front_matter_boundary`: the first page matching a Chapter 1 / Introduction heading).

The detector's thresholds are used exactly as M4 measured them; tuning them is out of scope.
- **No boundary found → nothing is removed** (fail-open). Retrieval behaves exactly as today on that document.
- **The abstract stays.** It's front matter, but it's real content.
- **No page at or after the boundary is ever removed**, so results tables in Chapter 4 are safe whatever they look like.

*Downside I accept:* a contents page on a document without a recognisable Chapter 1 heading isn't filtered.

### G4. Where the code lives: v1 untouched
- The detector functions move from `evals/retrieval_checks.py` into a new production module, `backend/page_filter.py`, unchanged. The eval imports them from there, so there's one definition. M4's numbers must reproduce exactly after the move (a guard run, before any filtering).
- The filtered chunker lives in the v2 backend. It reuses v1's paragraph splitting (Miss 3 page-number stripping included) and packing by importing them. It does not copy them, and it does not modify `academic_defense_simulator/`. If that's impossible without changing v1, stop.
- **Scanned-PDF detection is unchanged:** the minimum-characters check still counts *all* pages, including removed ones, so a document's scanned/not-scanned verdict can't change.
- **Page numbers stay true to the PDF:** `page_start`/`page_end` refer to the original page numbers, so the source reveal still points at the right page.
- **Parity:** on a document with no removed pages, the new chunker's output must be identical to v1's `chunk_pdf_with_pages`, text and page ranges alike.
- `backend/pdf_ingest.py` switches to the new chunker. If the v2 backend uses the bundled v1 sample sidecar anywhere, leave the sidecar unchanged and record that.

### G5. Pre-committed success rule
Run M4's full eval twice on the production stack: **before** (today's chunker) and **after** (filtered). Report them side by side. M5 passes only if all of these hold on both documents:
1. Zero archetype top-1 picks and zero simulated-session turns on a navigation page.
2. Zero pages removed at or after the front-matter boundary. List every removed page per document.
3. Check A's verdict doesn't move to a worse branch on either document.
4. Check E's maximum displacement rank stays at 5 or below.
5. Check B's near-tie rate is reported. It's not a pass/fail condition.

**If any of 1–4 fails:** don't merge. Record which one failed and why, and stop. The fix goes back to design in chat.
**None of the above** (a check can't run, or a document's boundary isn't detected): report it, and treat that document as "filter not applied" rather than as a pass.

### G6. Backend redeploy filter
The M4 push showed that changes to `docs/` and `evals/` redeploy the backend, costing a cold start for nothing. Add `docs/**` and `evals/**` to the backend service's ignored paths in `render.yaml`, alongside `frontend/**`.
