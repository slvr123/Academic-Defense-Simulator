# v2.0 M2 pre-check - an upload while another document is embedding

Status: closed 2026-10-20. GO on two runs; run 3 was aborted on the client side and measured nothing.
Follows up the caveat in [`v2.0-m1-memory-results.md`](v2.0-m1-memory-results.md): every M1 run had one upload at a time.
The queue embeds one document at a time, but a second upload is received and spooled while the first is embedding, and I estimated that case at about 385 MB, untested and close to the gate.

## Gate

The same gate as M1: VmHWM <= 400 MB on every run, with no process restart, both uploads ready, and the two actually overlapping.
"Overlapping" means the first job was still embedding when the second upload had been received.
A run where the first job finished first measured nothing, so it makes the verdict INCONCLUSIVE, not GO.
Cold start is recorded but isn't the question here; it was closed in M1.

## Setup

- Service: the M1 backend on `main`, unchanged, with `ADS_DEBUG_MEMORY=1` set in the Render dashboard for this run only.
- PDFs: DAZSMA (26.43 MB, 224 pages) for both uploads, the worst case for receiving the second one.

## Protocol

```
python scripts/measure_ingest.py "<DAZSMA.pdf>" --base-url https://<svc>.onrender.com --concurrent
```

Three runs, 16 minutes apart, so runs 2 and 3 start on a fresh process after a spin-down.
Each run uploads the PDF, waits until it is embedding, uploads the second PDF, and reads `/debug/memory` right after the second upload is accepted.
It then waits for both to be ready and reads `/debug/memory` again; VmHWM from that last reading covers startup, model load, both uploads and both jobs, in one process.
A changed pid or start time, or either session going missing, marks the run "process restarted, likely OOM".

## Decision

GO on two runs.
Receiving a second upload while another document is embedding doesn't need any change to the queue or the limits before M2.

What the two runs show:
- The overlap added nothing measurable over the single-upload peak. VmHWM was 331.6 and 333.8 MB, inside the 328.3 to 346.6 MB spread of M1 round 2's single-upload runs.
- In both runs the peak was set while parsing the first document, before the second upload arrived. VmHWM read right after the second upload was accepted equals the final VmHWM, so receiving and spooling the second 26 MB upload during the first job's embedding never pushed RSS above that parse peak.
- The second job's phase table says "peak set in: spooled" only because VmHWM is process-wide: when the second job started, the process had already reached the first job's parse peak, and nothing in the second job went above it.
- The M1 caveat estimated this case at about 385 MB. The measurement replaces that estimate; the estimate assumed the spooled upload would stack on top of embedding's peak, and it didn't.
- Headroom from the worse run: 66.2 MB to the 400 MB gate, 178.2 MB to Render free's 512 MB limit.
- Run 2 followed a 16-minute gap on a fresh process, with a 62.4 s cold start (M1's gate is 90 s).

Run 3 was aborted by a client-side timeout, not by the service.
After the second 16-minute wait, `/health` didn't answer within the script's 600 s, most likely because my laptop slept or lost network overnight.
The next morning the service woke and answered `/health` in 52.9 s, which rules out a stuck deploy.
No reading exists for run 3, so it counts for nothing either way.
The script now records a run like that as errored and still writes the results for the others.

Not a memory finding, but worth knowing for M2: the second document took 117.7 to 126.9 s from upload to ready, because it waits in the queue behind the first.
Its own job took 58 to 62 s.
The M1 upload-to-ready gate (120 s) was for a single upload, so it doesn't apply here, but a user who uploads right after someone else will wait about twice as long.

Caveat: two runs, not three.
I accept that because both landed in the middle of M1's single-upload range, with the peak in the same phase, rather than near the gate.
