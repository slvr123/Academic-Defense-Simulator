## Decision 1 — Four views ship, all zero-cost pure aggregation (LOCKED)

New module `analytics.py` (business logic only, no Streamlit imports), reading every `sessions/*.json`, filtering to `stage == "completed"` and `report is not None`. Sessions with no report (killed/aborted runs) are excluded from every computation below — they carry no `DefenseReport` to aggregate.

Four views, ordered by session `created_at` ascending:

1. **Session list** — one row per completed session: date, `defense_type`, `topic`, `overall_avg_clarity/depth/grounding`, turn count. A practice log, nothing computed beyond reading existing fields.
2. **Quality trend** — `overall_avg_clarity/depth/grounding` plotted session-over-session. Three lines, one per metric, x-axis = session sequence order.
3. **Difficulty trajectory comparison** — each session's `difficulty_trajectory` list shown side by side (as sequences, not one merged chart — comparing shape, not overlaying incompatible x-axes across sessions of different lengths).
4. **Pushback outcome trend** — per session, the `recovered`/`held`/`deteriorated` counts from `pushback_events`, shown session-over-session as a ratio or stacked count.

**No filtering UI in v1.0b** (by document, by `defense_type`, by date range) — every completed session is included, unconditionally. Filtering is real, wanted functionality, but it's additive and not needed to prove the aggregation pipeline works at 3 sessions. Parking-lot item, not cut silently.

**Charting:** `st.line_chart` / `st.bar_chart` over a small pandas frame — already an implicit dependency via the Streamlit ecosystem, no new charting library. Same "six integers don't need a chart, but a session list eventually does" reasoning as v0.3d Decision 6 — at 3 sessions a plain table might read just as well as a chart; Code picks whichever renders more legibly at current scale and notes which was chosen.

**In plain terms:** everything here is just re-arranging numbers your sessions already computed — no new intelligence, no new API calls, just organizing what's already sitting in your `sessions/` files into something you can actually look at across runs instead of one file at a time.

## Decision 2 — Recurring `primary_gap` themes: one cached `gemini-2.5-flash` call (LOCKED)

The one place this feature needs judgment, not arithmetic: deciding whether "didn't defend the cutoff value" and "unclear justification for the threshold" are the same underlying weakness. That's clustering free text by meaning — Python string-matching can't do it honestly, per the discussion in chat.

**Model: `gemini-2.5-flash`, not flash-lite.** This is a judgment task; Day 4 already established flash-lite is unfit for judgment work, and this project doesn't re-litigate that finding per call site — it applies the existing rule, same as the relevance gate did.

**New schema, new template, isolated from every session-generation prompt:**

```python
class GapTheme(BaseModel):
    theme_label: str            # short human name, e.g. "Quantitative justification"
    supporting_gaps: list[str]  # the original primary_gap strings grouped here, verbatim
    occurrence_count: int

class GapThemeAnalysis(BaseModel):
    themes: list[GapTheme]
```

`GAP_CLUSTERING_SYSTEM_PROMPT` — its own template, its own version constant:

```python
ANALYTICS_PROMPT_VERSION = 1
```

Deliberately **separate from `PROMPT_VERSION`** — that constant tracks the live defense-generation prompts (panelist/follow-up/scoring); this call never touches a live session, so it doesn't belong under the same version and doesn't need to move it. This is a new, additive prompt with no retroactive re-verification obligation — it wasn't verifying anything before.

**Fail-open, same as the relevance gate:** on any API error, the theme view renders "Theme analysis unavailable this session" — never a crash, never blocking the four free views above it.

**Input:** every non-null `primary_gap` string across all completed sessions, one call, flat list — not per-session, not per-panelist. Recurrence is only meaningful across the whole practice history.

**Call this only through the existing `GeminiProvider` abstraction** — no new provider-calling code path, just a new caller of the one that exists.

## Decision 3 — Caching: `st.cache_data`, keyed to invalidate on both data and prompt changes (LOCKED)

Without caching, Streamlit's full-script-rerun-per-interaction model would silently re-fire the clustering call on every click on the analytics page — a real, easy-to-miss cost leak.

Cache key: a hash of `(sorted list of all primary_gap strings, ANALYTICS_PROMPT_VERSION)`. Two consequences, both deliberate:

- **New completed session → new gap strings → new hash → cache miss → one fresh call.** Correct: the whole point is the view updates as practice accumulates.
- **Editing `GAP_CLUSTERING_SYSTEM_PROMPT` later → `ANALYTICS_PROMPT_VERSION` bump → cache miss even with identical session data.** Without this, a template wording change would silently keep serving stale themes computed under the old prompt — the same "prompt changes invalidate old verification" discipline `PROMPT_VERSION` already enforces for session-generation, applied here too.

**In plain terms:** the app only actually asks the AI to find recurring-weakness themes when there's genuinely new data to reconsider — not every time you glance at the page — and if the clustering instructions themselves ever change, it knows to ask fresh instead of handing back an answer computed under the old instructions.

## Call budget (standing constraint 2)

- Four free views: **zero** LLM calls, pure Python over existing fields.
- Theme clustering: **one `gemini-2.5-flash` call**, only on cache miss (new completed session, or a prompt-version bump) — not per page-view, not per session-turn. At current volume (a handful of practice sessions), this call fires on the order of once per new completed session, nowhere close to the ~20 RPD ceiling that constrains `2.5-flash` elsewhere in this project.

## Explicitly out of scope

- Any filtering UI (by document, `defense_type`, date range) — parking lot, additive later
- The `sessions/` retention/auto-pruning policy — already logged separately (2026-07-22 entry); analytics reads whatever exists today, no expiry assumption
- Any change to `PROMPT_VERSION`, or any session-generation template (panelist/follow-up/scoring)
- SQLite or any database — file-count is nowhere near the "only if earned" bar
- Cross-user or shared analytics (this is local, single-user data, same threat model as v0.4b Decision 1)
- Any second clustering pass, drill-down, or theme-editing UI — one flat theme list is the v1.0b bar
