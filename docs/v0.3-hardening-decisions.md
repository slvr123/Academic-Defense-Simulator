## Decision 1 — Resolve the chunk-70 reading empirically, via the probe, not archived evidence

**No raw evidence of the original chunk-70 finding exists** — no probe JSONL
row, no saved question text. Rather than block this design day on evidence
that may not be recoverable, the working assumption stated below is treated
as **provisional**, and the extended probe (Decision 7) is the actual test
that confirms or falsifies it — before task block 2 is considered done, not
after.

**Working assumption:** `is_grounded()` already catches the fabrication —
it's the standing hallucination detector, it runs on every generated
question, and the finding most plausibly surfaced during exactly this kind
of probe work. Under this reading, "warn-and-pass-through is correct for
signal collection, wrong for deploy" means the *detector* works and the
*policy* of only logging is what's inadequate — an enforcement fix
(Decisions 2–4), not a new detector.

**Alternative reading (not ruled out):** the fabrication lives in the
question's own content while `grounding_reference` still cites something
real — a plausible invented number or claim with a legitimate quote
attached as cover. `is_grounded()` cannot catch this; it only checks
`grounding_reference` against `chunk_text`, never the question text.

**Resolution procedure (binds task block 2, see brief):**
1. Build the fix under the working assumption (Decisions 2–4).
2. Run the extended probe at forced difficulty 4 and 5.
3. Human-judged column `content_fabricated_despite_grounding` on every
   probe row — does the question assert a fact, number, or claim not
   present in the excerpt, independent of whether `grounding_reference`
   passes?
4. **Zero such cases** → working assumption confirmed. Task block 2 is done
   as designed.
5. **One or more such cases** → alternative reading evidenced. **STOP.** Do
   not mark task block 2 done. Report the specific example(s) back in chat
   — this reopens the flash-lite-unfit-for-judgment problem from Day 4 and
   needs its own design pivot (likely an LLM fact-check call), not a
   same-session improvisation.

**In plain terms:** we don't have the original bug report anymore, so
instead of guessing at what it said, we build the fix we think is right and
then deliberately go hunting for the failure mode it's supposed to catch. If
we can't find it after actually trying, that's real evidence the fix
worked. If we do find it, we've learned the fix was aimed at the wrong
layer — better to learn that from a probe than from a real user.

## Decision 2 — No new detector; escalate `is_grounded()` enforcement, gated to difficulty ≥ 4

At difficulty 1–3: **unchanged.** Warn-and-log only, exactly as v0.2.5 built
it. The 0.85 fuzzy-match threshold is **not retuned** — this is an
enforcement change, not a detector change, same discipline as Miss 3
(Decision 8).

At difficulty ≥ 4: a `is_grounded()` failure on the generated
`grounding_reference` triggers **one retry** — same chunk, same target
difficulty, a fresh generation call. Not a new retrieval; isolates exactly
one variable (the LLM's output) rather than also changing what it's grounded
against.

**In plain terms:** the detector has been correctly flagging this since
v0.2.5 — nothing was broken there. What's missing is that a flag never
changed what happened next; it just wrote a line to a log file nobody reads
mid-session. This makes a flag actually do something, but only where the
evidence says it's needed (high difficulty), not everywhere, which would
spend calls for no reason.

## Decision 3 — Prompt fix: sharpen the challenge, not the content

New template fragment, inserted into both `PANELIST_SYSTEM_PROMPT` and
`FOLLOWUP_SYSTEM_PROMPT` via a new optional slot, populated only when
`difficulty_level >= 4`:

```python
HIGH_DIFFICULTY_GROUNDING_GUARD = """
At high difficulty, sharpen the CHALLENGE, not the CONTENT. Do not introduce
facts, numbers, claims, or specifics that are not present in the excerpt —
adversarial difficulty means harder scrutiny of what IS there, never
inventing what isn't.
"""
```

Rendered into a new `{high_difficulty_guard}` slot in both templates; empty
string below difficulty 4.

**`PROMPT_VERSION` bumps `"0.3c"` → `"0.3c-hardening"`.** Not `"0.3d"` —
that string is reserved for the actual roadmap UI version and would
misrepresent which session produced this prompt set. Wording diff outside
the new conditional line is zero; state this in verification notes, same
pattern as every prior prompt-touching session.

**In plain terms:** the theory behind the fabrication is that at high
difficulty the model reaches for something *sharper* to say and, lacking a
real fact to escalate with, invents one. This line tells it explicitly what
"harder" is allowed to mean — more scrutiny of what's actually there, never
new material.

## Decision 4 — Retry-once, then serve-and-flag

Matches the retry-cap-of-1 pattern used everywhere else in this project
(API timeout, malformed JSON, narrative fallback). On a second consecutive
`is_grounded()` failure: **serve the second attempt anyway**, flagged.

This is **not** a 5a fail-session case — 0.3a and 0.3c already established
that content-quality issues (as opposed to transcript corruption) don't
earn that treatment. It is also **not** silent pass-through — that's
exactly the "wrong for deploy" problem being fixed.

**Schema addition, `ConversationTurn`:**

```python
grounding_retry_used: bool = False   # first attempt failed is_grounded(); retry issued
grounding_flagged: bool = False      # both attempts failed; served anyway
```

Both stay `False` unconditionally outside difficulty ≥ 4 — zero behavior
change below the gate. No session-level rollup field; an eval reading the
session scans `turns` directly, consistent with this project's minimalism
on schema additions.

**Accepted edge case, not engineered around:** the `is_grounded()` retry
(this decision) is independent of and does not stack with 5a's API-failure
retry. Pathological worst case for one question is bounded at 2 full
generation attempts × their own internal 5a retry each — up to 4 raw API
calls. Rare, bounded, not worth additional machinery.

**Explicitly out of scope:** feeding `grounding_flagged` into the
`DefenseReport` (0.3c). That's report scope, already shipped; a future
enhancement, not this session's job.

**In plain terms:** killing the whole session over one bad question throws
away five good turns to protect against one flagged one — wrong trade.
Silently serving it, like today, is the exact problem we're fixing. So:
serve it, but make it visible everywhere that matters — the logs and the
exported transcript — rather than choosing between "stop everything" and
"hide it." If the probe shows double-failures are common, that means the
prompt fix isn't pulling its weight, and needs another pass — not a bigger
fallback.

## Decision 5 — Call budget: gated to difficulty ≥ 4 only

Per standing constraint 2. Worst-case pathological ceiling (every turn at
difficulty ≥ 4, every one fails its first attempt): `2T+1` → `3T+1` — for a
6-turn session, 13 → 19 calls. Realistic expectation is far lower —
difficulty trajectories don't sit at 4–5 for a whole session, and
`is_grounded()` is reliable outside this range per Day 2's baseline. The
probe (Decision 7) produces the real number.

## Decision 6 — DA's second grounding surface: digest-claim fidelity, human-judged, no new detector

DA has a fabrication risk `is_grounded()` cannot see. Per 0.3b Decision 2,
DA selects "the strongest / highest-scored prior claim" from the digest and
contests it. `is_grounded()` checks the question against the *document*
(same as every panelist, no exemption — unchanged). Nothing checks whether
DA's stated target claim actually matches what's in the digest — a forced
difficulty-5 DA question could fabricate on that axis instead, attacking a
claim the candidate never made.

**Decision: stays human-judged in the probe, not automated.** Consistent
with how `in_lane`/`difficulty_ok` have always been human-judged; building
a second auto-detector before knowing whether this is even a real failure
mode is the premature abstraction this project avoids.

**Test method: synthetic digest fixture, not a live multi-panelist session.**
A small hand-built set of prior turns representing one clear, strong claim,
rendered directly into DA's prompt at forced difficulty 5. Isolates exactly
the variable under test (DA behavior at high difficulty against a known
claim) without spending calls driving three other panelists through a full
session first — same fixture-over-live-session preference 0.3b already used
for schema/digest testing.

**In plain terms:** DA can lie in two different ways — about the document
(covered, no exemption) and about what the candidate actually said
(uncovered, untested). We're not building a detector for the second one yet
because we don't know if it's a real problem. We're just going to look,
cheaply, with a fake-but-controlled example instead of a whole expensive
session.

## Decision 7 — Probe: extend `probe_question_gen.py`, don't build new

**New capability required:** a `forced_difficulty: Optional[int]` parameter
that overrides the naturally-computed `difficulty_level` and injects it
directly into `{difficulty_level}` for both new-topic and follow-up paths —
without needing a full session to naturally escalate there.

**Coverage:**
- New-topic path: minimum 4 questions, forced across difficulty 4 and 5,
  across ≥ 3 distinct chunks.
- Follow-up path: minimum 2, forced via real turns (question → scripted
  weak answer → score → follow-up question), same as v0.2.5's method,
  forced at difficulty 4/5.
- DA fixture case (Decision 6): minimum 2 generations against the synthetic
  digest, forced difficulty 5.

**Output:** `scripts/probe_question_gen_v0.3_hardening_results.jsonl`. Per
row: full model output, chunk index, requested difficulty, path
(`new_topic` / `follow_up` / `da_fixture`), automated `is_grounded()`
boolean + ratio, and two human-judged columns left `null` for Sean:
`content_fabricated_despite_grounding` (Decision 1's actual test) and,
DA-fixture rows only, `digest_claim_fidelity` (Decision 6).

**In plain terms:** same probe script that already proved question
generation works, just given the ability to force the hard cases instead of
waiting for a session to wander into them naturally — and two new columns
so a human looks at exactly the two things no automated checker covers yet.

## Decision 8 — Miss 3: verify the real corruption pattern before writing the fix

**Flagged conflict, not silently overwritten:** Day 2 called stray page
numbers "harmless noise the LLM ignores." Miss 3 found real mid-sentence
corruption. Miss 3 supersedes Day 2's verdict — Day 2 was correct for what
it tested at the time; Miss 3 is a real counter-example, not a retraction.

**Before writing the regex:** confirm from the actual corrupted chunk text
(re-extract the DAZSMA doc if the original example isn't recoverable —
same evidence-reconstruction posture as Decision 1) whether the page number
sits on its own line (safe to strip) or is genuinely interleaved mid-token
within a real sentence (harder — a naive strip risks deleting a legitimate
number, e.g. a real sample size). **Explicitly not an `is_grounded()`
retune** — this is an extraction-layer defect (`chunk_pdf`), not a
checker-layer one, per the handoff's own framing.

**In plain terms:** same instrument-first instinct as everything else —
look at the actual broken text before deciding how to fix it, because the
fix is completely different depending on whether the number is sitting
alone on its own line or jammed into the middle of a sentence.
