# Part 1 — v1.0a: Deployment hardening

## Framing

This is an **audit**, not a build. Absent a real problem, this slice's output is
verification evidence. Three deliberate exceptions produce code, and only three:

- the analytics sidebar move (item 7 — a locked amendment, not a finding),
- the timeout env var (item 6 — a config knob added specifically to make the
  timeout guard forceable on live),
- anything items 1–6 actually find broken.

Any found-and-fixed issue gets documented with before/after evidence — never a
silent patch.

**Scope discipline on findings.** Items 4 and 5 exist to *surface* problems, not
to fix them. If item 4 confirms the filesystem is ephemeral, the fix is a storage
backend change — that is a new slice with its own design conversation, not
something to improvise mid-session. Same for item 5: a bad cold-start number is a
README line and a scoping decision, not a rewrite. **Record, don't chase.**

## Item 3 — Memory footprint under `torch`, on the free tier *(amended — A)*

**Superseded instruction, kept for the record:** *"Real usage numbers pulled from
Streamlit Cloud's own logs/dashboard during a live session — not an estimate."*

**Why superseded:** Streamlit Community Cloud does not expose a memory dashboard
with pastable per-process figures. That DoD was unmeetable as written, and an
unmeetable DoD is worse than none — it invites either a stalled session or a
fabricated number, both of which fail this project's evidence standard. Claude
identified this and proposed the replacement; I accepted it 2026-07-23.

**Replacement:** instrument `psutil.Process().memory_info().rss`, logged at three
points and read out of Streamlit Cloud's logs:

1. post-import, before any model load
2. immediately after the `st.cache_resource` embedding-model load resolves
3. after the first fully scored turn of a live session

Separately record whether the container hits a resource-limit restart at any point
during a full session — that event, or its absence across a complete run, is
itself primary evidence about headroom.

The `psutil` instrumentation may stay in the deployed app (cheap, useful) or be
reverted after the run — Code's call, stated either way. If it stays, it must not
be in a business-logic module (standing constraint 4).

## Item 4 — Persistence and analytics on an ephemeral filesystem *(new — D)*

**The gap this closes:** v0.4b writes sessions as JSON to local disk. v1.0b
analytics reads `sessions/*.json`. Streamlit Community Cloud containers restart
and discard non-repo files. If that is what actually happens on the live tier,
then two full shipped slices are locally-only features on a project whose pitch is
a live public URL — and neither was ever audited on live. An audit that doesn't
check this isn't an audit.

Verify, on the deployed URL, with real evidence:

- Does a completed session's JSON survive a container restart? Force the restart
  (reboot from the Cloud dashboard) and check.
- Does mid-session resume (the v0.4b feature) actually work for a real visitor on
  live, or only locally?
- With `sessions/` empty — which may be the permanent live state — does the
  analytics view render a clean empty state, or does it crash on an empty list?
  This is the one item here that has a fix *in* scope, because an empty-state
  crash is a straightforward bug, not an architecture change.

**Record, don't chase.** If persistence is confirmed ephemeral, document the
finding precisely (what survives, what doesn't, under which restart conditions)
and stop. The remedy — a real storage backend, or an explicit "local-only feature"
framing in the README — is a separate decision.

## Item 5 — Cold-start latency and the keyless-visitor path *(new — E)*

**The gap this closes:** v1.0's own definition of done promises "a live public URL
completing a full session for a first-time visitor with no setup beyond
(optionally) pasting their own key." Nothing in the original brief verified either
half of that sentence.

Measure and paste:

- **Wake-from-sleep → first paint.** Let the app idle into Community Cloud's sleep
  state, then time a cold visit.
- **First-question latency from a cold container** — upload through to the first
  rendered panelist question, wall-clock.
- **The keyless path, end to end.** A visitor who pastes no key: can they complete
  a full demo session on the project key under the `ADS_DEMO_*` caps? Run it as
  that visitor would (fresh browser profile, no secrets, no dev toggles) and show
  it completing or show exactly where it stops.

**Record, don't chase.** A 45-second cold start is a README line and a scoping
input, not a bug to fix in this session.

## Item 6 — Full error-state walkthrough on the live URL *(amended — B)*

The original brief named five error states with no forcing mechanism for any of
them. That's the single most likely way this session turns into a design session
mid-flight. Each mechanism is pre-decided below; Code executes, it does not
improvise.

Every state must show its intended clean UX. A raw traceback reaching the user is
a finding, and gets fixed and re-evidenced.

| Error state | Forcing mechanism (live URL) |
|---|---|
| Malformed document upload | Real. Upload a corrupt/truncated PDF and a non-PDF file. No mechanism needed. |
| API failure | Real. Use the v0.4a BYO-key field with a syntactically valid but invalid key → genuine 4xx from Gemini. |
| Demo cap reached | Real. Temporarily set `ADS_DEMO_MAX_TURNS=1` in Cloud secrets, exhaust it, screenshot, revert. This is the demo-cap env amendment paying off. |
| Relevance-gate soft-fail | Real. Upload an obviously non-defense document (receipt, recipe, unrelated article) and take the proceed-anyway path. |
| Timeout guard | See below — primary and fallback. |

### Timeout guard — mechanism (delegated to Claude 2026-07-23; Claude's call, recorded as such)

**Primary — make the timeout env-configurable and force it on live.** Add
`ADS_LLM_TIMEOUT_SECONDS`, defaulting to the current hardcoded value so behavior
is unchanged when unset. Set it to ~1s in Cloud secrets, trigger a real generation
call, capture the guard firing on the live URL, revert the secret.

**Why this over the alternative I originally proposed** (running locally against
the deployed revision): it keeps all five error states genuinely live with zero
deviation from the DoD; it's a legitimate configuration knob rather than
fault-injection code shipped to production; and it reuses the exact pattern v0.4a
already established for `ADS_DEMO_MAX_TURNS` / `ADS_DEMO_SESSIONS_PER_BROWSER` /
`ADS_DEMO_DAILY_CAP` rather than inventing a new one. The default-unchanged rule
means this adds a capability without changing any existing behavior.

**Fallback — only if the timeout proves structurally non-configurable** (e.g. it's
enforced inside the SDK rather than by our own guard, with no injection point):
run the case locally against the exact deployed revision, paste
`git rev-parse HEAD` alongside the output, and record the deviation explicitly in
the evidence. **Code takes the fallback only after showing why the primary wasn't
viable** — a stated reason with the relevant source, not a preference.

# Part 2 — v1.0c: Rename pass

## Item 0 — Inventory first, rename second

The original brief instructed Code to `git mv` each file "to its correct name"
without saying what the correct names are. That hands a design decision to a Code
session, which this project doesn't do. The mapping is now decided below — but it
is a *target*, conditional on those files still existing.

**Step 0, before any `git mv`:** run `ls docs/` and check every filename against
`v{version}-{slug}-{type}.md`. Paste the raw listing and the conformance result.

- If non-conforming files exist → apply the mapping table below.
- If the tree already conforms → **v1.0c closes as a zero-commit verification
  slice.** The inventory output *is* the evidence. A no-op with proof is a valid
  outcome; a no-op assumed is not.
- If a non-conforming file exists that isn't in the table → stop and surface it,
  don't guess a name.

**Known accepted exception:** this file
(`v1.0a-v1.0c-hardening-rename-brief.md`) spans two versions and doesn't fit the
pattern. Record it as accepted in the conformance output, not as a failure. Do not
rename it.

## Locked naming convention

- **Version segment: dots.** `v0.2.5-`, not `v0_2_5-`.
- **Everything else: dashes.** Slug words separated by dashes.
- **Allowed `{type}` vocabulary, closed set:** `decisions`, `brief`,
  `verification`, `handoff`, `eval`, `results`. Nothing else. Combined
  decisions+brief files use `decisions` — the lean-docs convention folds the
  brief in. *(Revision 3: `results` added — the vocabulary was locked before
  the real `docs/` tree was inspected; `v0.2-eval-results.md` and
  `v0.4c-second-doc-eval-results.md` are unambiguous as-is, and results
  genuinely aren't decisions. Renaming them would be churn for its own sake.)*

The original DoD required a byte-identical diff *and* updated cross-references.
Those contradict. Split:

**Commit 1 — pure `git mv`.** Nothing else. Content byte-identical, so

each reference. **Grep scope is the whole repo, not just `docs/`** — at minimum

Never delete-and-recreate. `git mv` only.
