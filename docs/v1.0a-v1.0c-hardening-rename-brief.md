## Item 3 — Memory footprint under `torch`, on the free tier *(amended — A)*

**Superseded instruction, kept for the record:** *"Real usage numbers pulled from
Streamlit Cloud's own logs/dashboard during a live session — not an estimate."*

**Why superseded:** Streamlit Community Cloud does not expose a memory dashboard
with pastable per-process figures. That DoD was unmeetable as written, and an
unmeetable DoD is worse than none — it invites either a stalled session or a

**Replacement:** instrument `psutil.Process().memory_info().rss`, logged at three
points and read out of Streamlit Cloud's logs:

1. post-import, before any model load
2. immediately after the `st.cache_resource` embedding-model load resolves
3. after the first fully scored turn of a live session

Separately record whether the container hits a resource-limit restart at any point
during a full session — that event, or its absence across a complete run, is
itself primary evidence about headroom.

The `psutil` instrumentation may stay in the deployed app (cheap, useful) or be
reverted after the run — Code's call, stated either way. If it stays, it must not
be in a business-logic module (standing constraint 4).

## Item 4 — Persistence and analytics on an ephemeral filesystem *(new — D)*

analytics reads `sessions/*.json`. Streamlit Community Cloud containers restart
and discard non-repo files. If that is what actually happens on the live tier,
then two full shipped slices are locally-only features on a project whose pitch is
a live public URL — and neither was ever audited on live. An audit that doesn't
check this isn't an audit.

Verify, on the deployed URL, with real evidence:

- Does a completed session's JSON survive a container restart? Force the restart
  (reboot from the Cloud dashboard) and check.
- Does mid-session resume (the v0.4b feature) actually work for a real visitor on
  live, or only locally?
- With `sessions/` empty — which may be the permanent live state — does the
  analytics view render a clean empty state, or does it crash on an empty list?
  This is the one item here that has a fix *in* scope, because an empty-state
  crash is a straightforward bug, not an architecture change.

**Record, don't chase.** If persistence is confirmed ephemeral, document the
finding precisely (what survives, what doesn't, under which restart conditions)
and stop. The remedy — a real storage backend, or an explicit "local-only feature"
framing in the README — is a separate decision.

## Item 6 — Full error-state walkthrough on the live URL *(amended — B)*

The original brief named five error states with no forcing mechanism for any of

### Timeout guard — mechanism (delegated to Claude 2026-07-23; Claude's call, recorded as such)

**Primary — make the timeout env-configurable and force it on live.** Add
`ADS_LLM_TIMEOUT_SECONDS`, defaulting to the current hardcoded value so behavior
is unchanged when unset. Set it to ~1s in Cloud secrets, trigger a real generation
call, capture the guard firing on the live URL, revert the secret.

**Why this over the alternative I originally proposed** (running locally against
the deployed revision): it keeps all five error states genuinely live with zero
deviation from the DoD; it's a legitimate configuration knob rather than
fault-injection code shipped to production; and it reuses the exact pattern v0.4a
already established for `ADS_DEMO_MAX_TURNS` / `ADS_DEMO_SESSIONS_PER_BROWSER` /
`ADS_DEMO_DAILY_CAP` rather than inventing a new one. The default-unchanged rule
means this adds a capability without changing any existing behavior.

**Fallback — only if the timeout proves structurally non-configurable** (e.g. it's
enforced inside the SDK rather than by our own guard, with no injection point):
run the case locally against the exact deployed revision, paste
`git rev-parse HEAD` alongside the output, and record the deviation explicitly in
the evidence. **Code takes the fallback only after showing why the primary wasn't
viable** — a stated reason with the relevant source, not a preference.

## A. Four findings (recorded)

### Finding 1 — Streamlit's file watcher force-imports the `transformers` model zoo

`local_sources_watcher` walks `sys.modules`; `transformers` uses lazy
`__getattr__` imports, so every module the watcher *examines* it **imports**,
working through the zoo (`pp_doclayout_v2`, `pp_doclayout_v3`, `aria`, …) and
raising `ModuleNotFoundError: No module named 'torchvision'` on each.

**Fix (already applied):** `.streamlit/config.toml` → `[server] fileWatcherType = "none"`.

| Checkpoint | Before | After |
|---|---|---|
| Post-import (fig 1) | 1198.2 MB | **174.1 MB** |
| After model load (fig 2) | *never logged* | 1107.0 MB |
| After scored turn (fig 3) | 1401.2 MB | 1169.6 MB |

**Honest reading:** the mechanism was right but the payoff is smaller than
first claimed. The watcher was force-importing `torch` + `transformers` core,
which the embedding model needs anyway, so the fix **defers** that cost to
model-load time rather than eliminating it. Net peak saving ~225 MB, not
~1 GB. What was actually gained: a 174 MB idle floor vs 1198 MB, and the
traceback spam is gone. See section E for the "~1 GB ceiling" correction.

### Finding 2 — 5-second delay on every question generation

Five live-Cloud samples, HTTP-200 → call-returned:

```
04:45:31,341 → 04:45:36,344   5.003s
04:46:51,410 → 04:46:56,418   5.008s
04:47:12,966 → 04:47:17,968   5.002s
04:48:04,162 → 04:48:09,171   5.009s
04:48:28,362 → 04:48:33,371   5.009s
```

Question generation only — **never on answer scoring** (call #2 returns ~2 ms
after its HTTP response). Millisecond-consistency regardless of
grounding-check outcome pointed at a fixed `sleep(5)`. Fixed — see B′.

### Finding 3 — HuggingFace is a runtime dependency on every cold start

`all-MiniLM-L6-v2` is fetched from the Hub at model-load time, not baked into
the image: ~60 HTTP requests to `huggingface.co`, **28 s** from cache-miss to
figure 2 — the bulk of cold start, network-bound. Logs carry the
unauthenticated-requests warning. Risk: unauthenticated Hub requests are
rate-limited; an HF throttle or outage means the app can't load its embedding
model and every visitor fails. Decision in section C.

### Finding 4 — grounding check fails repeatedly on table-dense chunks

Three failures in one PathClear session, all on the same reference — the
model reformats table cells into prose instead of lifting verbatim. Textbook
**fabrication-by-synthesis** per the project's own taxonomy (not content
fabrication, not a correctness bug). Newly notable because it fired
*repeatedly* on a table-dense document where DAZSMA is prose-dense.
**Recorded as a document-shape sensitivity in the retrieval/grounding story;
parked as v1.0-adjacent, not fixed here.** Its second role: it was the
intended burst path for B″'s RPM verification — in the event, the ordinary
turn cadence turned out to matter more than the retry burst it produces (see
B″).

**Bonus (feed the case study):** the live pass used PathClear — my own
ESP32-CAM thesis — as its test document. That's the third document the
pipeline has run against (DAZSMA capstone, `sample2` TDOA capstone, PathClear
ESP32-CAM thesis). Generalization evidence is now three documents across

## B. Decision — 5-second sleep (Finding 2) — SUPERSEDED, retained for the record

Claude proposed; I pre-committed it before the Code session. Preserved

1. First action: `git grep -n "sleep" -- academic_defense_simulator/`, report

## B′. Deviation record — the rule was malformed; the fix stands

**Outcome:** sleep removed. `48f552c`, committed only.

**What Code found.** The sleep lived in `engine.py`,
`_generate_with_grounding_enforcement._call()`. It was post-call,
unconditional, with no failed HTTP request preceding it. Git history
(`6570294`) shows it was a deliberate dual-layer RPM throttle — not a stray
leftover. Code flagged this before acting, then applied the rule as
instructed because it was pre-committed and unambiguous. That was the correct
call on Code's part; the fault is mine, in the brief.

**Why the rule was malformed.** Two defects, and they interact:

1. **Internal contradiction.** Step 2 gated removal on a precondition —
   "leftover / UX / no functional dependency" — while step 3 asserted an
   absolute override, "under any framing". The sleep had a functional
   dependency, so the precondition failed and the override fired regardless.
   A rule whose escape hatch swallows its own precondition isn't a decision
   rule; it's a foregone conclusion wearing one.
2. **Wrong shape.** My rule said pre-call. The actual sleep was post-call —
   an inter-call spacer, which none of my classification buckets described. I
   wrote the rule against a mental model of a retry backoff and never
   considered a proactive throttle.

**Lesson, generalized:** a pre-committed rule exists so a Code session
doesn't stall on a design question mid-run. That's still right. But it must
enumerate the possibility space it's ruling over, and any "under any framing"
clause needs to be justified against each bucket separately — otherwise it's
not pre-commitment, it's pre-emption. Next pre-committed rule gets a "what if
it's none of these?" branch that halts rather than defaults.

**Why I'm not reverting.** Reasoning, not evidence: the reactive layer
survives — `gemini_provider.py`'s `_retry_or_fail` / `_retry_text_or_fail`
are both conditional on a real prior exception, unchanged. So 429s are still
caught. The dual layer is now single, not zero. That's an argument, and Day 4
is the standing reason not to trust arguments of this shape. Closed by B″.

**Test-coverage gap opened.** `tests/test_engine.py`'s sleep-patching fixture
was removed rather than left inert — correct, since it asserted against code
that no longer exists. Consequence: nothing in `tests/` asserted any
rate-limiting behaviour until B″ shipped its own limiter's tests.

**Evidence (`48f552c`):** local reproduction pre-edit, mean 5.009s
(5.000/5.000/5.016/5.016/5.015), matching the Cloud finding. After fix:
0.0000s. Scoring-path regression guard: 0.0000s before and after — unchanged.
`evidence/v1.0a-question-gen-delay-fix.txt`. 223 passed, 1 pre-existing
failure (`test_persistence_defaults_off_when_unset`, known `.env` isolation
issue). No `streamlit` import in `engine.py`, verified.

## B″. Closed — peak RPM verified under 15, real session against PathClear

**Outcome:** verified. Peak RPM confirmed at 14 — real margin, not a graze —
on a real 12-turn PathClear session, panel generation through end-of-session
report and suggestions. A sliding-window RPM limiter shipped (`b5f4e6f`),
scoped wider than this section originally specified.

**What Code found that this section didn't anticipate.** The limiter was
specified above as "scoped to the retry loop" on the assumption that the
ordinary one-question-gen-plus-one-score turn was safe. It wasn't: isolating
the retry-free steady-state case (zero grounding retries) showed question-gen
and scoring firing back-to-back, ~1s apart, with only the driver's end-of-turn
sleep between turns — a cadence of ~16 calls/minute, already over the ceiling,
before any retry adds more. Root cause: the old dual-sleep design (`6570294`)
kept question-gen and scoring apart in time via question-gen's own sleep; B′
removed that sleep, collapsing the gap. A limiter scoped only to retries would
not have closed it. Code flagged this before implementing; I confirmed the
correction — scope the limiter to every real provider call, not just retries.

**Four real attempts, real Gemini API, real quota**
(`evidence/v1.0a-pathclear-rpm-verification.txt`):

| Attempt | Result |
|---|---|
| 1 | Real 429 (`RESOURCE_EXHAUSTED`, `limit: 15`) at turn 8 — decisive on its own |
| 2 | Peak RPM 17, no limiter; retry-free steady state alone already ~16/min |
| 3 | Limiter active, ceiling=14 — no 429, but the externally-measured peak still touched exactly 15, the same number attempt 1 failed on |
| 4 | Limiter active, ceiling=13 — peak RPM 14, zero errors, report and suggestions both completed cleanly |

**The fix:** `gemini_provider.py`'s `_throttle_for_rpm` — a sliding-window
admission control inside `_call_once`/`_call_once_text`, the single real-
network chokepoint every call (question-gen, scoring, panel generation,
report narrative, suggestions, any retry) already passes through. Module-
level state keyed by model name, not per-instance — every real call site
constructs a fresh `GeminiProvider` (`streamlit_app.py`'s `_new_provider` on
every rerun), so instance state would never accumulate, and the real Google
quota is per-project-per-model anyway. Sleeps zero while the rolling 60s
window has room; sleeps only the exact deficit once full.

**Test coverage.** `tests/test_gemini_provider.py` gains 5 tests: fresh
window (no sleep), burst up to ceiling (no sleep), exact deficit once full,
default ceiling for an unrecognized model, and a wiring check that
`_call_once` throttles unconditionally — closing the gap B′ flagged.

**Ceiling knob — documented offset.** The `_RPM_CEILING` value is not a
literal RPM cap. Observed peak runs consistently one call above the
configured value (14 → peak 15, 13 → peak 14), most likely a
sliding-vs-fixed window boundary effect between the limiter's own
admission-time bookkeeping and completion-time external measurement. 13 is
the verified-clean setting against the real 15 RPM free-tier limit — **do
not raise it to 15 on the assumption it maps directly to the tier limit**,
that reproduces attempt 1's real 429. Any tier change re-verifies
empirically against a real session, the same way this number was reached,
not by arithmetic against the stated limit. Same warning lives as a code
comment at `gemini_provider.py`'s `_RPM_CEILING` definition.

**Provenance:** the threshold and PathClear document choice were my own
pre-committed rule; the scope correction (every call, not just retries) is
Claude's finding, flagged before acting, confirmed by me before
