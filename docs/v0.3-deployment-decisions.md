## Decision 1 — Deploy target: Streamlit Community Cloud

Unchanged from Day 1's tech stack lock. No alternative considered — this was
never actually an open question, just never executed.

## Decision 2 — Secrets: root-level TOML key, no code change assumed

Streamlit Community Cloud secrets are pasted as TOML into the app's Secrets
field, and **root-level keys are automatically exposed as environment
variables** too — `os.environ["KEY"]` works identically to `st.secrets["KEY"]`
without any bridging code, confirmed against current Streamlit docs. Since my
provider abstraction already reads the Gemini key via an env var lookup for
local `.env` use, this should be a zero-code-change item: same variable name,
same lookup, different source. Code confirms the exact env var name in use
(don't assume a name — grep it) and confirms nothing needs to change for it to
resolve identically on Cloud.

**In plain terms:** locally, my key lives in `.env` and gets read as an
environment variable. On Streamlit Cloud, I paste the same `KEY = "value"`
line into their Secrets box instead of a file, and Streamlit quietly makes
that available as an environment variable too — so the code that reads
`os.getenv(...)` doesn't need to know or care which environment it's running
in.

## Decision 3 — Cold start: `st.cache_resource` on the embedding model

Flagged in `ROADMAP.md`'s original deployment-gate rationale as a real risk
found only by actually deploying. Confirm `sentence-transformers` model
loading is wrapped in `@st.cache_resource` (not `@st.cache_data` — a model
object, not serializable data). If it's missing, add it. If it's already
there, state that and move on — this is a check, not an assumed gap.

## Decision 4 — Config: `.streamlit/config.toml` must be tracked, not ignored

The oxblood/charcoal palette locked in v0.3d lives in `config.toml`. Confirm
it's committed to the repo, not caught by a stale `.gitignore` pattern —
common default-template gitignores exclude the whole `.streamlit/` directory,
which would silently deploy with default theming and no error.

## Decision 5 — Dependencies: `requirements.txt` audit

Confirm every import in the codebase resolves from `requirements.txt` with no
local-only assumptions (e.g. a dev-only package, a path that only exists on
my machine). PyMuPDF and sentence-transformers both ship prebuilt wheels for
Cloud's Linux environment — no expected build-tool issues, but confirm rather
than assume.

Whatever `requirements.txt`, `.streamlit/config.toml`, `.gitignore`, and the

### Task order
1. **Env var name audit (Decision 2):** grep for how the Gemini key is
   currently read (`os.getenv`/`os.environ`). State the exact variable name.
   Confirm no code change is needed for Cloud secrets to resolve the same way.
2. **Cold start (Decision 3):** confirm or add `@st.cache_resource` on the
   embedding-model loader. State which case applied.
3. **Config tracking (Decision 4):** `git check-ignore -v .streamlit/config.toml`
   — if it returns a match (meaning it's ignored), fix `.gitignore` and force-add
   the file. If it returns nothing (already tracked), state that.
4. **Dependency audit (Decision 5):** diff actual imports across the codebase
   against `requirements.txt`. Flag anything missing or version-unpinned in a
   way that risks nondeterministic installs on Cloud.
5. **Local smoke test under Cloud-like conditions:** run the app locally with
   `.env` temporarily renamed/unset and the same values supplied only via a
   throwaway `.streamlit/secrets.toml`, to prove the secrets path — not the
   `.env` path — actually works before Sean pastes anything into a live Cloud
   dashboard. Delete the throwaway secrets file after.
