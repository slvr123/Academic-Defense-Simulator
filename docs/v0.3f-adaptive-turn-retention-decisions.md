# v0.3f — Adaptive Turn Retention: Design Decisions

**Status:** LOCKED — 2026-07-13; **Decision 5 explicitly confirmed by Sean
2026-07-17** (was the doc's only pending item). Fully locked end-to-end,
including `T_max = 12` and the call-budget math that depended on Decision 5.
**Scope:** Retire pure round-robin. A panelist who surfaces a weakness keeps
the floor for capped consecutive follow-ups; new-topic rotation advances only
among panelists who haven't yet opened their own topic; Devil's Advocate fires
exactly once, after every domain panelist has spoken, and gets the same

## Decision 1 — Rotation mechanism: derived from `used_chunk_indices`, no new state (LOCKED)

Domain-panelist rotation is driven entirely by how many genuine new topics
have been opened so far — which is already exactly what
`len(session.used_chunk_indices)` counts, since new-topic turns always
retrieve a chunk never seen before and follow-up turns always reuse the
previous turn's chunk. No new field on `DefenseSession`.

```python
domain_panelists = [p for p in session.panel if p.archetype_key != DEVILS_ADVOCATE_KEY]
next_domain_panelist = domain_panelists[len(session.used_chunk_indices) % len(domain_panelists)]
```

**In plain terms:** every time a genuinely new topic gets opened, that's one
more "round" completed — so counting new topics is the same as counting
rounds, and the code already tracks new topics for an unrelated reason
(excluding chunks from re-retrieval). Reusing it means zero new bookkeeping.

---

## Decision 2 — Follow-up: the same panelist continues, full stop (LOCKED)

When `_should_follow_up(session)` returns `True` (unchanged function, unchanged
trigger and cap), the active panelist is whoever asked the previous turn —
looked up directly from `session.turns[-1].panelist_archetype_key`, not
re-derived. This applies uniformly to domain panelists and to Devil's Advocate
(Decision 4) — `_should_follow_up` is already panelist-agnostic, checking only
the previous turn's score, so no special-casing is needed for DA's own
follow-ups to fall out of the same rule correctly.

**This is the actual mechanism Sean described:** "an expert has 1-2 follow-ups
if he's not satisfied, then we're forced to proceed to the next panelist with
a different specialty." The existing cap (`MAX_FOLLOW_UPS_PER_TOPIC = 2`)
already enforces the "forced to proceed" half; this decision is what makes the
"same expert presses" half true, which round-robin never guaranteed.

## Decision 3 — New-topic rotation only advances among panelists who haven't spoken (LOCKED)

Combining Decisions 1 and 2: `select_active_panelist` becomes —

```python
def select_active_panelist(session: DefenseSession, turn_num: int) -> Panelist:
    if _should_follow_up(session):
        prev_key = session.turns[-1].panelist_archetype_key
        return next(p for p in session.panel if p.archetype_key == prev_key)

    domain_panelists = [p for p in session.panel if p.archetype_key != DEVILS_ADVOCATE_KEY]
    domain_spoken = {
        t.panelist_archetype_key for t in session.turns
        if t.panelist_archetype_key != DEVILS_ADVOCATE_KEY
    }
    if all(p.archetype_key in domain_spoken for p in domain_panelists):
        return next(p for p in session.panel if p.archetype_key == DEVILS_ADVOCATE_KEY)

    return domain_panelists[len(session.used_chunk_indices) % len(domain_panelists)]
```

`turn_num` becomes vestigial (kept in the signature for compatibility with
existing callers; the function no longer uses it directly). Flag for Code: if
nothing else calls this positionally in a way that would break, drop the
parameter instead of leaving a dead one — state whichever was actually done.

## Decision 4 — Devil's Advocate: fires once, after every domain panelist has spoken, same follow-up treatment (LOCKED)

DA's trigger (embedded in Decision 3's logic above): the turn after the last
domain panelist's own topic-opening turn. DA's own question does not consume a
`used_chunk_indices` slot (unchanged from `_generate_da_question` — it
re-grounds in the target claim's existing chunk, never calls `retrieve()`), so
it cannot interfere with domain rotation's counting.

DA's answer gets scored exactly like any other turn, which means
`_should_follow_up` can fire on it exactly like any other turn — DA presses its
own challenge for up to `MAX_FOLLOW_UPS_PER_TOPIC` follow-ups if the candidate's
answer is weak, via Decision 2's same-panelist rule. No special case required.

**Rationale over the alternatives considered:** a fixed-turn-number DA slot or
a DA fully decoupled from domain rotation were both considered and rejected —
neither actually guarantees "DA speaks after everyone else," which was the
entire narrative point of DA's original "always last" placement. This decision
preserves that guarantee more strongly than round-robin ever did, since
round-robin's "DA last" was really just a coincidence of list order, not an
enforced condition.

## Decision 5 — Termination: session ends when DA's own chain concludes
**(CONFIRMED by Sean, 2026-07-17 — LOCKED)**

The session ends the moment DA's follow-up chain concludes — DA has spoken,
and either the candidate's answer to DA was strong (no follow-up triggered)
or `MAX_FOLLOW_UPS_PER_TOPIC` was reached on DA's challenge. No second round;
no loop-back to domain panelists after DA. DA's contest is the capstone of
the session, not one stop in a repeating cycle.

**Provenance, kept for the record:** this was originally proposed by Claude
during the design conversation and flagged PENDING CONFIRM rather than
silently locked, because everything downstream (Decision 6's `T_max`, the
call-budget estimate) depended on it. Sean confirmed it explicitly on
2026-07-17 at the v0.3d→v0.3e handoff — the downstream math stands as
written, no rework needed.

## Decision 6 — `T_max`: a computed backstop, not a chosen number (LOCKED)

**Correction to an earlier, wrong recommendation, recorded honestly:** a
fixed `T_max = 10` was proposed mid-conversation on flawed reasoning — an RPD
justification for a number that was actually *below* the mechanism's own
natural worst case, which would have guaranteed DA gets cut off in the
pathological case for no real benefit, not protected against something rare.

**Corrected decision:** `T_max` is not an independently chosen limit — it is
exactly what the mechanism's own worst case computes to, given how many total
panelists a session has:

```python
T_max = 3 * len(session.panel)  # 1 initial + MAX_FOLLOW_UPS_PER_TOPIC(2) per panelist, worst case
```

With `v0.3e`'s uniform 4-total cap, this is a single number for every defense
type: **`T_max = 12`.** `T_max` is a defensive circuit-breaker (guard against a
bug or genuine infinite loop), not a real design constraint — under correct
operation, Decision 5's termination condition always fires at or before
`T_max`, never after.

**Expected real-world range, not the worst case:** best case (every answer
strong first try, including DA's) is 4 turns — one per panelist, no
follow-ups. A session where roughly half the turns trigger one follow-up lands
around 6-7 turns. Only a session where *every* panelist including DA maxes out
both follow-ups reaches the full 12. **Worth stating plainly: the typical
session is very likely shorter than the old fixed `MAX_TURNS = 6`, not
longer** — the old design ran a fixed 6 turns regardless of how the
conversation went; this design ends as soon as DA concludes, which for a
strong candidate could be turn 4.

**Call budget, restated honestly against the old flat `2T`:** 2 calls per turn
+ 1 report call. Best case: 2×4+1 = 9. Realistic: ~13-15. Worst case (rare):
2×12+1 = 25. Against 500 RPD: even the worst case supports ~20 sessions/day if
every single one hit the pathological ceiling, which is itself unlikely — the
realistic case supports a comparable or better number than the old flat
budget's ~33/day, since most real sessions will run shorter, not longer.

**Accepted, un-engineered-around edge case:** in the true worst case (every
panelist maxes every follow-up), the session could hit `T_max` before DA ever
fires, meaning DA never appears. No override logic is being built to force DA
in under budget pressure — this is rare, and whether it's worth solving should
be decided from real beta evidence of it actually happening, not designed
around speculatively now.

---

## Decision 7 — `MAX_TURNS` is retired (LOCKED)

The fixed turn-count constant is replaced entirely by Decision 5's termination
condition, backstopped by Decision 6's `T_max`. Not deprecated-but-kept — actually
removed, since keeping an unused constant around invites exactly the kind of
stale-assumption bug this project has caught several times tonight.

## Decision 8 — Downstream impact: confirmed narrow (LOCKED)

Checked explicitly so this isn't assumed:

- **`report.py` (0.3c):** unaffected. Per-panelist aggregation already filters
  by `archetype_key` and averages over however many turns exist for that key —
  no hardcoded assumption of one-turn-per-panelist. No changes needed.
- **UI turn/exchange rendering (0.3d):** unaffected. The transcript header
  already reads live off each turn's `panelist_archetype_key`/`panelist_name`;
  card states already read off `session.turns` and whatever
  `select_active_panelist` currently returns. No assumption of a fixed
  rotation pattern exists anywhere in the UI layer.
- **One real exception, corrected here rather than left as an oversight:** the
  turn-progress display (`"Turn N of 6"`) hardcodes the old fixed length.
  Under a variable-length session, showing `"Turn N of 12"` would be
  misleading — most sessions end well before 12. Replace with a progress
  indicator that doesn't imply a fixed denominator (options: turn number
  alone, or domain-panelists-spoken-of-total — Code's call which reads better,
  screenshot either way).
- **Persona generation timing (0.3a):** unaffected — still one upfront call at
  convene, unchanged.
