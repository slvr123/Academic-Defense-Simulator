## Part 1 — Locked decisions

Unless noted, Claude proposed each of these in our design conversation on 2026-10-27, and I confirm them by sending this brief. The three checks themselves come from case study §8, which has listed them as "specified, not yet run" since v1.

### F1. Why this milestone, and why now
The app's central claim is that several expert panelists interrogate *my* document. The generation half of that claim has been evaluated hard; the retrieval half never has. Since M3, the live app shows every visitor which passage each question came from, so if archetypes all pull the same evidence, anyone can see it. I'm measuring before the polish milestone and before the README refresh, so neither builds on an unmeasured claim.
*Downside I accept:* nothing visible changes in the app this milestone.

### F2. What retrieval actually does today (facts the checks are built on)
- A new-topic turn retrieves with `query = archetype_focus`: a fixed string per archetype, the same in every session and for every document. Follow-ups reuse the previous chunk; the Devil's Advocate doesn't retrieve.
- `top_k=1`, deterministic, with `exclude_indices` = chunks already used in the session.
- Embeddings: all-MiniLM-L6-v2 (ONNX in v2), **truncated at 256 tokens**. Chunks are packed to about 600–800 tokens.
- Prior evidence on `feat/retrieval-sources`: 135 of 141 chunks exceeded the 256-token limit, so the embedding only "sees" roughly the first third of most chunks. That branch also ran an 8-case labelled comparison (current chunks 4/8 hit@1, 5/8 hit@3); neither alternative chunker beat the default.

Because retrieval is deterministic and depends only on the document and the archetype, **every check in M4 runs offline with zero Gemini calls, zero MiMo calls and zero defense slots.**

### F3. Measure the live stack, not a copy
Every check uses the exact chunker and embedder that production uses: the v2 backend's ingest path and the ONNX embedder, not sentence-transformers. If the production path can't be called from a script without changing it, add a thin read-only adapter in the eval code. Never change production modules.

### F5. The five checks
Retrieving archetypes = all archetypes except the Devil's Advocate.

**Check A — archetype evidence overlap (the main question).** For each document, rank every chunk by cosine similarity to each archetype's query. For every pair of archetypes, count how many of their top-5 chunks are shared (0–5), and whether their top-1 is identical. Report the pair matrix per document, the median shared count, and a random baseline (expected shared count for two random 5-sets from that document's chunks).

**Check B — score spread (is `top_k=1` principled or arbitrary?).** For each archetype × document, record the top-5 cosine scores. A *near-tie* is when rank 1 beats rank 2 by less than 0.02. Report the near-tie rate and the full gap distribution.

**Check C — front-matter hit rate.** *Front matter* = every page before the first page whose text matches a Chapter 1 / Introduction heading. *Navigation pages* = pages where most lines end in a page number or dotted leaders (table of contents, lists of figures and tables). Report: the detected boundary page and the navigation-page list per document (for my eyeball check), the front-matter base rate (front-matter chunks ÷ all chunks), the share of archetype top-1 picks that land in front matter, the ratio between those two, and any pick that lands on a navigation page.

**Check D — embedding coverage.** For each document: how many chunks exceed 256 tokens, and the mean share of each chunk's tokens the embedding actually sees.

**Check E — simulated sessions (what a user actually gets).** For each defense type's recommended panel on each document, replay the engine's real retrieval order for the first 6 new-topic turns: round-robin, `top_k=1`, exclusion applied. Assume no follow-ups (they reuse chunks and depend on Gemini scores). Record the chunk and page each turn gets, and the **displacement rank**: where that chunk sat in the archetype's own ranking. Rank 1 means the archetype got its best match; rank 7 means six better matches were already taken or excluded.
**Validation:** replay the panel and document from the M3 and M3b live runs (raw API responses are in their results docs) and confirm the simulated turns 1–4 retrieve the same pages as the live sources. A mismatch means the simulation doesn't reproduce the engine: halt.

Why Check E matters: exclusion guarantees each panelist gets a *different* chunk even when all of them wanted the same one. So the live app can look differentiated while archetypes are actually being pushed down to their 5th or 10th choice. Displacement rank exposes that.

### F6. Pre-committed reading of the results
Written before any data exists. Each outcome says what it licenses.

**Check A verdict, from the median shared count across all archetype pairs and documents:**
- **0–1 shared → Differentiated.** I may state in the README and case study, with numbers, that archetypes retrieve different evidence.
- **2–3 shared → Partial.** I may only state it with the overlap numbers attached. Query enrichment becomes a candidate fix.
- **4–5 shared → Collapsed.** The claim is unsupported: differentiation lives in voice and lane, not evidence. A retrieval-fix milestone comes before polish, and the README must not claim evidence differentiation.
- **Documents disagree** (one Differentiated, one Collapsed): report per document, no overall verdict, and say what distinguishes them.

**Check B:** a near-tie rate above 50% means `top_k=1` is choosing among near-equals. Sampling among the top 3 becomes a candidate fix for repetition at no relevance cost. 50% or below means `top_k=1` is defensible as is.

**Check C:** a ratio above 1.5, or any navigation-page pick, means front matter is over-retrieved. Down-weighting or excluding navigation pages becomes a candidate fix.

**Check D** is a fact, not a verdict. The case study must state it.

**Check E:** any archetype with displacement rank above 5 in the first round of turns is a collapse signal that exclusion is masking. Report it alongside Check A.

**None of the above** (a check can't run, a metric is undefined, documents too short to have 5 chunks per archetype): halt that check, record why, and continue with the rest.

**M4 implements no fixes.** Candidate fixes go into the results doc as proposals, each with expected effect and downside. Choosing one is my decision in chat after the debrief.
