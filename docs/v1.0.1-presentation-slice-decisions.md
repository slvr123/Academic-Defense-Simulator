## Decision 0 — Gate: the sample document is chosen and licence-verified before the Code session opens (LOCKED)

**This is a gate, not a task.** The Code session does not open until I have the
sample PDF in hand and its licence confirmed. Every other decision in this file
depends on which document this is, so resolving it mid-session would stall the
session at step one.

**Selection criteria:**

- **Licence permits redistribution.** This is the load-bearing criterion and
  the easiest one to get wrong. arXiv's *default* submission licence grants
  arXiv a distribution licence and does **not** grant me the right to
  redistribute the PDF inside my repo. Only papers explicitly marked
  **CC BY, CC BY-SA, or CC0** on their arXiv abstract page qualify. Verify the
  licence line on the abstract page itself; do not infer it from the fact that
  the PDF is downloadable.
- **10–30 pages.** Long enough for varied chunks, short enough that ingestion
  is quick.
- **Has a methodology section, an implementation or system section, and
  results.** All three archetype lanes need real material or the example
  session renders thin.
- **Legible domain.** An ML, software-engineering, or systems paper reads to a
  general LinkedIn audience; a signal-processing paper does not. This is a demo
  asset, not eval evidence, so audience legibility outranks domain diversity
  here.
- **Text-extractable by PyMuPDF**, not scanned images.

**Explicitly excluded: DAZSMA and the TIP TDOA capstone.** Both were used with
consent *for evaluation*. Bundling either into a public repo as a permanent
demo asset is a materially wider consent scope than the one I obtained, and
v1.0's close-out already resolved one document-exposure finding on consent
grounds. I am not re-opening that question to save myself an hour of searching.
A CC-licensed third-party paper costs nothing and keeps the demo assets cleanly
separate from the eval evidence base.

**Recorded in the repo:** the chosen paper's title, arXiv ID (or equivalent),
licence string, and retrieval date go in the sample directory's README. Future
readers must be able to verify the redistribution right without trusting my
memory.

**In plain terms:** I pick one freely-redistributable paper before opening
Code, and I check its licence properly rather than assuming that a public PDF
is a reusable PDF. The two documents I already have are off the table because
permission to test with something is not permission to publish it.

## Decision 1 — One document serves both the sample path and the example session (LOCKED)

The sample document from Decision 0 is also the document the committed example
session (Decision 4) is recorded against.

**Reasoning.** The example session's transcript contains question text and
`grounding_reference` strings quoted from whatever document it was run on. If I
recorded it against DAZSMA, I would be publishing DAZSMA excerpts through the
transcript's back door — the exact class of exposure v1.0's close-out found and
resolved. Unifying on one licence-clean document makes that entire question
disappear rather than requiring a redaction argument.

**Consequence:** the example session must be **generated fresh** during this
slice. It cannot be pulled from the three existing persisted sessions, all of
which are against the eval documents.

**In plain terms:** one paper, used twice — as the thing visitors can try
instantly, and as the thing the recorded session was recorded against. That
removes the awkward situation where a stranger reads a stranger's capstone
through my transcript view.

## Decision 2 — Sample path: precomputed chunks and embeddings, shipped as a versioned sidecar (LOCKED)

The sample document ships with its ingestion output precomputed and committed,
so the sample path skips chunking and document-embedding entirely.

**Committed artefacts** (directory name is Code's call; `sample/` is the
obvious choice):

- the PDF itself
- `chunks.json` — the chunk texts and their indices, exactly as the live
  chunker produces them
- `embeddings.npy` — the chunk embedding matrix
- `manifest.json` — the guard payload, per Decision 3
- `README.md` — Decision 0's provenance record

**What this actually saves, stated honestly:** the chunking pass and the
document-embedding pass. It does **not** save the `sentence-transformers` model
load, because each turn embeds a freshly-generated query and that needs the
encoder live. Anyone reading this doc later should not come away believing the
sample path is model-free — it is not, and overstating this in the README would
be a claim the code doesn't back.

**In plain terms:** the sample paper arrives pre-digested, so clicking it skips
straight past the slowest setup work. The embedding model still has to wake up
for the questions themselves — this is a real speed-up, not a magic one.

## Decision 3 — Sidecar staleness guard: assert on load, fail open to live ingestion (LOCKED)

Precomputed embeddings are silently coupled to the embedding model and to the
chunker's current parameters. If either changes, the vectors go stale, cosine
similarity keeps returning confident-looking numbers, and retrieval quality
degrades **with no error anywhere**. That is the worst failure shape available:
wrong, quiet, and plausible.

**The guard.** `manifest.json` records at minimum:

- embedding model identifier (`all-MiniLM-L6-v2`)
- embedding dimensionality
- chunker parameters (target size, overlap — whatever the chunker actually
  takes; read the source, don't assume the Day 1 numbers still hold)
- chunk count
- the PDF's SHA-256

On load, all of these are asserted against the live configuration and the live
file. **Any mismatch → log a warning naming the mismatched field, discard the
sidecar, and ingest the sample PDF live.** The user still gets a working
session; they just pay the ingestion cost. Same fail-open pattern the relevance
gate and the answer-suggestions call already use.

**Not negotiable:** the mismatch path must log loudly enough that I notice it
in the deployed logs. A silent fallback would hide exactly the regression the
guard exists to catch.

**In plain terms:** the pre-digested sample is stamped with the recipe that
made it. If the recipe ever changes, the app notices, throws the stale copy
away, and re-does the work rather than serving quietly wrong results.

## Decision 4 — Relevance gate is precomputed on the sample path, never skipped-and-hidden (LOCKED)

The sample document is known-good, so the v0.3g `DocumentAssessment` call does
not fire on the sample path. The assessment is precomputed once, stored in
`manifest.json` as real JSON from a real call, and loaded.

**Quota effect:** removes one of the two `gemini-2.5-flash` calls per demo
session (gate + answer-suggestions). Against the documented ~10-full-sessions
per day free-tier ceiling, this materially raises the number of sample sessions
a launch day can absorb. I am not attaching a precise multiplier — the
suggestions call remains, and the real ceiling depends on which call dominates
under actual traffic. Mechanism stated, number withheld, same discipline
applied to adaptive difficulty in every public artefact.

**Transparency requirement:** dev-view renders the precomputed assessment with
an explicit `precomputed` marker. The gate must not appear untested or absent —
it is a real result from a real call, and the dev drawer says so.

**In plain terms:** the app doesn't re-ask the AI whether the sample paper is a
research document, because it already asked once and saved the answer. The dev
drawer shows that answer with a label saying where it came from, so nobody
inspecting the app concludes the check was quietly dropped.

## Decision 5 — Example session: a committed fixture rendered through the existing renderers, as a new read-only stage (LOCKED)

**Data source: a committed JSON fixture, not the runtime persistence
directory.** Persistence is opt-in via `ADS_PERSISTENCE_ENABLED` and scoped to
local/self-hosted only (v0.4b) — the deployed app has no session files to read.
The example session is a repo artefact.

**Rendering: reuse `_render_report` and the existing transcript renderer
unchanged.** No parallel render path. This is the smallest correct diff and it
is self-verifying: if the example view renders correctly, the real renderers
work.

**Mechanism: a new stage in the existing state machine** (e.g.
`stage = "example"`), not a Streamlit multipage app. Multipage buys routing and
a second navigation model for a single read-only view.

**Read-only means:** no answer box, no submit control, no dev-view toggle. A
fixed banner above the transcript — *"Recorded example session — not live"* —
and a single CTA returning to intake.

**Reachable from two places:**

1. A secondary control on the intake screen, visible before any mode is chosen.
2. The demo-exhausted and demo-already-used gates (v0.4a Decision 6), whose
   copy gains a link to it. **This is the launch-day failure this decision
   exists to prevent:** the post lands, the daily cap is reached, and every
   subsequent visitor currently meets a disabled button and nothing else. After
   this slice they meet a full recorded session at zero API cost.

**In plain terms:** one real session, recorded and committed, viewable by
anyone in five seconds with no key, no upload, and no quota. It is also what
visitors see once the day's demos run out, so hitting the cap stops being a
dead end.

## Decision 6 — The example session is recorded, never authored (LOCKED)

The fixture is produced by running a genuine session locally against the sample
document with `ADS_PERSISTENCE_ENABLED` on, then redacting and committing the
resulting JSON.

**Quality target for the recording:** answers of deliberately mixed strength,
so the difficulty trajectory moves and at least one pushback event registers. A
flat trajectory renders correctly (0.3d Decision 6 already handles the
zero-escalation case with an explicit line) but makes a poor demo artefact.

**Hard rule: if the recorded session comes out flat or unrepresentative, I run
it again with genuinely different answers. I do not edit the JSON.** Hand-tuning
a committed session file to look better is fabricating evidence, and this
project's entire evidence standard rests on the opposite instinct. Re-running
costs ~15 calls. Editing costs the credibility of every number in the repo.

**Redaction requirement — the known landmine.** v1.0's close-out found a
3,827-character verbatim document chunk inside a committed session JSON. The
export path has a `document_chunks` redaction; the raw persistence path is what
produced the finding. **The fixture is redacted and then verified by the
inventory script before it is committed.** This is also the first live exercise
of the inventory-script regression check already queued as a v1.1 handoff item
— run it here and the standing pre-publish check gets its first real use.

**In plain terms:** the example session is a real session I actually sat, not a
mock-up I wrote to look good. If it comes out boring I sit another one. And
before it goes into the repo, the redaction check runs — because this is
precisely the file shape that leaked a document chunk last time.

Placed above the mode radio on the intake screen, so it clears the fold on a

**Headline (locked copy):**

**In plain terms:** the app finally says what it is on the first screen,
in the same words the LinkedIn post leads with. Three bullets explain the
mechanism to someone who has never heard of RAG, without promising a number I
haven't measured or a privacy property I haven't checked.

## Decision 8 — Mobile: check first, then one capped fix; no viewport detection (LOCKED)

**The check is mandatory; the fix is conditional.** Streamlit collapses the
sidebar on narrow viewports, and the case-file sidebar (0.3d Decision 9) holds
the panel roster and turn progress — load-bearing context that silently
vanishes on a phone. LinkedIn traffic is majority mobile, so this is the
default viewing condition for the launch, not an edge case.

**Procedure:** run a full session on a real phone against the deployed app —
intake, mid-session, report, example view. Record findings with screenshots.

**Pre-authorised fix, if the check confirms the problem:** a compact
turn-progress and panel-roster line rendered in the **main column**,
unconditionally, on every viewport. Harmless on desktop, load-bearing on
mobile.

**Explicitly rejected: viewport detection.** Streamlit has no reliable
server-side viewport query, and the JS-component workarounds cost a dependency
and a rerun for a cosmetic conditional. Unconditional duplication is the
cheaper correct answer.

**Anything the check finds beyond this is recorded, not fixed in this
session.** That is the cut line — see the session-risk note below.

**In plain terms:** I look at the app on my phone before strangers do. If the
sidebar disappearing turns out to matter, the fix is to also show that
information in the main column always, rather than building viewport-detection
machinery to show it conditionally.

## B2 — Decision 3: staleness guard blast radius, corrected downward

Code reported that the CRLF issue would fire the staleness guard on "every

Git classified the sample PDF as *text* because reportlab's output for a
text-only document contains no NUL byte in its first 8000 bytes — which is the
entire heuristic git uses. With `core.autocrlf=true`, checkout rewrites the
PDF's 372 LF bytes to CRLF, changing its size and its SHA-256.

`core.autocrlf=true` is a **Windows** default. Linux and macOS checkouts,
including Streamlit Community Cloud's, use `false` and preserve the bytes. So
the actual blast radius was Windows working trees — my machine and any Windows
collaborator — not the deployed app.

**The fix is still correct and still necessary.** `.gitattributes` marking the
sample assets `binary` is what makes the committed SHA-256 mean anything across
platforms.

**Worth recording as the more interesting finding:** the guard would have
*worked*. It would have caught the corrupted SHA, logged loudly, and fallen
back to live ingestion — a working app with a degraded optimisation and a log
line saying exactly why. That is Decision 3 behaving precisely as designed
against a failure nobody anticipated. Code was still right to remove the root
cause: a guard that fires constantly is a guard people learn to ignore.

**Provenance:** Code found and fixed it; Claude corrected the blast-radius
claim; I locked the correction, 2026-07-27.

## B8 — `test_persistence_defaults_off_when_unset`: fix the test, not `load_settings`

**Status at close of steps 1–5: 243 passed, 1 failed.** Code correctly proved

**The call: the test is at fault, not the configuration code.**

Cause: my local `.env` sets `ADS_PERSISTENCE_ENABLED=1`. `load_settings()`
calls `load_dotenv()`, which re-injects the variable *after* the test's

tried to clear.

**Fix:** monkeypatch `load_dotenv` to a no-op within that test, so it exercises

latent fragility and will pass or fail depending on the developer's `.env`.
Find them and apply the same isolation, whether or not they currently fail on
my machine.

## C2 — fileWatcherType made environment-conditional (LOCKED)

**Partially reverses a locked v0.3 hardening decision.** Stating that plainly
rather than letting this read as new.

The original decision set `fileWatcherType = "none"` globally in `config.toml`,
because Streamlit's watcher force-imports the transformers model zoo via a lazy
`__getattr__` and inflates boot RSS by roughly 225 MB.
That reasoning was correct and is unchanged — but it was reasoning about
deployment, where memory is the binding constraint.
It was applied globally, which also removed the watcher locally, where memory is
not a constraint and the watcher is what makes editing code and re-running work
at all.

**The cost of the global setting, measured in practice.** With no watcher, a
running process never picks up a source edit.
Combined with Streamlit binding port 8501 alongside an already-listening process
without warning, a server that outlives a rename serves stale modules
indefinitely and a restart appears to do nothing.
This cost roughly an hour on 2026-07-27 and produced an `AttributeError` that
survived every obvious fix.
Phases 2 and 3 of the remaining work are almost entirely edit-then-re-run
cycles, which is exactly the shape that triggers it.

**Decision: watcher enabled locally, "none" on deploy.**

**Implementation note.** `config.toml` is static and cannot be made conditional
directly, but Streamlit reads configuration from environment variables.
Keep `config.toml` as the deploy default (`"none"`) and have the local launcher
set `STREAMLIT_SERVER_FILE_WATCHER_TYPE` to enable the watcher.
This makes C3 the delivery mechanism for C2 — the restart script is where the
variable is set, so the two ship together and neither is useful alone.

Deploy behaviour must be verified unchanged, not assumed: confirm the deployed
instance still resolves to `"none"` and that the RSS saving is intact.

**In plain terms:** the memory saving was always about the server, not about my
laptop.
Local development gets the watcher back; the deployed app keeps the saving it
was built for.

## D1 — Decision 6 CARVE-OUT: re-running a failed call on unchanged inputs is recovery, not authoring (LOCKED)

**The situation.** The committed fixture came back with
`suggestions_fallback_used: true` and an empty `answer_suggestions` list. The
answer-suggestions call is fail-open by design (`report.py`: an API error
returns `[], True` and never raises, so a suggestions failure can never damage
the narrative or the rest of the report). The transcript, the scores, the
trajectory and the narrative were all real and intact — one optional call had
failed, and the recording had captured the failure rather than the result.

**Decision 6's hard rule is "I do not edit the JSON."** Read literally that
would freeze the fallback state into the example view forever, so the example
session — the one artefact whose entire job is showing the product working —
would permanently end on "Suggestions unavailable this session."

**The carve-out, and the line it draws.** Re-running a real call against
unchanged inputs after a transient failure is **recovery**. Hand-writing
suggestions, or editing the ones the model returned, is **fabrication**.
Decision 6 exists to prohibit the second, not the first. The distinguishing
test is whether a human wrote any of the content: here, none of it. The
transcript, scores, panel and narrative were not touched, and the inputs to the
re-run were byte-identical to what the original call received.

**Guard rails, applied.** One attempt, no retry loop. If the call had failed
open a second time the fixture was to be left untouched and the failure
reported — the fallback state is a real state and papering over it would be the
fabrication this carve-out exists to prevent. It succeeded on the first
attempt: 8 suggestions, one per turn, from `gemini-2.5-flash` (the v1.0b-2
Decision 2 pin).

**Verified scope of the change.** A field-by-field diff of the fixture before
and after showed exactly two changes:
`session.report.answer_suggestions` (0 → 8 entries) and
`session.report.suggestions_fallback_used` (true → false). Nothing else in the
file moved. The inventory script was re-run afterwards and passed, so the
`document_chunks` redaction assertion still holds.
