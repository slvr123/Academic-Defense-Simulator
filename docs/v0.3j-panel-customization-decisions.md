## Decision 1 — Customization lives on intake, per archetype slot (LOCKED)

Name and icon controls render on the intake screen, inside/adjacent to the
composition-preview area — one row per selected archetype, plus a fixed row for
the always-seated Devil's Advocate. Each row: the archetype title (existing),
an optional "Panelist name" text input, and an icon select.

Blank name = the generated name from persona generation, exactly as today. The
preview's "Assigned at convene" placeholder shows only for slots left blank.

I considered a post-generation edit step (rename panelists after convene) and
rejected it: it adds a screen and a state-machine stage for no gain. The
real-world use case — naming panelists after my actual defense panel — works
*better* at intake, because I know my panel's roles and names before any
generation runs. Claude proposed intake over post-generation during our design
conversation; I confirmed it today.

**Implementation flag (confirm against actual code, don't assume):** if the
intake controls currently sit inside an `st.form`, per-slot rows can't
dynamically track the multiselect within the form (forms don't rerender on
widget change). If so, either the multiselect + customization rows move outside
the form, or the rows render for all selectable archetypes with unselected ones
ignored at submit. Code session picks whichever matches the existing intake
structure with the smallest diff — this is an implementation detail, not a
design decision, but it must be stated in the verification notes which path was
taken and why.

**In plain terms:** when you're picking which panelists sit on your panel, you
can also type who they are — "Dr. Reyes" instead of whatever name the AI would
invent — and pick a small icon for them. Leave it blank and the AI names them
like it always has. No new screens; it's part of the same setup step.

## Decision 2 — Plumbing: customizations ride on `DefenseProfile`, override applied post-generation (LOCKED)

```python
class PanelistCustomization(BaseModel):
    archetype_key: str
    display_name: Optional[str] = None   # None/blank → keep generated name
    icon: Optional[str] = None           # None → archetype default

class DefenseProfile(BaseModel):
    # ... existing fields unchanged ...
    panel_customizations: list[PanelistCustomization] = Field(default_factory=list)
```

Validator addition on `DefenseProfile`: every `archetype_key` in
`panel_customizations` must be in `selected_archetypes` or be the DA key; no
duplicate keys. Same style as the existing `check_selected_archetypes`
validator — schema validates once, downstream code trusts it.

**The override is applied in Python, after persona generation returns.**
Persona generation runs unchanged for every panelist — it produces more than a
name, and its prompt template is not touched. Where a `display_name` exists for
that archetype, it replaces the generated name on the `Panelist` object before
the roster is finalized. From that point on, every existing consumer —
`panelist_name` injection in question templates, transcript attribution, card
labels, export JSON — receives the custom name with zero further changes,
because they all already read from the `Panelist` model.

`Panelist` gains one field: `icon: str` (non-optional on the model — the
archetype default is resolved at roster-build time, so downstream rendering
never handles a missing icon).

**In plain terms:** the AI still fully invents each panelist like before — we
just swap in your chosen name at the last moment before the panel is seated.
Because every part of the app reads the panelist's name from one place, the
custom name automatically shows up everywhere (questions, transcript, report,
export) without touching any of those parts.

## Decision 4 — `difficulty_start` becomes a visible intake control (LOCKED)

The field already exists on `DefenseProfile` (default 2, validated 1–5, v0.3e)
— it has just never been wired to a form control, the same pre-exposure status
`panel_size` had before 0.3a. This decision wires it: `st.select_slider`,
options 1–5, default 2, label **"Starting difficulty"**, caption: *"How hard
the panel opens. It adapts from there based on your answers."*

The caption deliberately names that adaptation exists (already public knowledge
— it's the app's pitch) without exposing the live meter. **The
never-surfaced-mid-session rule is unchanged and untouched:** live
`difficulty_level`, scores, deltas, and gaps stay dev-view only. This control
sets the entry point; it reveals nothing during the session.

This closes the "no exposed difficulty adjuster" half of live-testing finding
2 (recorded in the 0.3d doc). The other half — "sharp even early," the
untested hypothesis that prompts don't differentiate tone between difficulty
1–2 and 3–4 — is *not* addressed here and is explicitly deferred to v0.4c's
probe. Moving the entry point and fixing tone modulation are different
problems needing different evidence; I'm not conflating them.

**In plain terms:** you can now choose how tough the panel starts (1 = gentle,
5 = brutal), where before it always started at 2 with no way to change it. The
panel still adjusts as you go — you just pick the opening intensity. Whether
low-difficulty questions actually *feel* gentler is a separate question we're
testing properly in v0.4, not guessing at here.

## Amendment — 2026-07-20 (same day, post-landing)

Two revisions after seeing the landed slice live; both are mine.

**Decision 1 amended - customization collapsed by default.**
The open row block cluttered the intake screen.
The rows now live in a default-collapsed `st.expander`; the composition preview
stays outside it, always visible, so a collapsed expander still shows the
customized result.

**Decision 3 amended - curated image icons replace emoji as the primary medium.**
Emoji looked off on the cards.
The picker is now fed from `assets/icons/`: I source icon images myself and drop
them in; every file becomes a predetermined choice, and a file named exactly
after an archetype key becomes that archetype's default (see the README in that

This is still not user uploads - that stays parked exactly as before; the
choices are curated by me, bundled with the app.
The emoji set remains as the fallback while the directory is empty and as the
representation in plain-text surfaces (sidebar captions, old exports).
`Panelist.icon` stays a plain string either way (emoji glyph or file stem), so
the schema, the export shape, and the zero-LLM-impact guarantee are all
unchanged.

## Verification notes (Code session, 2026-07-20)

**Decision 1 form-structure flag:** the intake controls do NOT sit inside an
`st.form` - they are plain widgets with a regular `st.button`, so every widget
change already triggers a rerun.
The customization rows therefore track the multiselect reactively with no
restructuring - the smallest-diff path of the two the flag allowed.
Rows use archetype-scoped widget keys, so a slot's entries survive unrelated
reruns and disappear with the slot when it is deselected.

**Decision 3 key check:** the constants block's five keys match the real
`ARCHETYPE_CONFIG` and `PANEL_COMPOSITION` keys exactly - verified against
`prompts/panelist_prompts.py` before committing them.
The icon constants live in `panel.py` (alongside `PANEL_COMPOSITION` and
`DEVILS_ADVOCATE_KEY`) rather than in the prompts module - icons are roster
material, not prompt text, and nothing in them ever reaches an LLM call.

**Implementation detail forced by Decision 5:** `Panelist` is also the
structured-output wire schema (`PanelGeneration` -> `response_schema`), and
`PERSONA_GENERATION_PROMPT` pins that exact JSON shape.
Adding a required `icon` to it would have changed the schema Gemini sees - a
Decision 5 violation.
So the generation schema kept its own three-field model (`GeneratedPanelist`)
and the seated-roster `Panelist` gained the non-optional `icon`; both
`generate_panel` exits (validated and fallback) pass through
`apply_customizations`, which means a user's custom name survives even
persona-generation fallback.
The wire schema and prompt are byte-identical to before.

**Small presentation guard:** the name input's placeholder states that "Dr." is
added automatically, protecting the Day 2 double-Dr. fix without any
name-normalization logic.

**Decision 5 statement:** `PROMPT_VERSION` is unchanged at `"0.3g"`; `git diff`
over `academic_defense_simulator/prompts/` is empty.
Nothing to re-verify under the Day 4 rule.
