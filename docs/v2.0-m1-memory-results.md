# v2.0 M1 - memory results on Render free

Status: automated, waiting for the Render run.
Brief: [`briefs/v2.0-m1-backend-skeleton-brief.md`](briefs/v2.0-m1-backend-skeleton-brief.md).
Hosting spike: [`v2.0-hosting-spike-results.md`](v2.0-hosting-spike-results.md).

This run decides two things: whether the M1 backend fits Render free (512 MB) with the largest PDF I want to accept, and what the final upload limits are.
It also closes the hosting spike's two pending items (OOM restarts across fresh starts, and cold start).

## Gates

I set these on 2026-10-19; the first two carry over from the hosting spike, which Claude proposed and I confirmed.

- Peak RSS (VmHWM) <= 400 MB on every run.
- No process restart during any run (on Render free, a restart mid-ingest is almost always the OOM kill).
- Cold start (first `/health` 200 after a spin-down) <= 90 s.
- DAZSMA (26.43 MB, 224 pages) upload-to-ready <= 120 s.

The verdict is GO only if every run passes every gate.
It is INCONCLUSIVE, not GO, if the runs couldn't measure a gate: no run followed a spin-down gap, or the instance never actually spun down.

## Setup

- Service: Render Blueprint from `render.yaml` (free plan, one uvicorn worker, Python 3.13.7, `MALLOC_ARENA_MAX=2`).
- `render.yaml` on this branch also sets `ADS_DEBUG_MEMORY=1`, `ADS_MAX_UPLOAD_MB=30` and `ADS_MAX_PAGES=250`, for the measurement only; they come out before the branch merges.
- `ADS_DEBUG_MEMORY=1` turns on `GET /debug/memory`: pid, process start time, deployed commit, limits, current RSS, VmHWM, and the last ingest job's stats.

## Protocol

One command from my machine runs everything:

```
python scripts/measure_ingest.py "<largest.pdf>" --base-url https://<svc>.onrender.com
```

It does three runs, 16 minutes apart, so each of runs 2 and 3 starts on a fresh process after a spin-down.
For each run it times the first `/health` 200 (the cold start), reads `/debug/memory`, uploads the PDF, polls until ready or failed, and reads `/debug/memory` again.
A changed pid or start time, or the session going missing (404), marks the run "process restarted, likely OOM".
VmHWM is read from the second `/debug/memory` read, so it covers startup, model load, the upload and the job, in one process.
It also checks that runs 2 and 3 really were fresh processes; if the instance didn't spin down, the cold start and VmHWM for that run aren't what the gates ask for.
At the end it prints the table and the verdict, and rewrites the section below.

## Local reference run (Windows, 2026-10-19) - not the gate

Claude ran the backend locally with the prod-only venv (no torch, sentence-transformers or transformers installed), one uvicorn worker, `ADS_MAX_UPLOAD_MB=30`, `ADS_MAX_PAGES=250`.
Windows working set is not Linux RSS (spike 1 read about 320 MB locally and 495 MB on Render), so these numbers only show the path works.

Startup log:
```
memory at startup rss=62.5MB hwm=62.9MB
memory after runtime imports rss=113.2MB hwm=129.2MB
memory after model load rss=237.6MB hwm=278.2MB load_s=0.66
```

| PDF | MB | pages | chunks | parse_s | embed_s | job_peak_rss | hwm after ingest |
|---|---|---|---|---|---|---|---|
| sample3.pdf | 11.67 | 82 | 49 | 0.27 | 8.09 | 288.2 MB | 370.0 MB |
| DAZSMA documentation | 26.43 | 224 | 92 | 0.40 | 15.85 | 306.2 MB | 370.0 MB |

The high-water mark reached 370 MB during the `sample3.pdf` job, while that job's sampled peak was 288.2 MB.
It isn't the upload path: on a fresh server, uploading and spooling `sample3.pdf` and rejecting it at the page check (`ADS_MAX_PAGES=20`, HTTP 413) left the high-water mark at the after-model-load value, 271.2 MB.
So something inside the job (parsing the 82-page PDF or an embedding pass) peaked for less than the sampler's 20 ms interval; I haven't pinned down which.
That's why the go/no-go reads `hwm`, not `job_peak_rss`.

Embedding ran at about 0.17 s per chunk locally.
Spike 2 measured about 0.6 s per chunk on Render (8.1 s for 14 chunks), so the 92-chunk DAZSMA would take roughly a minute there.
