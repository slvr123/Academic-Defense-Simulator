**Status:** LOCKED — 2026-07-28. Claude proposed the slice and all ten decisions
in our design conversation; I accepted the set the same day and scoped it to a
single Code session.

**Scope:** Browser-native text-to-speech for panelist questions. A deterministic
archetype → voice profile map, one speech component per question with in-iframe
controls, and a global voice toggle defaulting off. Entirely client-side:
zero API calls, zero new Python dependencies, zero prompt-template edits.

**Explicitly not in scope:** speech-to-text. See Decision 1.

**Builds on:** `v0.3d-defense-ui-decisions.md` (question rendering, panelist

**Convention note:** one combined file, decisions + brief together, per the
lean-docs rule. This file is the complete design record for the slice.

**Version-numbering note:** this is `v1.2`, not `v1.1`. It is a feature, so the
`v1.0.x` patch line is wrong for it; and v1.1's scope (retriever interface

## Decision 1 — Output only. Speech-to-text is not in this slice (LOCKED)

The panel speaks. The user still types.

**Why STT is excluded, on complexity and risk rather than cost.** The scoring
pipeline reads the user's answer text. Browser and cheap-model transcription
mangle technical vocabulary — domain terms, acronyms, instrument names,
standards identifiers. Feeding that into the scorer makes `difficulty_delta`
respond to transcription noise stacked on top of a signal whose behaviour is
already unexplained across documents (`case-study.md` §3). That is a new
uncontrolled variable introduced into the one subsystem that currently has an
open research question against it.

**Recorded for whenever STT is revisited, so it isn't re-derived:**

- `st.audio_input` is now a native Streamlit widget returning recorded audio to
  Python. The earlier assumption that STT required a custom bidirectional
  component is **retired** — that was the basis of an earlier cost estimate and
  it no longer holds.
- Server-side Whisper stays dead regardless: torch alongside `sentence-transformers`
  against Streamlit Community Cloud's 690 MB guaranteed floor, with working RSS
  already ~1.17 GB.
- The Gemini API accepts audio input, so transcription is one call through the
  existing provider abstraction. Budget effect: `2T + 1` → `3T + 1`.
- **The mandatory guard, non-negotiable if it is ever built:** the transcript
  lands in an editable text box and the user submits the text. Text stays
  canonical end to end. Scoring never sees audio.
- That guard is also what makes the cheap model acceptable for transcription —
  errors are user-correctable by construction, so transcription is not a
  judgment task in the sense that ruled flash-lite out for the relevance gate.
- Any STT slice routes its audio call through the same RPM gate as every other
  provider call, or the empirically verified ceiling of 13 stops meaning what
  it was verified to mean.

**In plain terms:** the panel talking to me is free and safe. Me talking back
is neither, and the risky half touches the one part of the system I can't yet
explain — so it waits, with the reasoning written down instead of relitigated.

## Decision 2 — Browser `speechSynthesis`, client-side, zero server involvement (LOCKED)

Speech is produced by the visitor's browser. Nothing is synthesised, buffered,
or stored server-side. No audio bytes cross the wire.

Consequences, all of them wanted: no API calls, no quota consumption, no effect
on the ~10-full-sessions-per-day `gemini-2.5-flash` ceiling, no memory cost
against the Community Cloud floor, no new Python dependency, no new failure mode
in the provider layer.

**In plain terms:** the browser already knows how to talk. The app just hands it
the sentence.

## Decision 3 — Voice assignment is a deterministic archetype → profile map in the UI layer (LOCKED)

The map lives beside the existing archetype → avatar map, in the same module.
One archetype key, one lookup, both cosmetic identity fields together.

**Rejected: an LLM-generated `voice_profile` field on the persona schema.**
Three reasons, any one sufficient:

1. It moves `PROMPT_VERSION` for a cosmetic. The three independent prompt-version
   constants exist precisely so unrelated things don't move together; bumping the
   session-generation constant for a UI feature would invalidate the comparability
   of every existing eval artifact.
2. It makes the voice inconsistent across sessions — the Methodology Expert
   would sound different every run, which inverts the entire point of giving a
   persona a voice.
3. Browser voice lists are platform-dependent, so a model-emitted voice name is
   unreliable at runtime anyway. The schema cost buys a value that has to be
   fallen back from.

**This is not a violation of dynamic persona generation.** The archetype key is
itself the output of the dynamic step — panel composition selects archetypes,
and fixed presentation assets hang off the result. The nine avatar images
already establish exactly this pattern; voice is its audio equivalent.

**In plain terms:** the panel is still chosen dynamically. Once someone is on
the panel, their face and their voice are both just files looked up by name.

### Deviation, 2026-07-28 - the map lives in `panel.py`, not the UI layer

**Provenance.** Code hit the conflict during implementation and proposed the
resolution rather than silently picking one side.
I confirmed it on 2026-07-28.

This decision's heading and the Brief's "files expected to change" both say the map
belongs in the UI layer, while the body of this same decision says it lives "beside
the existing archetype → avatar map, in the same module".
Those turned out to conflict, because the avatar map (`ARCHETYPE_DEFAULT_ICONS`) is
not in the UI layer at all: it is in `panel.py`.

**The colocation instruction was followed.**
`VOICE_PROFILES` sits in `panel.py` directly above `ARCHETYPE_DEFAULT_ICONS`, and is
read only by `streamlit_app.py`.

The reasoning, in order of weight:

1. The standing boundary rule is about **imports**, not about which file a constant
   lives in. `VOICE_PROFILES` is inert data that imports nothing and is imported by
   the UI layer. `panel.py` still imports no `streamlit`, verified by grep in the
   DoD.
2. `ARCHETYPE_DEFAULT_ICONS` already established this exact location for exactly
   this class of data, with a comment saying why: icons are roster material, not
   prompt text, and nothing in that block ever reaches an LLM call. Voice is the
   audio equivalent, which is this decision's own argument.
3. The body instruction is the specific one and the heading is the general one, and
   the whole point of the body instruction was one archetype key, one lookup, both
   cosmetic identity fields together. Splitting them across modules would satisfy
   the heading while defeating what the heading was for.

If a future slice moves presentation data out of `panel.py`, both maps move together
or neither does.

## Decision 4 — Profile shape: an ordered `voice_prefs` list plus `pitch` and `rate` (LOCKED)

```python
VoiceProfile = {
    "voice_prefs": [str, ...],  # ordered, first available wins
    "pitch": float,             # 0.0–2.0, browser default 1.0
    "rate": float,              # 0.1–10.0, browser default 1.0
}
```

**Resolution chain, in order:**

1. Call `speechSynthesis.getVoices()`. **If it returns empty, wait for the
   `voiceschanged` event and re-read.** It is routinely empty on first call.
   This is the single most common way a naive implementation ships silent.
2. Walk `voice_prefs` in order; take the first name present in the list.
3. No match → use the browser default voice.
4. **Apply `pitch` and `rate` unconditionally, in every branch including the
   default-voice branch.**

Step 4 is the load-bearing one. A different synthesis voice separates two
panelists far better than the same voice at two pitches, so `voice_prefs` does
the heavy lifting where it resolves — but where it doesn't, pitch and rate are
the degraded fallback that keeps a panel from collapsing into one voice reading
everything.

**In plain terms:** each panelist has a list of preferred voices because I can't
control what's installed on a stranger's machine. Whatever voice they end up
with, the pitch and speed still make them different from the panelist next to
them.

four archetypes actually seated are distinguishable from each other**, not that

## Decision 6 — Assignment is on acoustic separation only, never role-matched (LOCKED)

Voices are assigned to maximise audible distance between archetypes that can be
seated together. They are **not** matched to what the archetype does.

An ethics reviewer that is always female-voiced and a technical reviewer that is
always male-voiced is a stereotype baked into a config file. It reads badly in a
portfolio piece and buys nothing — the separation the feature needs is fully
available without it. Recorded as a design constraint so a later tuning pass
doesn't quietly reintroduce it while chasing "fit."

**In plain terms:** voices get spread out so people sound different, not chosen
to match a stereotype of what a methodology expert or an ethics reviewer sounds
like.

## Decision 7 — Auto-speak on first render, guarded by `sessionStorage`, with in-iframe controls (LOCKED)

A real defense panel does not wait for you to press play. Auto-speak is the
correct default for the simulation. The controls exist as fallback and utility,
not as the primary path.

**The failure this decision exists to prevent:** Streamlit reruns re-render
components. Fire-and-forget `speak()` on render means the question re-speaks on
every rerun. This is the primary bug class in the slice.

**Mechanism, all four parts required:**

1. **`sessionStorage` guard, inside the iframe.** Key on a stable per-question
   identity — `ads-spoken:{session_id}:{turn_index}`. Present → do nothing.
   Absent → set it, then speak. The guard must live in the iframe's own
   `sessionStorage`, not in `st.session_state`; see part 3 for why.
2. **Controls rendered as plain HTML inside the component**, not as Streamlit
   buttons: a play/replay control and a stop control (`speechSynthesis.cancel()`).
   In-iframe clicks cause no Streamlit rerun, so the controls cost nothing in
   state churn — and a click inside the iframe grants that document genuine user
   activation, which is what makes it a real fallback when autoplay policy blocks
   the automatic attempt.
3. **The component is always rendered while voice is on**, never conditionally
   removed after speaking. Streamlit components are sandboxed cross-origin
   iframes, so the script cannot reach `window.parent.speechSynthesis` — the
   utterance belongs to the iframe's own window and dies if the iframe is
   removed. Server-side "only render it once" logic would therefore cut off the
   speech it just started.
4. **The question text is JSON-encoded into the script**, with `</` escaped as
   `<\/`. The text is LLM-generated and will eventually contain a quote, an
   apostrophe, or a bracket sequence that breaks a naively interpolated
   `<script>` block.

**Accepted limitation:** a rerun during playback reloads the iframe and cancels
the in-flight utterance. In practice reruns happen on answer submit, by which
point the question has been heard. Recorded rather than engineered around.

**In plain terms:** the panelist starts talking on their own, like a real
panelist would. A note in the browser's own memory stops them repeating
themselves every time the page refreshes, and there's a play button right there
for when the browser blocks the automatic start or I want to hear it again.

## Decision 8 — One global voice toggle, default off, in the sidebar (LOCKED)

A single control in the case-file sidebar, persisted in `st.session_state`.
Off → the component is never rendered at all.

**Default off, deliberately.** Audio starting unbidden in a shared space or an
office is a bad first impression for a portfolio link, and a meaningful share of
LinkedIn traffic will open the app somewhere audio is unwelcome. Opt-in also
means the entire feature is provably inert for anyone who doesn't want it, which
is what lets it ship without competing for verification effort against the eval
backlog.

**In plain terms:** the app is silent until I turn it on, so nobody gets ambushed
by a talking panel on a train.

## Decision 10 — Accepted limitations, stated here so they're read rather than discovered (LOCKED)

- **Separation degrades to pitch and rate alone** when no preferred voice
  resolves. On a panel of four this is audible but subtle. Accepted.
- **Voice availability is uncontrollable and unstable.** Browsers add and remove
  voices between versions. A profile verified today can silently fall back
  tomorrow. There is no fix short of shipping audio, which Decision 2 rules out.
- **iOS Safari is verified by hand or not at all.** No automated coverage.
- **No test asserts that audio was actually produced.** Tests cover the map, the
  escaping, and the toggle. Whether sound came out is a by-ear DoD item, not a
  test. Stated plainly rather than implied by an absent test.
- **The corrected voice table is environment-specific** (added 2026-07-28 with the
  Decision 5 amendment). It was measured on one browser on one machine: Chrome on
  Windows, 22 installed voices of which six are English. iOS Safari, Edge on
  Windows, and Chrome on Android ship different voice sets, so on those both the
  resolved voice and the collision structure differ from what was measured. Every
  "Google ..." voice is network-only, so resolution can vary run to run on the same
  browser as well. This is recorded as a limitation, not queued as work: verifying
  the table across platforms is explicitly not in scope, and an honest note is the
  correct treatment of a property that cannot be controlled anyway.

## Session-risk note and cut line

This is a small slice by design — one map, one component, one toggle, no
business logic. The risk is not size, it is browser behaviour: `getVoices()`
timing and autoplay policy are the two places where an afternoon disappears.

**Pre-agreed cut line, in order of what gets dropped first:**

1. **DoD item 5's coverage narrows** from five archetypes across two sessions to
   one session and whatever it seats. The remainder is recorded as open, not
   silently dropped.
2. **The stop control** goes. Play/replay does not — it is the autoplay-block
   fallback and cannot be cut.

**Auto-speak, the `sessionStorage` guard, the `voiceschanged` re-read, the
escaping helper, and the completeness test are not cuttable.** Each one is a
visitor-facing defect if absent. If those cannot all close, the session ends
without a push and the remainder becomes v1.2.1 — I do not ship a half-wired
voice path.

Per Decision 0: this slice does not get a second session before the retrieval
eval gets its first.
