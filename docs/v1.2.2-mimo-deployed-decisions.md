## Decision 2 — Provider default is key-presence-driven (LOCKED)

*Sean specified; Sean locked, 2026-07-31.*

`ADS_TTS_PROVIDER` unset now resolves to `mimo` when `MIMO_API_KEY` is
present in the environment, `browser` when it is absent. This replaces
v1.2.1 Decision 3's "unset means browser" for the unset case specifically —
explicit `ADS_TTS_PROVIDER=browser` still always means browser regardless of
key presence, and explicit `ADS_TTS_PROVIDER=mimo` with no key still falls
back to browser (this was already true under v1.2.1 Decision 3's "any other
value... falls back," extended here to cover the valid-value-but-missing-key
case explicitly).

**Key absence must resolve to browser with no failed network call.** This is
a config-resolution-time decision, not a fail-open catch — Decision 6's
fail-open exists for a call that was attempted and failed (network, auth,
quota, timeout, malformed response), not for a call that was never going to
succeed because no key exists to attempt it with. Defaulting to `mimo` and
letting fail-open catch the guaranteed-missing-key failure would work
functionally but burns a doomed request every synthesis attempt for no
reason — this decision closes that off at the source instead.

## Decision 3 — Disclosure gate before first synthesis (RETIRED 2026-07-31,
same day it shipped)

*Sean specified; Sean locked, 2026-07-31.*

Before the first Mimo synthesis attempt in a session, the UI states —
visibly, not in hover-help alone — that question text derived from the
uploaded document is sent to Xiaomi's Mimo API for speech synthesis. Mimo
audio stays off until this is acknowledged. Acknowledgement is **per-session,
not persisted** — `st.session_state` only, same as every other v1.2/v1.2.1
voice control; a new visit or a new session gets the gate again.

This governs the Mimo path only. The browser (Web Speech) voice toggle sends
nothing anywhere and needs no disclosure — v1.2.1 Decision 1 already covers
that distinction and it is unchanged here.

**RETIRED 2026-07-31 (Sean specified; Sean locked) — reason, stated as
given:** "for now I want the default voice to be the mimo one." The
disclosure caption and the separate opt-in toggle were both removed the same
session they shipped; Mimo now fires automatically whenever it resolves as
the provider (Decision 2), gated only by the existing "Panel speaks
questions" toggle, same as the browser path always was.

**Consequence worth recording, not a reason to reverse the decision, since
Sean made this call with the information in hand:** the disclosure toggle's
click was the one reliable gesture in the Mimo flow. Task 6's evidence
(`evidence/v1.2.2-autoplay-verification.txt`) showed a fresh visitor's
browser blocks `st.audio` autoplay without a prior gesture, and a gesture
elsewhere on the page doesn't reliably carry forward to a later-rendered
player. With the toggle gone, a first-time visitor may see the audio player
sitting unplayed with nothing explaining why — recoverable only if they
notice and click the native play control themselves (confirmed reliable in
the same evidence file), same worst case as the browser path already has.

## Decision 4 — Latency and autoplay must be re-verified against the deployed
path, not assumed from local numbers (LOCKED)

*Sean specified; Sean locked, 2026-07-31.*

v1.2.1's Decision 0c latency figures (`evidence/v1.2.1-latency.txt`, median
6.160330749997229s) were measured from Sean's own machine and connection to
Xiaomi's API — Streamlit Community Cloud's network path to the same API is a
different round trip and the number does not transfer. Ten timed synthesis
calls from the deployed environment, min/median/max, go in `evidence/` once
the key is live there.

Separately: `st.audio`'s `autoplay` attribute is subject to ordinary browser
autoplay policy, which is not the same mechanism v1.2's Web Speech path
handles (that path's Replay button exists specifically because
`speechSynthesis` autoplay can also be blocked without a prior gesture — see
`docs/v1.2-panelist-voice-decisions.md` Decision 7 part 2). Whether
`st.audio(autoplay=True)` actually plays without a prior user gesture must be
verified, not assumed inherited from the Web Speech precedent; if it does
not, playback is gated behind an explicit control the same way the browser
path already is.

**Outcome, 2026-07-31.** Latency: **blocked.** Measuring the deployed path
needs `MIMO_API_KEY` live in Streamlit Cloud secrets and a deployment, and I
was told to do neither — Sean adds the key himself, and deploying needs its
own separate authorization. `evidence/v1.2.2-autoplay-verification.txt` has
the ten-run harness ready to run the moment both exist; nothing else blocks
it.

Autoplay: **verified, real browser, two ports** — one previously used by this
profile (contaminated: autoplayed with zero clicks, not representative of a
first-time visitor) and one never before visited (clean: `st.audio(autoplay
=True)` did not even load without a click, and a real click elsewhere on the
page did not reliably unblock a later-rendered player either). The native
play control did work reliably when clicked directly. `_render_voice_
component` never suppresses `st.audio`'s default `controls`, so that fallback
was already present — this decision closes by confirming the existing
default is the correct gate, not by adding a new one. Full detail:
`evidence/v1.2.2-autoplay-verification.txt`.
