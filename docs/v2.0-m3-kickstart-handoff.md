## The API M3 builds against

Source of truth: `backend/schemas.py`, decisions in [`v2.0-m2-defense-api-decisions.md`](v2.0-m2-defense-api-decisions.md).

| Call | Purpose | Notes |
|---|---|---|
| `GET /health` | Liveness, `model_loaded` | Use it to wake a spun-down instance |
| `GET /quota` | `used`, `cap`, `remaining`, `resets_at` | Cap is 11 defenses a day; 503 if Neon unreachable |
| `POST /sessions` | Multipart: `file` (PDF) + `panel` (JSON `PanelConfig`) | 202 with `session_id`, `queue_position`. 30 MB / 250 pages max |
| `GET /sessions/{id}` | Poll: `queued` / `embedding` (`progress`) / `ready` / `failed` | `defense`: `not_started` / `in_progress` / `done` once ready |
| `POST /sessions/{id}/start` | Panel + first question | ~30 s (three Gemini calls). Safe to call again if the first question failed |
| `POST /sessions/{id}/answers` | `{text}` -> `evaluation`, `next_question` or `done` | A turn happens completely or not at all |
| `GET /sessions/{id}/report` | v1's `DefenseReport` + full transcript with sources | |
| `DELETE /sessions/{id}` | Drop a session | |

Things the UI has to own because the API doesn't:

- **Every question carries `sources[]`** (chunk text, 1-based `page_start`/`page_end`, `score`, `origin`). That's the source-passage reveal, already served.
- **Scores are on v1's 1-5 scale.** Rescaling to 100 for display (v1.2.1) is the UI's job; reuse v1's formula exactly.
- **`PanelistOut.name` is the surname only**; the client adds "Dr.". `icon` is a name (`professor`, `hacker`, ...) matching PNGs in `academic_defense_simulator/assets/icons/`.
- **Error contract:** 503 busy with `Retry-After` (Gemini 429/503, never "done for today"), 409 a request already running for this session, 502 turn failed and nothing recorded (resend the same answer), 429 per-IP start limit (3 a day) with `Retry-After` to midnight Pacific, 422 validation (including "document too short for this panel"), 404 session gone.

## To lock in chat before Code (Claude's proposals)

**1. Repo layout.** `frontend/` in this repo: Vite + React + TypeScript.
Downside: the backend's `render.yaml` build filter has to ignore `frontend/**`, and the static site needs its own filter, or every frontend commit redeploys the backend.

**2. CORS on the backend.** There is no `CORSMiddleware` in `backend/app.py` today, so every browser call from the static site's origin will fail. Add it with an explicit allowlist from an env var (`ADS_CORS_ORIGINS`: the static site URL plus `http://localhost:5173`), never `*`.
Downside: a backend change inside a frontend milestone, and a new env var to keep in sync when the static site URL changes.

**3. API types generated from FastAPI's OpenAPI schema** (`openapi-typescript` against `/openapi.json`) instead of hand-written TypeScript copies of `schemas.py`. Pydantic stays the one contract; drift shows up as a type error.
Downside: generated types are harder to read while learning TypeScript, and there's a regen step to remember after any schema change.

**4. No state or data libraries at first.** Plain `fetch` in one typed API client module, and the defense flow as a single `useReducer` state machine (a discriminated union of phases: waking, uploading, queued, embedding, preparing, question, submitting, report, error). No Redux, no React Query.
Downside: I write the polling and retry logic by hand, which React Query would give for free. The upside is that I learn what those libraries actually do.

**5. Styling: Tailwind. Framer Motion deferred.** The stack-swap entry lists Vite, Tailwind and Framer Motion; M3 uses CSS transitions only.
Downside: the "distinct panel presence" motion I want comes later, so M3's first deploy looks plainer than the vision.

**6. No real streaming in M3.** The backend has no SSE endpoint, so the question reveal is client-side (typewriter over the full question text). Real SSE is a later backend milestone.
Downside: it isn't streaming, so the README and case study must not call it streaming.

**7. Keep the instance awake during a defense.** Render free spins down after 15 idle minutes and sessions live in memory, so a user who thinks for 15 minutes with no other traffic loses the whole defense. That's earlier than the 30-minute session TTL. Proposal: while a defense is open, the client pings `/health` every few minutes; when it isn't, no pings.
Downside: it uses Render free-tier instance hours while tabs are open, and it hides the problem rather than fixing it (persistence would).

**8. Avatars served by the static site.** Copy the icon PNGs into `frontend/public/icons/` rather than serving them from the backend.
Downside: two copies of the icons; needs a check that every icon name the backend can send has a file.

**9. Voice (MiMo TTS) is its own milestone after M3's core loop works.** It needs a backend `POST /tts` (the MiMo key never reaches the browser), the browser `speechSynthesis` fallback in React, the empty-audio fix below, and the disclosure gate ported (document text reaches MiMo inside questions).
Downside: M3's first deploy has no voice, and voice is what makes the app feel real.

**10. M3 scope = one vertical slice.** Upload with panel config, quota display, every wait state, the full answer loop with the source-passage reveal after each answer, and a basic report with the transcript. The debrief-style report rebuild, motion, and voice come after.
Downside: the first M3 deploy is functional rather than impressive, so it shouldn't be the one I post about.
