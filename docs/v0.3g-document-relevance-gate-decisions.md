# v0.3g — Document Relevance Gate

I decided this slice was small enough that its design could live in the execution
brief itself instead of a separate decisions doc.
Claude proposed the design during our chat sessions around the post-deploy
bugfixes; I confirmed it on 2026-07-18.
Recording the brief text here now, verbatim, so the design record actually lives in
the repo rather than only in chat history.

## Design context

- **What:** a document relevance gate at ingestion.
  One structured-output LLM call assesses whether the uploaded document is
  plausible defense material.
  If not, the user sees a warning but can proceed anyway.
- **Soft gate, not hard block.** The "Other" defense type deliberately covers
  unusual documents (grant defenses, scholarship panels, certification material).
  A hard block will eventually false-positive on a legitimate document.
  The app raises an eyebrow; it doesn't slam the door.
- **Model: `gemini-2.5-flash`, not flash-lite.** This is a judgment task and
  flash-lite is already on record as unfit for judgment tasks (inverted
  difficulty_delta, inflated clarity scores).
  One call per upload — RPD cost is negligible.
- **Runs after chunking, before embedding.** Needs chunks to sample; no reason to
  spend embedding time on a document the user may abandon at the warning.
- **Sampling:** first 2–3 chunks plus 1–2 from the document's middle.
  First-pages-only gets fooled by cover letters and templated front matter.
- **Lives in business logic, not `streamlit_app.py`.** The gate function returns
  the assessment; the UI decides how to render it.
  No Streamlit imports in the gate module.
  Testable with a mocked LLM response.
- **`PROMPT_VERSION` is NOT bumped.** It stamps defense-session exports; the
  gate's prompt is outside that surface.
  (Coincidence note: current PROMPT_VERSION is 0.3g from the acknowledgment fix —
  unrelated axis, leave it alone.)

In plain terms: before the app spends time and API budget building a defense
panel around a document, it takes one quick look and asks "is this actually
something someone would defend?"
If the answer is no, it tells the user what it thinks the document is and why a
session against it won't be meaningful — but the user always gets the final say.

## Schema

```python
class DocumentAssessment(BaseModel):
    is_defense_material: bool
    document_kind: str   # e.g. "research paper", "resume", "invoice", "novel excerpt"
    reason: str          # one sentence, user-facing on rejection
```

## What got built

- `assess_document(chunks, provider) -> DocumentAssessment` in
  `academic_defense_simulator/document_relevance.py`.
- `DocumentAssessment` in `academic_defense_simulator/models/document_assessment.py`.
- `RELEVANCE_PROMPT` in `academic_defense_simulator/prompts/relevance_prompts.py`.
- Wired into `_ingest_and_extract` in `streamlit_app.py`: gate runs after
  `chunk_pdf`, before `_load_embedding_model`/encode.
  A rejection stores the assessment in `st.session_state.relevance_warning` and
  returns without setting `document_id`; the intake UI renders the warning and a
  "Proceed anyway" button, which re-calls `_ingest_and_extract` with
  `skip_relevance_check=True`.
- Fail-open on any `LLMProviderError`: logged, treated as
  `is_defense_material=True`.
- `tests/test_document_relevance.py`: 7 tests against a mocked provider —
  rejection path, pass path, fail-open, short/single-chunk sampling, sample
  head+middle selection.

## Implementation deviations from the brief's literal text

Claude flagged two places where the brief's literal signature conflicted with
its own stated design intent, and resolved both in favor of the stated intent
plus the codebase's existing pattern, rather than stopping the whole brief over
what read as drafting-level imprecision.
I have not separately reviewed these two calls beyond this record; noting them
here is what "commit nothing new unless an item fails" surfaced needing.

1. **Chunk type.** The brief's schema line read
   `assess_document(chunks: list[Chunk], ...) -> DocumentAssessment`, but
   `Chunk` (in `rag/retrieval.py`) carries an embedding, and the brief's own
   design context says the gate "runs after chunking, before embedding" — those
   two statements can't both be literally true.
   Claude used `list[str]` (raw chunk text, what `chunk_pdf` actually returns
   pre-embedding), matching the stated intent.
2. **Provider construction.** The brief implied the gate function would
   construct its own `gemini-2.5-flash` provider internally.
   Claude instead had `assess_document` take `provider: LLMProvider` as a
   parameter — the same shape as `document_profile.py`'s
   `extract_document_profile` — and pinned the model at the call site in
   `streamlit_app.py` (`_new_relevance_provider()`).
   Keeps the gate provider-agnostic and testable with the existing stub-provider
   pattern instead of hardcoding a concrete provider class into business logic.

## Bugs found and fixed during implementation (not part of the original brief)

1. **Missing rerun on rejection.** The first pass set
   `st.session_state.relevance_warning` on a negative assessment but never
   called `st.rerun()`.
   `intake_slot.container()` (which reads that state) had already rendered
   earlier in the same script pass, so the warning silently never reached the
   browser — same transitional-window class of issue the codebase already
   documents for the success path.
   Fixed by rerunning whenever either `document_id` or `relevance_warning` gets
   set.
2. **Sidebar overlap.** Found live while testing the intake flow, not
   introduced by this brief: the prior "sidebar toggle no longer shifts main
   content" fix centers `.stMainBlockContainer` against the full viewport, which
   on any realistic screen width puts its left edge underneath the now-fixed-
   position sidebar's 300px width.
   The intake screen's "Process document" and "Proceed anyway" buttons were
   physically unclickable without collapsing the sidebar first.
   Fixed by clamping the container's left margin to
   `max(300px, natural centering offset)`, which only changes anything below
   the ~2100px viewport-width threshold; verified clear at 1024/1280/1440/1920px
   and confirmed the no-shift-on-toggle invariant still holds.
