## Decision 1 — Schema: direct selection replaces a count (LOCKED)

`DefenseProfile.panel_size: int` is retired. Replaced with:

```python
class DefenseProfile(BaseModel):
    defense_type: DefenseType
    other_subtype: Optional[OtherSubtype] = None
    domain: str = Field(..., min_length=1)
    topic: str = Field(..., min_length=1)
    selected_archetypes: list[str] = Field(..., min_length=1, max_length=3)
    difficulty_start: int = Field(default=2, ge=1, le=5)
    document_id: str

    @model_validator(mode="after")
    def check_selected_archetypes(self):
        key = _composition_key(self.defense_type, self.other_subtype)
        allowed = set(PANEL_COMPOSITION[key])
        chosen = set(self.selected_archetypes)
        if not chosen.issubset(allowed):
            raise ValueError(
                f"selected_archetypes contains keys not valid for '{key}': "
                f"{chosen - allowed}"
            )
        if len(chosen) != len(self.selected_archetypes):
            raise ValueError("selected_archetypes contains duplicates")
        return self
```

No migration path needed — nothing is deployed yet, no real exported
transcripts exist to preserve compatibility with. This is a breaking schema
change made freely because there's no live data it could break.

**In plain terms:** instead of telling the app "I want 3 panelists" and letting
it pick which 3 from a fixed priority order, you tell it exactly which 3. The
schema just stores your literal picks now, not a number.

## Decision 2 — Selectable set stays scoped per defense type (LOCKED)

`PANEL_COMPOSITION`'s existing lists are unchanged — still the source of truth
for *which* archetypes are relevant to a given defense type, and in what
priority order. What changes is that the user picks a subset of that
type-appropriate list, not a `count` truncating it. A capstone defense still
only offers capstone-relevant archetypes; an oral-comps defense still only
offers its three.

---

## Decision 3 — Cap: 3 domain selections, uniform across every defense type (LOCKED)

Max 3, min 1, for every `defense_type`/`other_subtype` combination. This
changes thesis/capstone (previously allowed 4 domain archetypes, 5 total with
DA) down to 3 (4 total). `other/*` subtypes were already capped at 3 domain
archetypes (4 total) — unaffected.

**Consequence, confirmed deliberate:** every defense type now has the same
total ceiling — 4 panelists, always. This directly feeds `v0.3f`'s `T_max`,
which becomes one clean number instead of two asymmetric ones.

## Decision 4 — Natural order governs speaking order, not click order (LOCKED)

Confirmed by Sean. `compose_panel` changes from truncation to filtering:

```python
def compose_panel(profile: DefenseProfile) -> list[str]:
    """Return the user's selected archetype keys, in PANEL_COMPOSITION's
    priority order for this defense type — not click order. Validation
    (subset check, max 3, no duplicates) already happened at the schema level
    (DefenseProfile.check_selected_archetypes); this function trusts it and
    does not re-check."""
    key = _composition_key(profile)
    roster = PANEL_COMPOSITION[key]
    return [a for a in roster if a in profile.selected_archetypes]
```

The old `ValueError` for exceeding the composition list's length is retired —
that check now lives entirely in the schema validator (Decision 1), not
duplicated here. One place validates; this function trusts it.

**In plain terms:** if a capstone panel's natural order is Technical →
Methodology → Ethics → Literature, and you pick Ethics and Technical, they
still speak Technical-then-Ethics — the order that reflects "capstones get
grilled on what was built first," not whichever order you happened to click
them in.

## Decision 5 — Devil's Advocate is never selectable (LOCKED)

Confirmed. DA never appears in the selectable set — the UI's picker only ever
lists domain archetypes from `PANEL_COMPOSITION[key]`, which has never included
DA (unchanged since 0.3a). `compose_full_roster = compose_panel(profile) +
[DEVILS_ADVOCATE_KEY]` is unchanged from 0.3b — DA remains the unconditional,
always-present 4th, appended after the user's picks, never one of them.

## Decision 6 — UI: multiselect + live composition preview (LOCKED)

The intake screen's `panel_size` `st.number_input` is replaced with a
multiselect populated from `PANEL_COMPOSITION[_composition_key(...)]`, showing
archetype titles (Title Case, from `ARCHETYPE_CONFIG`) as the options.

**Implementation note, not yet confirmed against the Streamlit API:** if
`st.multiselect` doesn't natively support a max-selection count, validate
manually — same pattern as the existing domain/topic empty-field check
(`st.error()`, no `st.rerun()`, form stays in place to correct). Confirm the
actual API before assuming either way.

The 0.3d composition-preview row (currently showing a priority-truncated slice
with placeholder names) now renders the user's actual live selections, still in
natural order (Decision 4), still with "Assigned at convene" placeholders since
real names still don't exist until the persona-generation call fires.
