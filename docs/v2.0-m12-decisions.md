### The measurement (decision rule written before the data)

Speaker order is not chunk order. A panelist's question comes from whatever its focus query retrieves, so the ordering may not be enough. We measure it.

- **Sample.** 10 sessions:
  - 5 on the AniCheck sample, 5 on a second document from the existing eval set;
  - thesis defense type;
  - a panel that includes `problem_objectives_reviewer`.

  Only the opening round is generated. No answers are needed.
- **Chapter map.** The eval script builds a page-to-chapter map from the PDF's "CHAPTER n" headings. AniCheck's start on pages it can detect. This is eval-only code, not product code. Pages before Chapter 1 count as chapter 0. If the second document has no detectable chapter headings, use a different eval document and say which.
- **Definition.** An opening round **passes** if its cited chapters never go backwards. 1→2→3 passes, 1→3→3 passes, 3→1→3 fails.
- **Rule.**
  - **≥ 8 of 10 rounds pass:** ship the ordering.
  - **< 8 of 10:** still ship the ordering, because it's harmless and it's what a real panel does. Record the number honestly in the results doc, and park a chapter-biased retrieval filter as M14 (same pattern as M9 routing). M12 doesn't attempt the filter.
- **Spend.** Pre-authorized: up to 10 measurement sessions, opening round only, on `gemini-3.1-flash-lite`. On a 503 streak, wait and resume. Never switch models.
- **Evidence.** A table with one row per session: document, speaking order, cited page and chapter per question, pass/fail. No passage text in committed files.

## Decision 3 — Remove every glow

What reads as "AI-generated" is the soft glow, not any one color.
- Remove glow-style `box-shadow`, `text-shadow`, `drop-shadow` filters and blur halos from accent elements, cards, buttons and the speaking badge.
- The active or speaking state becomes a **1px solid accent border** with no shadow.
- Functional focus rings stay. They're accessibility, not decoration.
- GSAP choreography stays. Only glow properties inside tweens are removed. **M11.1 lesson:** anything that must end visible gets an explicit end state.

## Decision 5 — Free-tier cold starts

Render's free web services spin down after 15 minutes without traffic and take about a minute to wake. A recruiter clicking the LinkedIn link must not meet a dead page.

**In code (M12):**
1. **Verify, with network evidence,** that the recorded demo makes **zero backend calls.** If it makes any, report them (STOP POINT B) before changing anything. The demo has to work while the backend sleeps.
2. **Pre-wake.** On app load, the frontend fires one non-blocking `GET /status`. No UI waits on it.
3. **An honest waking state.** If a backend request has not answered within 3 s, show: "Waking the panel — free hosting sleeps when idle. This can take up to a minute." Make it calm, with no spinner glow.
4. **Report what `/status` does.** It must not touch Neon. If it does, report it (STOP POINT C), because a keep-alive that also wakes the database burns Neon compute for nothing.
5. **Report from `render.yaml`** whether the frontend is a static site or a web service. This decides the hours math below.

**Outside code (Sean, manual):** an external keep-alive pinger hits `https://ads-backend-bv63.onrender.com/status` **every 10 minutes from 06:00 to 24:00 PH time.**
- **Hours math:** 18 h × 31 days = 558 h, against the 750 free hours each workspace gets per month.
- The pinger is set up after M12 deploys, so the pre-wake and the waking state are tested against a genuinely cold service first.

**Downsides accepted:**
- The pinger uses about 75% of the workspace's free hours. Running out suspends **all** free web services in the workspace until the month ends. Any other free Render web service on the same account would push that over.
- Overnight PH visitors still get a cold start, which the waking state covers.
