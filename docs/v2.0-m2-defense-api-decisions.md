# v2.0 M2 - defense API and daily Gemini quota guard: decisions

## Context

M2 puts a full defense behind the API: start, answer, score, report, all guarded by a durable daily quota so the public demo can't run the Gemini free tier dry.
The brief is in my M2 message of 2026-10-19; this file records the decisions made while building it.
Two of them override the brief, and I've marked those where they come up.

## 1. Two Gemini models, as in v1

The defense model (`ADS_GEMINI_MODEL`, default `gemini-3.1-flash-lite`) does extraction, persona generation, questions, scoring and the report narrative.
Answer suggestions run on `ADS_GEMINI_SUGGESTIONS_MODEL`, default `gemini-2.5-flash`, the model v1 pins them to.

**Overrides the brief**, which defaulted everything to `gemini-2.5-flash`.
At 20 requests a day that model can't carry one worst-case session of 41 calls, so the cap would have been 0.
Claude flagged this while counting the calls on 2026-10-19; I confirmed the v1 split the same day.
Docs call it "the defense model (`ADS_GEMINI_MODEL`)", not "the main model".

## 2. The daily cap is per model, from v1's own call budget

`academic_defense_simulator/call_budget.py` counts a session's worst-case calls per call role, from the loop bounds already in the engine and panel code, and sums them per model.
A full panel (three domain panelists plus the Devil's Advocate) comes to 40 calls on the defense model and 1 on the suggestions model.

The cap is the smallest of floor(RPD / worst-case calls on that model) across the models in use, less `ADS_QUOTA_MARGIN` (default 1).
**Overrides the brief's** single `ADS_GEMINI_RPD`: `ADS_GEMINI_LIMITS` holds an RPD and RPM per model instead, because the two models have separate quotas.
Startup logs each model's share and which one binds.

The defaults are my project's free tier as AI Studio showed it on 2026-10-20:

| Model | RPM | TPM | RPD | Sessions a day |
|---|---|---|---|---|
| `gemini-3.1-flash-lite` | 15 | 250K | 500 | 12 (40 calls each) |
| `gemini-2.5-flash` | 5 | 250K | 20 | 20 (1 call each) |

Flash-lite binds, so the cap is 12 - 1 = 11 defenses a day.
TPM is recorded but not enforced; a defense's prompts come nowhere near 250K tokens a minute.

v1's per-minute limiter now takes the configured RPM less 2 per provider: 13 for flash-lite, the value v1 verified clean against its 15 RPM, and 3 for 2.5-flash, which is unverified.
Without the setting, v1 keeps its own table unchanged.

## 3. Every Gemini 429 or 503 means "busy", never "done for today"

Decided 2026-10-20.

When a Gemini call fails with a 429 (any quota) or a 503 UNAVAILABLE that survives the provider's one retry, the request answers 503 "The panel is busy right now. Please try again in a minute.", with `Retry-After: 60`.
The turn isn't recorded and `daily_usage` isn't touched.
Only the backend's own quota counter closes a day.

**Overrides the brief**, which mapped a Gemini rate limit to "demo quota exhausted for today".
Claude's earlier proposal was to tell per-minute and per-day 429s apart and close the day on a per-day one.
I captured one of each with `scripts/capture_429.py` and then decided not to classify them at all.
The limiter and the session cap already make both kinds rare, and closing the day by mistake would take the demo down until midnight Pacific, while calling a real daily exhaustion "busy" costs only a few failed retries.

The trade-off I'm accepting: if the daily quota is ever genuinely exhausted (for example, the same key used elsewhere), users see "busy" until midnight Pacific instead of a clear "done for today".
If that ever becomes a real problem, the two captures are what a classifier would be built from.
They are in `backend/tests/fixtures/gemini_429/`, and they differ exactly where a classifier would look: `QuotaFailure.violations[].quotaId` is `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` in one and `GenerateRequestsPerDayPerProjectPerModel-FreeTier` in the other, and `RetryInfo.retryDelay` is 46 s against 8462 s.

The v1 provider raises `LLMQuotaExhaustedError` for a 429 and `LLMServiceUnavailableError` for a 503 that survives the retry.
Both subclass `LLMProviderError`, keep v1's messages, and change nothing for v1's own callers.

## 4. A second upload while one embeds needs no change

Measured on Render on 2026-10-20: GO, peak VmHWM 333.8 MB with the two overlapping, inside M1's single-upload range.
Details in [`v2.0-m2-concurrency-results.md`](v2.0-m2-concurrency-results.md).

## 5. Panel config and sources

The upload's `panel` field now carries `defense_type` (default `thesis`), `other_subtype` (required for "other", and only then), optional `domain` and `topic`, `archetype_keys` and `starting_difficulty`.
Chosen panelists must be on v1's `PANEL_COMPOSITION` list for that defense type, three at most.
Leaving them out gives the top three of the recommended list, which is v1's "Use recommended panel".
`devils_advocate` can't be chosen: v1 always adds it last.
M1 had accepted it, which was a mistake.

Every question carries `sources[]` with one entry, since v1 retrieves the top 1.
Each entry has the chunk text, `page_start` and `page_end`, `score` and `origin`.
Pages are 1-based, as a PDF viewer numbers them; I confirmed this on 2026-10-20.
`score` is the cosine similarity v1's `retrieve()` ranked by, computed from the query vector the backend's encoder kept, so there's no second embedding.
A follow-up stays on the previous chunk and the Devil's Advocate contests an earlier one, so neither retrieves; their source carries the score from that chunk's first retrieval, and `origin` (`new_topic`, `follow_up`, `devils_advocate`) says which kind of turn it was.
v1's engine now takes a `TextEncoder` Protocol instead of the sentence-transformers class in its type hints, so the backend's ONNX encoder type-checks; I confirmed this on 2026-10-20.

## 6. Missing domain and topic are read from the document

If the client sends no domain or topic, `/start` runs v1's extraction call, after the quota is reserved; it's already in the call budget.
v1's extraction never fails a session; it returns blank fields.
In that case the domain becomes "unspecified" and the topic becomes the PDF's filename without its extension, so `/start` never fails after spending a reservation.

## 7. A turn happens completely or not at all

`POST /answers` scores the answer, records it, and then either asks the next question or builds the report, all on a copy of the defense.
The copy replaces the defense only if every Gemini call succeeded.
If any call fails, the answer isn't recorded, and the client sends the same answer again.
The cost is that a turn whose next question failed scores the answer again on the retry: one extra Gemini call, which the margin covers.
The alternative, recording the score and then failing to ask, would leave a defense with no pending question and no clean way for the client to continue.

The last answer's request makes three Gemini calls (score, narrative, suggestions) and builds the report; `GET /report` returns the stored report with the full transcript, including each turn's sources.
Scores in the API stay on v1's 1-5 scale; v1.2.1 rescales to 100 for display only, so that's the UI's job.

## 8. Starting a defense

`/start` refuses with 422, before reserving, when the document has fewer chunks than there are domain panelists, because each of them must open a topic of their own.
It then reserves one slot for today, and fails closed (503) if the quota store can't be reached, while the upload's check fails open, as in item 2.
Extraction and persona generation follow; both fall back instead of failing.
If the first question then fails, the defense stays set up with no question pending, and calling `/start` again asks it without a second reservation or a second persona call.

## 9. One request per session at a time

Each session has a lock that a defense request takes without waiting.
A second request for the same session while one is running gets 409 instead of queueing behind it, so a double-clicked submit can't score the same answer twice.

## 10. Other Gemini failures

A Gemini failure that isn't busy (malformed output or a timeout after the provider's own retry, or another API error) returns 502 "The panel hit a problem with that turn. Nothing was recorded; send the same request again.", with nothing recorded, as in item 7.
The narrative and suggestions calls keep v1's fallbacks: if either fails, even with a 429, the report ships without it and says so in `narrative_fallback_used` or `suggestions_fallback_used`.

## 11. Secrets and startup

The server refuses to start without `DATABASE_URL` or `GEMINI_API_KEY`.
Both are `SecretStr` settings, so they never appear in a repr, a log line or a settings dump, and a test checks that the key isn't in the log, the settings or the providers.
Each defense gets its own pair of providers with a call counter, and the backend logs that defense's total calls when it finishes; the key goes only to Google's client.

## 12. The per-IP limit, and which X-Forwarded-For entry I trust

Each client IP gets three defense starts per Pacific day (`ADS_PER_IP_DAILY_STARTS`), counted in memory, so a restart resets them.
That's a speed bump for one person refreshing, not a security boundary; the daily quota in Postgres is the real guard.
The IP check comes before the quota reservation, and a start the quota then refuses (used up, or the store unreachable) is given back to the IP.
The 429 says the network has used its starts, with `Retry-After` to midnight Pacific.

Behind Render, the TCP peer is Render's proxy, so the client has to come from `X-Forwarded-For`.
That header is a list the client can start: whatever it sends arrives first, and each proxy appends the address it received the connection from.
So I trust only the entry `ADS_TRUSTED_PROXY_HOPS` from the right, default 3: the address Cloudflare saw, followed by the two entries Cloudflare and Render's internal proxy appended.
Everything to its left is the client's own claim and is ignored, so sending a fake header doesn't buy more starts.
If there are fewer entries than trusted hops, or the entry isn't an IP address, the TCP peer is used, and a header with fewer entries than trusted hops logs a warning.

uvicorn runs with `--no-proxy-headers`, so `request.client` is always the TCP peer and `backend/client_ip.py` is the only code that reads the header.
I checked this locally: without the flag, uvicorn rewrote the peer from a forged header sent from 127.0.0.1 (its default trusted address); with it, the peer stayed 127.0.0.1.
Claude's earlier note that uvicorn 0.54 takes the leftmost entry was wrong: it took the rightmost one in that check.
It doesn't matter for the design, since uvicorn no longer interprets the header at all.

`GET /debug/client` exists only while `ADS_DEBUG_CLIENT=1`, and it shows the peer, every header entry and the resolved IP.

**The live check on 2026-10-20 proved the first default wrong.**
I built this first with one trusted hop, assuming Render's own proxy was the only one in front of the service.
With that, the resolved IP was Render's internal proxy, so every visitor would have shared one per-IP bucket.
Render's chain is client, then Cloudflare, then Render's internal proxy.
With a spoofed header, the list had four entries: my spoof, my real IP (matching ipify), a Cloudflare address, a Render internal address.
With `ADS_TRUSTED_PROXY_HOPS=3`, two checks both resolved to my real IP; the Cloudflare and internal addresses changed between the checks, but the count stayed the same.
3 is now the code default.

A browser sends no `X-Forwarded-For` of its own, so its requests arrive with exactly three entries, and the warning fires below three, not below four.
I had asked for "fewer than hops + 1", counting the spoofed entry from my check.
Claude pointed out that this would warn on nearly every real request, which carries exactly three entries.
I couldn't recheck an unspoofed request live because `/debug/client` was already off, so this rests on how the chain appends, not on a measurement.

The risk: the limit depends on Render's chain length, which Render doesn't document and could change.
If the chain gets one hop shorter, ordinary requests fall below three entries: the warning fires on every start, and everyone shares the peer's bucket.
Worse, a client that sends a spoofed entry would then have it land in the trusted position.
If the chain gets one hop longer, the resolved IP becomes a Cloudflare address, so visitors share Cloudflare's few addresses, and nothing warns.
Either way the damage is limited to the per-IP speed bump; the daily quota still holds.
After any Render or Cloudflare change, I rerun the spoof check with `ADS_DEBUG_CLIENT=1`.

## 13. The end-to-end check

`scripts/e2e_defense.py` runs one whole defense against a running backend and writes the transcript, timings, quota before and after, and (with `ADS_DEBUG_MEMORY=1`) RSS and VmHWM around `/start` and the last answer.
By default it builds each answer from the question's own source passage, so a run needs no typing; `--interactive` lets me type the answers.
It waits out a busy 503 using `Retry-After`, up to three times, and retries `GET /quota` after 3 s on a 503.
The setup log line reports the engine's chunk copy in MB (`chunk_copy_mb`); a synthetic 92 x 384 document measures 1.09 MB, so five live defenses hold about 5.5 MB of copies.
A local run against Neon spends a real slot in `public.daily_usage` for that Pacific day, the same counter production will use.

## 14. Dead pooled connections are replaced, not reported

Neon suspends its compute after 5 idle minutes, which leaves the pool's open connections dead without the pool knowing.
The first live end-to-end run hit this: `GET /quota` returned 503 "waking up", and a rerun seconds later worked.
Left alone, the first visitor after any lull would have seen that 503, and `/start`, which fails closed, would have refused them.

The pool now checks each connection when it's checked out (`psycopg_pool`'s `check_connection`), and a dead one is discarded and replaced before the request uses it.
The check is one round trip per request that touches the quota, which is negligible next to a defense's Gemini calls.
I reproduced the failure against Neon by shutting down a pooled connection's socket under libpq: without the check, the next read raised the same error the live run hit; with it, the read succeeded on a fresh connection.
A database test does the same, and it fails when the check is removed.
The check doesn't cover a connection that dies between the check and the query; that window is milliseconds, and `/quota` and the upload check stay retry-safe.
