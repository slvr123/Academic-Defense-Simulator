# v2.0 M2 - defense API and daily Gemini quota guard: decisions

## Context

M2 puts a full defense behind the API: start, answer, score, report, all guarded by a durable daily quota so the public demo can't run the Gemini free tier dry.
The brief is in my M2 message of 2026-10-19; this file records the decisions made while building it.
Two of them override the brief, and I've marked those where they come up.

## 1. Two Gemini models, as in v1

The defense model (`ADS_GEMINI_MODEL`, default `gemini-3.1-flash-lite`) does extraction, persona generation, questions, scoring and the report narrative.
Answer suggestions run on `ADS_GEMINI_SUGGESTIONS_MODEL`, default `gemini-2.5-flash`, the model v1 pins them to.

**Overrides the brief**, which defaulted everything to `gemini-2.5-flash`.
At 20 requests a day that model can't carry one worst-case session of 41 calls, so the cap would have been 0.
Claude flagged this while counting the calls on 2026-10-19; I confirmed the v1 split the same day.
Docs call it "the defense model (`ADS_GEMINI_MODEL`)", not "the main model".

## 2. The daily cap is per model, from v1's own call budget

`academic_defense_simulator/call_budget.py` counts a session's worst-case calls per call role, from the loop bounds already in the engine and panel code, and sums them per model.
A full panel (three domain panelists plus the Devil's Advocate) comes to 40 calls on the defense model and 1 on the suggestions model.

The cap is the smallest of floor(RPD / worst-case calls on that model) across the models in use, less `ADS_QUOTA_MARGIN` (default 1).
**Overrides the brief's** single `ADS_GEMINI_RPD`: `ADS_GEMINI_LIMITS` holds an RPD and RPM per model instead, because the two models have separate quotas.
Startup logs each model's share and which one binds.

The defaults are my project's free tier as AI Studio showed it on 2026-10-20:

| Model | RPM | TPM | RPD | Sessions a day |
|---|---|---|---|---|
| `gemini-3.1-flash-lite` | 15 | 250K | 500 | 12 (40 calls each) |
| `gemini-2.5-flash` | 5 | 250K | 20 | 20 (1 call each) |

Flash-lite binds, so the cap is 12 - 1 = 11 defenses a day.
TPM is recorded but not enforced; a defense's prompts come nowhere near 250K tokens a minute.

v1's per-minute limiter now takes the configured RPM less 2 per provider: 13 for flash-lite, the value v1 verified clean against its 15 RPM, and 3 for 2.5-flash, which is unverified.
Without the setting, v1 keeps its own table unchanged.

## 3. Every Gemini 429 or 503 means "busy", never "done for today"

Decided 2026-10-20.

When a Gemini call fails with a 429 (any quota) or a 503 UNAVAILABLE that survives the provider's one retry, the request answers 503 "The panel is busy right now. Please try again in a minute.", with `Retry-After: 60`.
The turn isn't recorded and `daily_usage` isn't touched.
Only the backend's own quota counter closes a day.

**Overrides the brief**, which mapped a Gemini rate limit to "demo quota exhausted for today".
Claude's earlier proposal was to tell per-minute and per-day 429s apart and close the day on a per-day one.
I captured one of each with `scripts/capture_429.py` and then decided not to classify them at all.
The limiter and the session cap already make both kinds rare, and closing the day by mistake would take the demo down until midnight Pacific, while calling a real daily exhaustion "busy" costs only a few failed retries.

The trade-off I'm accepting: if the daily quota is ever genuinely exhausted (for example, the same key used elsewhere), users see "busy" until midnight Pacific instead of a clear "done for today".
If that ever becomes a real problem, the two captures are what a classifier would be built from.
They are in `backend/tests/fixtures/gemini_429/`, and they differ exactly where a classifier would look: `QuotaFailure.violations[].quotaId` is `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` in one and `GenerateRequestsPerDayPerProjectPerModel-FreeTier` in the other, and `RetryInfo.retryDelay` is 46 s against 8462 s.

The v1 provider raises `LLMQuotaExhaustedError` for a 429 and `LLMServiceUnavailableError` for a 503 that survives the retry.
Both subclass `LLMProviderError`, keep v1's messages, and change nothing for v1's own callers.
