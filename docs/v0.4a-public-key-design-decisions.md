# v0.4a — Public API-Key Design: Decisions + Brief

**Status:** LOCKED — 2026-07-20. Claude proposed all six decisions in our design
conversation; I accepted the full set same day.
**Scope:** User-supplied Gemini key with validation, per-session client
construction, demo mode with layered caps, exhaustion copy through the existing
abort path, and a key-leak audit. This is the slice that turns the quiet v0.3
deployment URL into a shareable one. Zero prompt-template changes —
`PROMPT_VERSION` does not move.
**Builds on:** `ROADMAP.md` → v0.4 scope item 3; `v0.3d-defense-ui-decisions.md`
(aborted-state machinery, stage-aware copy); v0.3h (call-count instrumentation:
~12–15 calls per 4-turn session against 500 RPD); the Day 1 provider abstraction
— this slice is where that seam pays for itself structurally.
**Convention note:** one combined file, decisions + brief together, per the
lean-docs rule. This file is the complete design record for the slice.

## Decision 1 — Two modes at intake: own-key (recommended default) and demo (LOCKED)

A radio control above the upload step:

1. **"Use my own Gemini API key"** — default-selected, labeled recommended.
   Reveals a password-type text input and a help expander titled something like
   *"Don't have a key? It's free — 60 seconds"* containing plain-language
   steps: go to `https://aistudio.google.com/apikey`, sign in with any Google
   account, click Create API key, paste it here. Explicitly states: free tier,
   no billing setup, no card.
2. **"Demo mode — limited session"** — no input; caps stated up front in the
   UI copy (turns per session, sessions per day) so exhaustion is never a
   surprise.

The help expander is a load-bearing part of this design, not decoration: the
audience includes people who have never held an API key, and self-serving them
onto their own free key is what keeps demo mode from being the default path in
practice.

**In plain terms:** when you open the app you either paste your own free Google
AI key (with instructions right there for getting one) or you try a short demo
on my key. The demo tells you its limits before you start, not when you hit
them.

## Decision 2 — Validation via `models.list`, not a generate call (LOCKED)

On own-key submit, exactly one `client.models.list()` call against the supplied
key. Success → proceed; auth failure → inline `st.error` with plain copy
("This key was rejected by Google — check for missing characters or create a
fresh key"), form stays in place, no rerun-and-lose-state.

**Known accepted gap:** a key could pass listing but fail generation (edge-case
restrictions). Rare; the first real generate call's existing error handling
covers it (see Decision 6). The alternative — a minimal generate probe — burns
a generate request from *the user's own* quota on every validation attempt for
marginal certainty. Rejected.

**In plain terms:** we check the key with the cheapest possible "are you real"
call that costs no meaningful quota, instead of a tiny fake question that would
eat into the user's daily allowance every time they paste.

---

## Decision 3 — Key lives in `st.session_state` only; leak audit with real evidence (LOCKED)

The key is never written to disk, never included in session exports or
transcripts, never placed in URL params, never echoed in UI beyond the masked
input widget, and never logged.

"Never logged" must be *shown*, not claimed. The v0.3h call-lifecycle logging
is the concrete risk surface — it must be audited to confirm it logs call
timing/counts only, never client config, headers, or key material. **DoD item:
run a real session with a recognizable test key, capture the full log output,
and paste the grep showing zero occurrences of the key string.**

**Open question this session answers first (flagged 2026-07-20, unresolved at
lock time):** does the v0.3h instrumentation write to stdout only, or to any
file? Does anything anywhere log request metadata? Stdout-only → the audit is
quick. File logging → the audit widens to those paths and the finding gets
recorded in the verification notes either way.

**In plain terms:** your key exists only in your live browser session's memory
and dies with it. And rather than promising that, the evidence includes an
actual log from a real run, searched for the key, coming back empty.

---

## Decision 4 — Client construction goes per-session through the provider abstraction (LOCKED)

**The slice's only structural change.** The Gemini client can no longer be a
module-level or globally cached object built from the project key. Two bugs
live down that road: a global client silently ignores the user's key, and a
naively `st.cache_resource`-cached client would share one user's key across
*all* users — a genuine cross-user security bug, not a style issue.

The provider abstraction's constructor takes the API key as a parameter. The
Streamlit layer builds (or retrieves) the client per session: own-key mode
constructs from the user's key; demo mode constructs from the project key
(sourced from secrets/env exactly as today). If any caching is used it must be
keyed on the key itself; plain per-session construction in `st.session_state`
is acceptable and simpler — smallest correct diff wins.

**Unaffected:** embeddings. `sentence-transformers` is local and keyless; its
existing `st.cache_resource` model-load caching stays exactly as is.

**In plain terms:** today the app has one phone line to Google, opened with my
key when the app boots. Now each visitor gets their own line, opened with
whichever key their session is using. The danger being avoided: accidentally
letting visitor B make calls on visitor A's key because the app reused the
same line — that's the bug the careful construction here rules out.

## Decision 5 — Demo mode: 4 turns, one session per browser session, 8 sessions per day globally; enforcement limits stated honestly (LOCKED)

Three layers:

1. **Turn cap: 4 turns per demo session** (~12–15 LLM calls per v0.3h's
   measured budget). Constant, e.g. `DEMO_MAX_TURNS = 4`.
2. **One demo session per browser session** — flag in `st.session_state`.
3. **Daily global cap: 8 demo sessions per day** — a JSON counter file on
   disk (`{date, count}`; date rolls over → reset). 8 sessions ≈ 100–120
   calls, reserving the bulk of the 500 RPD for me and named-link users.
   Constant, e.g. `DEMO_DAILY_SESSION_CAP = 8`.

**Enforcement honesty, recorded here and in the README:** the browser-session
flag resets on refresh; the file counter resets on Streamlit Cloud container
restarts. A determined person can grind past both. Accepted — the threat model
is accidental quota drain from casual visitors, not adversaries. Real
enforcement means auth infrastructure, which this project has correctly
refused three times; the stated-tradeoff is itself the engineering signal.

Concurrency note: two simultaneous demo starts racing the counter file is
possible and tolerated — worst case the day admits one extra session. Not
worth locking machinery at this scale; noted so it reads as a decision, not an
oversight.

**In plain terms:** demo visitors get one short session per visit, and the app
stops handing out demos after 8 in a day so strangers can't drain my daily
quota. The limits are honest speed bumps, not walls — someone determined could
route around them, and the docs say so plainly instead of pretending
otherwise.

---

## Decision 6 — Exhaustion behavior reuses the v0.3d abort machinery; no new states (LOCKED)

Two paths, both through the *existing* stage-aware aborted-state flow:

1. **Demo turn cap reached mid-session** → session ends via the abort path
   with copy in the voice of the app: e.g. *"Demo limit reached — the panel
   adjourns early. Bring a free Gemini key (60 seconds, link above) to sit a
   full defense."* The partial report renders if the existing abort flow
   supports it at that stage; whatever the abort machinery already does at
   that stage is what happens — no new report logic.
2. **Own-key auth/quota error mid-session** → existing API-error handling,
   with copy that names the likely cause: their key's own rate limits or
   revocation — not a generic "something went wrong."

Daily-cap-reached and demo-already-used are *pre-session* gates: the demo
radio option renders disabled with a one-line explanation; intake never starts.

**In plain terms:** running out of demo turns ends the session the same
graceful way an API failure already does — with a message that tells you
exactly what happened and what to do next — instead of a crash or a mystery.
And if the day's demos are used up, the demo button simply tells you so before
you upload anything.

## Call budget (standing constraint)

Per-session generate budget unchanged (~12–15 calls per 4-turn session). New
cost: one `models.list` per own-key validation attempt — negligible, and not a
generate call. Demo mode *reduces* worst-case daily project-key burn from
unbounded to ~120 calls.

## Verification notes (Code session, 2026-07-20)

**Brief step 1 — logging-paths finding (answered before any code, as required).**
Grepped every `logging.`/`logger.`/`print(`/`FileHandler` in the tree.
Result: stdout/stderr only, everywhere.
`streamlit_app.py`'s `logging.basicConfig(level=logging.INFO, ...)` (the v0.3h
instrumentation) has no `filename=` argument, so it attaches a `StreamHandler`
to the default stream — no file handler exists anywhere in the codebase (`git
grep -n "FileHandler"` empty).
Metadata logged: call sequence number, stage label (one of the `LLM_STAGE_*`
strings), Python thread id, start/return/timeout timing, and on abort the
stage label plus `str(exc)`.
I traced `str(exc)` for the one case that matters — `genai_errors.APIError`,
the exception type an auth/quota failure raises — into the SDK source
(`errors.py`): its message is built from `self.code`/`self.status`/`self.details`,
all derived from Google's **response body**, never from the outgoing request.
The key itself never touches that path: I confirmed in `_api_client.py:800`
that the SDK sends it via the `x-goog-api-key` **header**, not the URL or a
loggable client attribute, and httpx's default INFO-level request log is
method+URL+status only — header dumps are httpcore's DEBUG level, which our
root INFO handler never emits.
This scoped step 6's audit to "does stdout ever contain the raw key string,"
not a wider file search — there was nothing to widen it to.

**Decision 4 — structural finding.** `GeminiProvider.__init__` already took
`api_key` as a parameter and already constructed a fresh, non-cached
`genai.Client` per instance since v0.3h; `git grep -n "genai.Client("` found
exactly one construction site, and the only `st.cache_resource` in the
codebase is the keyless embedding model (Decision 4's stated exception).
So there was no existing violation to fix — the work was routing the *correct*
key value into `_new_provider`/`_new_relevance_provider` per session
(`_active_gemini_key()`, reading `st.session_state.active_api_key`), not a
client-caching bugfix.

**Hard constraint held — no new state-machine states.** The demo-cap and
own-key-error paths both resolve entirely inside the existing `"aborted"`
stage: `DEMO_TURN_CAP_ABORT_STAGE` is a fourth key in the `ABORT_MESSAGES`
dict (the dict was already keyed by label for exactly this kind of extension),
and `_abort_demo_limit()` sets the same `stage`/`abort_stage` fields `_abort()`
does, just without an exception (logs at INFO, not ERROR, and leaves
`abort_message` unset — dev-view's raw-exception caption correctly shows
nothing for a non-error abort). The own-key cause-naming copy is a conditional
caption appended in the existing aborted-stage render block, keyed on
`api_key_mode`, not a new branch. Nothing here needed to invent a stage — did
not have to flag anything back.

**Decision 5 — `_reset()` had to change to hold the flag.** The one snag not
visible from the decision doc alone: `_reset()` wipes all of
`st.session_state`, and both the "aborted" and "done" screens offer "Start a
new session" — including the demo-turn-cap abort screen itself, one click from
undoing the cap it just enforced. Preserved `demo_session_used` explicitly
across the wipe (see the comment at `_reset()`); every other demo/key
session-state key resets normally, matching Decision 5's "resets on refresh"
framing for everything except that one flag.

**Decision 2 evidence gap, disclosed.** The two-keys-two-sessions DoD item
asks for direct evidence, not inference. This environment has exactly one real
Gemini credential (the project key already in `.env`) — no second personal key
to paste as "someone else's own key." I closed this with two levels of
evidence instead of faking a second credential: (a) mocked-SDK unit tests
(`test_gemini_provider.py`) proving two `GeminiProvider` instances built with
different key strings each construct their own `Client` with their own key,
never sharing; (b) a live introspection run using the *real* `GeminiProvider`
class end-to-end (construction only, zero network cost) — the real project key
plus a second, distinct placeholder string, reading each instance's
`._client.models._api_client.api_key` back out. Output:

```
session A client key == real project key passed in: True
session B client key == its own distinct key passed in: True
session A and session B clients hold DIFFERENT keys: True
session A stored key does not equal session B's literal string: True
```

Combined with the live browser run below (which does exercise a real,
different-from-project key end-to-end through actual generate calls), I'm
counting this as satisfying the DoD item's intent, not silently downgrading
it.
