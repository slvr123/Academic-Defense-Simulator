## Context and provenance

I did the free-hosting research in chat on 2026-10-18, and I set the condition for the FastAPI migration then: migrate only if free hosting is viable.
This spike tests the one thing that research could not settle from documentation: whether the embedding model fits Render's free instance (512 MB RAM, fractional CPU) once torch and sentence-transformers are gone.
Claude built the spike and ran it locally; the go/no-go numbers come from Render, not from this machine.

## Pre-committed thresholds (measured on Render free, not locally)

| Check | Threshold |
|---|---|
| Peak RSS | <= 400 MB (headroom under the 512 MB limit) |
| Warm `/spike` embed time, 14 chunks | <= 20 s |
| First request after a spin-down (cold start) | <= 90 s |
| Min cosine vs committed `sample/embeddings.npy` | >= 0.999 |

Branches:
- All pass: GO, the migration proceeds with Render + ONNX.
- RSS fails: NO-GO on ONNX; the next step is a design decision between Gemini embeddings and in-browser embeddings.
- Only latency fails: I report the numbers, and the design decides whether the UX can absorb them.
- Cosine fails: retrieval would change, so a retrieval re-check is needed before any swap.
- Anything else: halt and report.

## What the spike is

A FastAPI app with two routes.
`GET /health` returns `{"status": "ok"}`.
`GET /spike` embeds the 14 committed sample chunks (copied from `academic_defense_simulator/sample/chunks.json`) and returns model load time, embed time, RSS before load / after load / peak during embedding, and the min and mean cosine of each chunk's ONNX vector against the committed sidecar (copied from `sample/embeddings.npy`).
The model loads once at startup, so the first request after a spin-down pays for boot and load, and later requests measure warm embedding.

Requirements (pinned in `spikes/render-onnx/requirements.txt`): `fastapi`, `uvicorn`, `onnxruntime`, `tokenizers`, `numpy`, `psutil`.
No torch, no sentence-transformers, no huggingface_hub.

### Why onnxruntime + tokenizers, not fastembed

The point of the spike is parity with what sentence-transformers produced, and owning the pipeline makes that parity explicit rather than trusted.
The pipeline is four steps: tokenize with truncation at 256, run the official ONNX export, mean-pool over the attention mask, L2-normalise.
That mirrors `SentenceTransformer.encode(normalize_embeddings=True)` for this model (`max_seq_length` 256, mean pooling, per the repo's `sentence_bert_config.json` and `1_Pooling/config.json`).

That control turned out to matter.
The repo's `tokenizer.json` ships with truncation at 128 tokens, not 256.
Our chunks run 1,000-2,900 characters, well past 128 tokens, and with the shipped setting the min cosine against the sidecar is 0.7323 (mean 0.8466).
With truncation overridden to 256 it is 0.99999994.
Any library that takes the tokenizer config at face value would fail the cosine gate on long chunks, so I want that override written down in code I can read.

fastembed would also pull in huggingface_hub, requests, tqdm, loguru, mmh3, pillow and py-rust-stemmers, none of which this needs.

### Runtime settings decided before the Render run

- `ORT_THREADS` defaults to 1.
  The free instance has a fraction of a CPU, while `os.cpu_count()` reports the host's cores, and oversubscribing threads on a fractional CPU only adds contention.
- `ORT_ARENA` defaults to 0 (ONNX Runtime's CPU memory arena off).
  Measured locally with five `/spike` calls each, same build:

  | Arena | Peak RSS, request 1 | Peak RSS, requests 2-5 | Embed s |
  |---|---|---|---|
  | on (ORT default) | 330.8 MB | 444.7-446.9 MB | 1.04-1.08 |
  | off | 280.9 MB | 318.8-320.9 MB | 1.07-1.37 |

  The arena held onto about 125 MB of freed activation buffers and bought no measurable speed, so I turned it off before deploying, not after seeing Render's numbers.
  Setting `ORT_ARENA=1` on Render restores ORT's default if I want the comparison there too.

Both settings show up in the `/spike` response (`ort_threads`, `ort_cpu_mem_arena`).

## Render deployment steps

1. In the Render dashboard: New, then Web Service, then connect this GitHub repo.
2. Branch: `spike/render-onnx`.
3. Root Directory: `spikes/render-onnx`.
4. Language / Runtime: Python 3.
5. Build Command: `pip install -r requirements.txt && python fetch_model.py`
6. Start Command: `uvicorn app:app --host 0.0.0.0 --port $PORT`
7. Instance Type: Free.
8. Environment variables: `PYTHON_VERSION` = `3.13.7`.
   The folder also has a `.python-version` file with the same value; the env var makes it explicit.
   Leave `ORT_THREADS` and `ORT_ARENA` unset so the defaults above apply.
9. Advanced, Health Check Path: `/health`.
10. Create the service and wait for the deploy log to show `model.onnx: 90405214 bytes` from the build step and the service to go live.

Measuring (replace `<svc>` with the service's subdomain):

```sh
# warm: three calls back to back; take embed_s and the highest rss_os_high_water_mb
for i in 1 2 3; do curl -s https://<svc>.onrender.com/spike; echo; done

# cold: leave the service idle for 15+ minutes so it spins down, then
curl -s -o /dev/null -w "cold total %{time_total}s\n" https://<svc>.onrender.com/spike
```

Also check the Metrics tab's memory graph for the same window as a second source for peak memory.
If the build succeeds but `/spike` fails because `model/` is missing at runtime, that falls under "anything else: halt and report".

## Spike 2 - batched embedding under a realistic baseline (pre-registered 2026-10-18, before any measurement)

### Question

Can local ONNX embedding stay under 400 MB on Render free once the backend's real heavy imports are loaded, if the embedder works in small batches, glibc's malloc arena count is capped, and only one embedding runs at a time?

### Changes from spike 1

- The embedder processes chunks in batches of `EMBED_BATCH` (default 2; also run with 1).
- `MALLOC_ARENA_MAX=2` is set through a Render environment variable.
  glibc otherwise creates up to 8 x cores malloc arenas for a threaded process, and each one can hold freed memory.
- At startup the app imports the real backend's heavy runtime deps (`google-genai`, `pymupdf`, `pydantic`, pinned to the app's versions: 2.10.0, 1.28.0, 2.13.4) before loading the model, so the baseline RSS reflects the actual backend.
  Import only: no client is constructed and no API call is made.
  `numpy` moved from 2.5.4 to 2.4.6 to match the app as well.
- A module-level `threading.Lock` makes embeddings run one at a time per process.
- New `GET /spike-concurrent` fires two full embeddings at once on two threads and reports wall time, each thread's elapsed time and cosine (or its error), and peak RSS.
- Responses now also report `rss_bare_mb` (before the backend imports), `embed_batch` and `malloc_arena_max`.
- Unchanged: model files and revision, fp32, truncation at 256, `ORT_THREADS=1`, ORT CPU arena off, `PYTHON_VERSION=3.13.7`.

Spike 1's code is at commit `11ba5fc`.

### Protocol

Run A, with `EMBED_BATCH=2` and `MALLOC_ARENA_MAX=2` and the deploy live:
1. Three sequential `GET /spike` calls.
2. One `GET /spike-concurrent`.

Run B: change `EMBED_BATCH` to 1 in Render (saving the env var redeploys, so the process starts fresh), then repeat steps 1 and 2.

How each check is read from a run's four responses:
- Peak RSS: the larger of the highest `rss_peak_during_embed_mb` and the last `rss_os_high_water_mb`.
  The high-water mark covers startup and model load as well as embedding.
- Warm embed: `embed_s` of `/spike` calls 2 and 3.
- Cosine: `cosine_min` of every `/spike` call and of both `/spike-concurrent` threads.
- Concurrent survival: `/spike-concurrent` returns HTTP 200, both threads report a `cosine_min` and no `error`, its `request_number` is 4 (same process, no restart), and Render's Events and Logs show no out-of-memory restart.

### Thresholds (same as spike 1, plus the concurrent check)

| Check | Threshold |
|---|---|
| Peak RSS, including `/spike-concurrent` | <= 400 MB |
| Warm embed, 14 chunks | <= 20 s |
| Min cosine vs committed sidecar | >= 0.999 |
| `/spike-concurrent` | completes without the process dying |

Each run gets its own verdict.
The overall verdict is GO if at least one run passes every check; the configuration carried into the migration is the passing run with the larger batch.

### Spike 2 verdict: GO with ONNX at `EMBED_BATCH=1`, pending two checks

Under the pre-registered rule (at least one run passes every check), the overall verdict is GO with ONNX at `EMBED_BATCH=1`.
It is pending two things I still have to do:
1. Check Render's Events for out-of-memory restarts during both runs (the last part of the concurrent-survival check).
2. Measure the cold start (first request after a spin-down, <= 90 s).

The concurrent thread timings (8.6 / 17.2 s and 8.2 / 16.5 s) show the lock doing its job: the second embedding waited for the first rather than overlapping it.
Run A's sequential peaks (384-386 MB) were under 400; only the concurrent call pushed it over, even though the lock kept the two embeddings from overlapping.
I have not established where that extra memory comes from.

## Carried-forward requirements for the v2.0 design (not implemented now)

- Cap concurrent embedding requests: queue a small number and reject beyond that with a friendly "busy" message.
  The lock alone bounds the forward pass, not what queued requests hold while they wait.
- Re-measure peak memory with the largest PDF the app accepts, including PyMuPDF parsing.
  Spike 2 embedded 14 chunks from text already extracted, so neither a long document nor parsing has been measured.
- The margins are thin: Run B's 370.2 MB peak is about 30 MB under the 400 MB line and about 142 MB under Render free's 512 MB hard limit.
  Any backend feature that adds resident memory has to be measured against those numbers.

## Not in scope, but the migration will need it

The spike embeds all 14 chunks in one batch.
A real upload can have many more chunks, and activation memory grows with batch size, so the migrated embedder should encode in fixed-size batches (sentence-transformers uses 32) and the RSS check should be repeated with the largest document the app accepts.
