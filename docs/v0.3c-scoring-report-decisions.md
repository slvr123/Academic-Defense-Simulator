## Decision 1 — "Handling pushback": escalation-recovery classification (LOCKED)

This is the metric Day 1 deferred because it "doesn't apply cleanly to a first
question." It ships here as a pure-Python aggregate over the full session.

**Definition:**

- A **pushback event** exists at every turn *t* where
  `difficulty_trajectory[t] > difficulty_trajectory[t-1]` — the candidate was
  escalated into that question.
- Each event is classified by comparing the **quality sum**
  (`clarity + depth + grounding`, range 3–15) at turn *t* against turn *t−1*:
  - **`recovered`** — sum improved, **or** sum at turn *t* ≥ 11 (the existing
    strong-answer threshold from `_should_follow_up`, Day 4 Decision 3)
  - **`held`** — sum within ±1 of the prior turn
  - **`deteriorated`** — sum dropped by more than 1
- Precedence: `recovered` is checked first (a strong answer under escalation is a
  recovery even if the raw sum dipped from an even stronger prior answer), then
  `held`, then `deteriorated`.
- A session with **zero escalations reports exactly that** — an empty event list,
  no fabricated insight, no "N/A" placeholder metric.

Every classification is traceable to exactly two turns in the transcript. No LLM
involvement, no heuristic that can't be probed.

**Threshold status:** the ±1 band for `held` is a **defensible default, not
evidence** — same epistemic status as the 0.85 grounding threshold at v0.2.5. It
gets tuned (if at all) from real report output against live sessions, not
re-guessed. Reusing the existing ≥ 11 strong threshold instead of inventing a
second constant keeps the report consistent with the branching logic that shaped
the session it's reporting on.

**In plain terms:** "handling pushback" means: *when the panel turned up the heat,
what did you do?* The difficulty trajectory already records every moment the heat
went up. For each of those moments, we look at your answer quality right before
and right after. If quality went up (or stayed genuinely strong), you recovered.
If it stayed about the same, you held. If it dropped, you crumbled under pressure.
That's it — three buckets, computed from numbers the session already produced,
each one checkable by hand against the transcript. We deliberately did **not** ask
the LLM to judge "how well did they handle pushback," because that would be an
unverifiable vibe; this is arithmetic.

## Decision 2 — Report schema: `DefenseReport` on the session (LOCKED)

New Pydantic models in the models module:

```python
class PushbackEvent(BaseModel):
    turn_index: int                 # the escalated-into turn (t)
    prior_turn_index: int           # t-1
    difficulty_from: int
    difficulty_to: int
    quality_sum_prior: int          # 3–15
    quality_sum_at: int             # 3–15
    outcome: PushbackOutcome        # str enum: recovered / held / deteriorated

class PanelistReportSection(BaseModel):
    archetype_key: str
    panelist_name: str
    turns_taken: int
    avg_clarity: float
    avg_depth: float
    avg_grounding: float
    primary_gaps: list[str]         # every non-null gap this panelist surfaced, in order

class DefenseReport(BaseModel):
    difficulty_trajectory: list[int]        # per-turn difficulty_current, first-class per ROADMAP
    overall_avg_clarity: float
    overall_avg_depth: float
    overall_avg_grounding: float
    panelist_sections: list[PanelistReportSection]   # composition order
    pushback_events: list[PushbackEvent]
    narrative: Optional[str] = None
    narrative_fallback_used: bool = False
```

`DefenseSession` gains one field:

```python
report: Optional[DefenseReport] = None   # populated by the engine at session end
```

**Why on the session, not export-time-only (like `prompt_version`):** the numbers
are recomputable from `turns`, but the **narrative is not** — it's LLM output;
regenerating it produces different text. It's session *content*, not provenance
metadata. And 0.3d's UI renders the report from session state, so it has to live
there anyway. `prompt_version` stays export-time-only, unchanged.

**Per-panelist sections are new scope relative to the Day 1 deferral** — flagged
per the standing rule, not silently added. Rationale: Day 1 deferred a
single-panelist metric; 0.3c lands *after* 0.3b shipped a real panel. A report
that can't say *which panelist* found which gaps would be reporting on a product
that no longer exists.

**In plain terms:** the report is a typed object with three layers — the whole
session (averages + the difficulty line over time), each panelist (their averages
and every weakness they caught), and the pushback events from Decision 1. It gets
attached to the session itself rather than bolted on at download time, for one
simple reason: everything else in the report could be recalculated later from the
turns, but the narrative paragraph is one-of-a-kind LLM text — throw it away and
you can't get the same one back. So it belongs *inside* the saved session. The
difficulty trajectory is stored as the full turn-by-turn sequence, not just a
summary, because insights like "recovered after escalation" need the actual line,
not its average.

## Decision 3 — Narrative call: numbers in, prose out (LOCKED)

One LLM call at session end. **Input: the computed `DefenseReport` serialized to
JSON, minus `narrative`/`narrative_fallback_used`. Nothing else.** No transcript,
no candidate answers, no chunks, no digest.

- **Model: flash-lite** (dev default, env-swappable, same mechanism as
  everything). This is a *writing* task, not a *judgment* task — all judging
  already happened per-turn on the scoring calls. The Day 4 finding disqualifies
  flash-lite from judgment specifically; generation was separately probed at
  v0.2.5/0.3a and passed.
- **New template:** `REPORT_NARRATIVE_PROMPT`, lives in the prompts module with
  the others. Instructs: summarize performance from the provided data only; do
  not invent facts, scores, or events not present in the data; address the
  candidate directly; concise (target 150–250 words). Output is **plain text**,
  not JSON — there is no structure to enforce, and demanding JSON adds a parse
  failure mode for zero benefit.
- **`PROMPT_VERSION` bumps `"0.3b"` → `"0.3c"`** — new template in the set.
  No wording changes to any existing template; the diff outside the new
  template is zero (state this in the Code session's verification notes, same
  pattern as 0.3a's scoring-prompt note).

**In plain terms:** the ROADMAP already locked the principle — Python does the
math, the LLM only writes it up. This decision is about making that principle
mechanically enforceable: the narrative call literally *cannot* contradict the
data or hallucinate a detail from the session, because the only thing it ever
sees **is** the data. It never sees what you actually said, so it can't misquote
you; it never sees the document, so it can't invent a claim from it. Fabrication
isn't prevented by asking nicely in the prompt — it's prevented by starving the
call of raw material. And we use the cheap model because turning a table of
numbers into readable feedback is writing, not judging — the judging that
flash-lite is provably bad at already happened, on every turn, before this call
ever runs.

## Decision 4 — Failure behavior: retry once, fall back to numbers-only (LOCKED)

If the narrative call fails (timeout, API error, empty response): **retry once,
then ship the report with `narrative=None`, `narrative_fallback_used=True`, and a
`logging.warning`.** The session never fails over the narrative.

This is the **second deliberate departure from 5a's fail-clean rule**, same class
as 0.3a's persona fallback, justified identically: 5a's rule protects *transcript
integrity* — a silently skipped question or score corrupts the defense record.
Here the defense is already complete and every number is intact; only prose is
missing. Failing a finished session over garnish is the wrong trade.

The fallback flag lives **on the report model** (not export-time like
`personas_fallback_used`) because the report is session content (Decision 2) —
an eval reading a stored session must know whether the narrative it doesn't see
was never generated or was stripped.

**In plain terms:** by the time the report runs, you've already finished the whole
defense — six turns, all scored, all saved. If the very last API call flops, the
only thing missing is the paragraph of prose *about* numbers you already have.
Killing the entire session over that would throw away everything real to protect
something decorative. So: try again once, and if it still fails, you get the full
numeric report with a flag saying "narrative missing," and the session completes
normally. Compare that to 5a's rule, which is about mid-session failures — there,
a missing question or score means the transcript is a lie, so dying loudly is
correct. Different failure, different stakes, different rule — and we write down
*why* so it reads as a principle, not an inconsistency.

## Decision 5 — Placement: new `report.py` module, engine calls it once (LOCKED)

- New module `academic_defense_simulator/report.py`: the pure aggregate functions
  (trajectory extraction, quality sums, pushback classification, per-panelist
  attribution) plus the narrative-call orchestration.
- Engine calls `build_report(session)` **once, after the final turn**, assigns
  the result to `session.report`. Drivers (`main.py`, `streamlit_app.py`) change
  minimally — the CLI driver prints the numeric report; UI rendering is 0.3d.
- Every aggregate function is a **zero-LLM pytest target**. Required test
  coverage: trajectory correctness; pushback classification hitting all three
  outcomes plus the zero-escalation case plus the recovered-precedence case
  (strong answer with a dipped sum); per-panelist attribution on a synthetic
  multi-panelist fixture; averages; narrative fallback forced (mock/injected
  fault, mechanism stated, per the standing evidence bar).
- Import boundary holds: `report.py` imports no streamlit; the narrative call
  goes through the existing provider abstraction.

**In plain terms:** the report logic gets its own file instead of being stuffed
into the engine, for the same reason the retriever and grounding check got their
own files — one job per module, and every piece of the math becomes a plain
function we can unit-test without spending a single API call. The engine just
calls `build_report` once when the session ends. Because it all runs through the
engine, the report works identically headless (CLI) and, later, in the browser —
which also means 0.3c stays fully verifiable *without* touching the Streamlit
layer where the hang lives.

## Decision 6 — Call budget: 2T + 1 (DECLARED)

Per standing constraint 2, stated against 0.3b's declared **2T**:

- **2 calls per turn** (generation + scoring, active panelist only) — unchanged.
- **+1 report narrative call** at session end (worst case +2 with the single
  retry, failure path only).
- **Session of T turns = 2T + 1 calls.** A 6-turn session = 13 calls;
  with 0.3a's extraction + persona calls, a full app session = **15 calls**,
  ~33 sessions/day against the 500 RPD budget.

Digest rendering and all report aggregation remain **0 calls**.

**In plain terms:** the whole report costs exactly one extra API call per
session, ever, because all the analysis is local Python — the call is only for
the write-up. We state it explicitly because that's the standing rule: every
version declares its per-session cost so nothing ever multiplies calls silently.

## Definition of done (0.3c Code session — brief to be drafted from this doc)

- `pytest` green including all new report tests, output pasted
- One real end-to-end session (CLI, DAZSMA doc) producing a populated
  `DefenseReport`: raw JSON pasted, every number hand-traceable to the turns
- Pushback classification demonstrated against real trajectory data (or a
  replayed session if the live run produces zero escalations — state which)
- Narrative generated live from a real report: prose pasted alongside the input
  JSON, spot-checked to contradict nothing
- Fallback forced (mechanism stated), numbers-only report + flag + warning shown
- Export JSON shows `prompt_version: "0.3c"` and the report riding inside
  `session`
- Import boundary intact; no new dependencies; existing 85 tests still green
